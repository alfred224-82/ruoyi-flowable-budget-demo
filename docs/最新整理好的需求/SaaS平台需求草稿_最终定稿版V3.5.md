# 多租户 SaaS 平台（小微版）需求草稿 · 最终定稿 V3.5

> **版本**：V3.5（行业模板版，当前定稿）
> **适用范围**：内部需求基线 / 技术评审 / 开发交付依据
> **平台边界**：仅描述**小微版（生活服务/到店服务类）**，企业版（资金管控/工程项目类）另行立项，不在本文档范围内。

---

## 一、平台总体架构

1. **平台定位**
   - 统一 SaaS 平台，支持多租户隔离。
   - 租户分为**小微版**与**企业版**两大类，底层技术架构一致，**业务术语与逻辑完全隔离**（见「术语隔离」原则）。

2. **租户类型（Tenant Type）**
   - **小微版（Life/Service）**：面向**到店服务类**本地生活服务业（桌游、足浴、健身、美业等）。
   - **企业版（Enterprise）**：面向资金管控、工程项目类客户（有项目经理、生命周期、审批流）。
   - **术语隔离原则**：
     - 小微版统一称 **「服务项目」**；
     - 企业版统一称 **「工程项目」**；
     - 两套术语在各自业务域内**互不可见**，禁止混用。

3. **隔离原则**
   - **数据隔离**：基于 `tenant_id` 的硬隔离，跨租户数据不可见。
   - **功能隔离**：登录后根据租户类型动态加载菜单。
   - **物理隔离**：代码仓库、数据库、部署环境建议独立，规避合规风险（见第十一章）。

## 二、核心实体：项目（Project）模型

> **需求决策：单表设计，不分表，通过类型字段区分。**

1. **统一概念**
   - 系统内统称「项目（Project）」，通过 `project_type` 字段区分业务形态。
   - 小微版项目即**「服务项目」**（足浴 60 分钟、私教课、剧本杀等）。

2. **小微版项目（服务项目）**
   - **定义**：租户长期提供的**服务**（不支持实物商品，实物/零售类见第十章排除清单）。
   - **特征**：
     - 无强制项目经理（一线执行人为「员工」，见第四章）；
     - 长期有效（不受项目起止时间限制）；
     - 关联属性：价格、时长、主图。
   - **业务关联**：活动、推广码、海报、房间、员工角色。

3. **设计原则**
   - 物理上只有一张 `Project` 表，差异字段（价格、时长等）在同一表中共存（非必填）。
   - **禁止**为小微版与企业版分别建立独立的 `service_item` / `engineering_project` 表。
   - 业务层通过 `project_type` 做逻辑分支，避免冗余。

## 三、通用评价与点赞体系（互通设计）

> **需求决策：评价用户（User），而非角色。**

1. **评价对象**
   - 评价的目标是**「用户（User）」**（具体的人），而非「技师」「教练」等头衔。
   - 技师、教练、项目经理本质都是 `User`，只是**角色标签**不同。

2. **通用模型**
   - 建立统一的评价/点赞表，核心字段：
     - `target_user_id`：被评价人；
     - `author_user_id`：评价人；
     - `rating`：星级；
     - `content`：评论内容；
     - **`scene`（场景字段）**：区分评价来源。
       - `SERVICE`：小微版（顾客给服务人员的评价）。

3. **展示逻辑**
   - 小微版：服务人员详情页，仅展示 `scene = 'SERVICE'` 的评价。
   - **个人总览**：可聚合该用户在所有场景下的平均评分（如：某员工既是足浴技师又是健身教练，显示综合评分）。

## 四、角色体系与权限控制（原子定义 vs 业务编排）

> **核心架构：「平台-租户」两级角色，租户内严格区分「原子定义权」与「业务编排权」。**

### 4.1 平台级角色（Admin）

- **平台管理员 (Admin)**：系统超级管理员。
  - 负责全局配置、**发放 License Key**、监控平台健康度、**设计并维护行业模板**。
  - **不直接参与具体租户的经营**。

### 4.2 租户级角色（控制层）

#### A. 租户管理员 (Tenant Admin) —— 原子定义者
租户的**最高权限者**（通常为注册者/购买者）。拥有**原子定义权**，负责构建租户的经营基础资源。

- **版本控制（License）**：
  - 在 PC 端输入 **Admin 发放的 License Key**，激活并管理租户版本（免费版/付费版）及有效期。
- **初始化配置（行业模板）**：
  - 创建店铺时**选择所属行业**，**一键套用** Admin 提供的**行业模板**，瞬间初始化房间、项目、角色及绑定关系（详见第十六章）。
- **原子定义（造积木）**：
  - **定义房间**：创建物理空间（包厢、大厅、场地），设定物理属性（名称、容量、设备）。
  - **定义项目**：创建服务/商品（足浴、SPA、私教课），设定经营属性（名称、价格、时长）。
  - **定义角色**：基于 `Staff` 基类**裂变**具体业务岗位（洗脚技师、按摩师、前台）。
  - **定义视觉**：从系统预置的 **4 套主题** 中选定并应用租户整体视觉风格。
- **个性化微调**：在模板基础上**按需新增、修改、删除、重绑定**（详见第十六章）。
- **账号分发**：创建「老板」角色的账号，赋予其经营权限（**租户管理员可创建老板，老板不可创建租户管理员**）。

#### B. 老板 (Boss) —— 业务编排者
由租户管理员创建的**业务经营者**。拥有**业务编排权**，负责将原子资源组合成可销售的商品和流程。

- **业务编排（搭积木）**：
  - **资源绑定**：将**房间**与**项目**关联（如：888 包厢只能做 SPA）；将**项目**与**角色**关联（如：SPA 只能由按摩技师做）。
  - **人员配置**：将具体员工（如：张三）**挂靠**到已定义的角色中（如：把张三挂到「按摩技师」下）。
  - **调度确认**：基于排班和预约，进行人工干预、确认订单、处理异常。
- **经营查看**：查看财务数据、员工业绩、经营报表。

### 4.3 执行与消费角色

- **员工 (Staff)**：一线服务人员。根据老板的编排和排班，执行服务、查看个人业绩。其权限由挂靠的**具体岗位角色**决定（如：技师可接单，前台可核销）。
- **顾客 (Customer)**：消费端用户。拥有浏览、预约、支付、评价权限。

### 4.4 权限边界总结

- **租户管理员**：管「**有什么**」（房间、项目、角色、主题、版本、模板套用）。
- **老板**：管「**怎么用**」（绑定关系、排班、调度、看钱）。
- **员工**：管「**怎么干**」（接单、服务）。

### 4.5 权限继承与隔离

- **继承**：裂变岗位（如洗脚技师）**继承** `Staff` 基类的系统权限（登录、接单）。
- **隔离**：通过**岗位标签**与**资源白名单**（房间、项目）实现业务隔离。
- **数据隔离**：所有角色数据严格基于 `tenant_id` 进行物理隔离。

## 五、资源调度与预约规则

### 5.1 资源绑定关系（强控，老板职责）

> **核心原则：默认隔离，手动授权。房间、项目、员工之间默认互不关联，所有绑定由老板在 PC 端完成。**

1. **房间 ↔ 项目**
   - 老板配置：指定某个房间**仅能承接**特定项目（如：剧本房只能玩剧本杀，豪华包厢只能做 SPA）。

2. **项目 ↔ 角色**
   - 老板配置：指定某个项目**仅允许**特定岗位角色执行（如：SPA 项目仅限「SPA 技师」岗位）。
   - **拖拽式管理**：老板将**岗位角色**（而非具体人名）拖入项目白名单——**只有拥有该标签的员工才能被预约执行该项目**。

3. **房间 ↔ 角色（可选高级玩法）**
   - 老板可指定某个房间**仅允许**特定岗位角色进入（如：大厅仅限学徒/保洁）。

4. **顾客端表现**
   - 顾客只能看到并选择**被老板授权**的合法组合（房间 + 项目 + 员工）。
   - 提交预约时，后台强制校验 `房间-项目-员工` 组合合法性，**非法组合一律拦截**。

### 5.2 房间与大厅策略

1. **房间定义**：物理空间（包厢、场地、工位），由**租户管理员定义**。
2. **大厅定义**：系统内置的**虚拟房间**，不可删除，作为未预约时的默认归属。
3. **预约兜底**：顾客未主动预约房间时，订单自动关联「大厅」。
4. **行业差异**：到店服务类（桌游、足浴、健身）默认支持房间预约；**零售/生鲜类不在本平台适用范围内**（见第十章）。

### 5.3 资源状态与人工兜底

1. **状态定义**：空闲 (Idle)、忙碌 (Busy)、锁定 (Locked)、维护 (Maintenance)。
2. **系统自动计算**：基于排班表与预约订单自动标记状态。
3. **人工干预（最高优先级）**：老板在 PC 端可**强制修改**任何房间或员工的状态，**覆盖系统逻辑**。
4. **调度看板**：PC 端提供可视化日历/甘特图，支持老板拖拽调整订单归属。

## 六、员工排班与调度

1. **周期性排班（周模板）**
   - 老板在 PC 端设置**周排班模板**（定义一周 7 天，每天哪些岗位/员工上什么班次）。
   - 系统依据模板自动生成未来（可配置周期）的每日排班数据。

2. **临时变动（手动调整）**
   - 老板可对任何日期的排班进行**手动修改**（换班、取消、增班）。
   - 手动修改**优先级最高**，覆盖周模板，系统记录操作日志便于审计。

3. **排班与状态联动**
   - 员工**仅在排班时间段内**才被视为「可服务」。
   - 状态判定优先级：**老板手动锁定 > 无排班 > 有预约（忙碌） > 无预约（空闲）**。

---

## 七、活动与有效期管理

1. **有效期强制**
   - 所有活动必须设置有效期（`start_time`, `end_time`），过期后自动注销（状态变更为 `EXPIRED`）。

2. **客户端表现**
   - 小程序端**仅展示进行中的活动**，过期/注销活动不可见。

3. **历史记录**
   - **仅限 PC 端租户管理员**可见（含活动配置、扫码数据、首单数据、奖励发放记录）。
   - 小程序端（含老板本人）不可见历史记录。

## 八、版本分级、License 机制与海报生成

> 本平台采用**「免费版引流，付费版变现」**策略，通过功能隔离满足不同发展阶段商家的需求。

### 8.1 版本定义

- **免费版 (Free)**：定位于**基础营销获客工具**。仅提供活动发布、推广码归因及**基础海报合成**功能。商家需自行准备素材，系统仅负责按固定模板合成。
- **付费版 (Pro)**：定位于**全链路经营管理系统**。在免费版基础上，解锁预约调度、资源管理及**智能设计（AI/主题）**等核心经营功能。

### 8.2 版本控制（License 驱动）

1. **生成**：平台管理员（Admin）生成包含版本信息、有效期、资源限制的 License Key。
2. **输入**：**租户管理员**在 PC 端「系统设置」中输入 Key。
3. **校验**：系统验证 Key 合法性（签名、有效期、租户 ID）。
4. **生效**：验证通过后，租户版本立即升级，付费功能菜单解锁，**历史活动与归因数据完全继承**。

### 8.3 功能矩阵对比

| 功能模块 | 免费版 (Free) | 付费版 (Pro) |
| :--- | :--- | :--- |
| **核心营销** | ✅ 活动管理、推广码、首单识别 | ✅ 含免费版所有功能 |
| **海报生成** | ✅ **基础合成**（自助上传 + 强控尺寸） | ✅ **智能设计**（AI 生图 + 4 套主题 + 预览） |
| **素材来源** | **老板自行上传**（需符合尺寸） | 系统主题库 / AI 生成 |
| **编辑能力** | ❌ 不可编辑（位置/字体固定） | ✅ 所见即所得（换主题/微调） |
| **视觉门槛** | 高（需懂图片处理） | 低（小白也能做） |
| **服务/空间/人事管理** | ❌ 不支持 | ✅ 项目、房间、员工角色、排班 |
| **调度预约** | ❌ 不支持 | ✅ 资源绑定、可视化调度、人工兜底 |
| **评价/报表** | ❌ 不支持 | ✅ 订单管理、评价/点赞、全维度报表 |

### 8.4 海报生成逻辑差异（核心细节）

#### A. 免费版逻辑（自助强控）
1. **自助上传**：老板需自行准备海报背景图并上传。
2. **尺寸强控**：
   - 系统**强制校验**图片尺寸（建议宽高比 `3:4`，标准尺寸 `750px × 1000px`，**以最终 UI 稿为准**）。
   - **不符合尺寸 / 宽高比 / 文件过大（如 > 2MB）则禁止上传**，并给出明确提示。
   - **目的**：保证生成的海报**正好放入小程序展示区，不变形、不模糊、不裁切关键内容**。
3. **固定合成**：
   - **底层**：老板上传的背景图；
   - **中层**：系统按**预设坐标**叠加活动文字（标题、奖励金额），字体、颜色、位置**固定不可改**；
   - **顶层**：系统生成的**推广码**，位置固定（如底部居中）。
4. **主题配色**：文字与码的**颜色**沿用租户管理员选定的主题配色，保证整体视觉统一。
5. **目的**：确保海报在小程序内展示时**尺寸精确、不变形**，虽不美观但保证可用、能发出去。

#### B. 付费版逻辑（智能设计）
1. **主题库 / AI**：提供 4 套预设主题，支持 **AI 生成背景图**，无需老板准备素材。
2. **所见即所得**：PC 端支持实时预览，老板可切换主题、微调文字。
3. **一致性**：PC 预览与小程序生成效果 **100% 一致**。
4. **目的**：提升品牌形象，提高点击率，降低操作门槛。

### 8.5 业务逻辑

1. **免费版定位**：商家通过「自助上传 + 系统合成」的方式，**零成本**发出活动海报进行地推/朋友圈推广。
2. **升级路径**：商家因「嫌上传麻烦」或「想要更好看的海报 / 需要预约排班管理」而升级。升级后，**历史活动数据与推广归因数据完全继承**，海报能力无缝切换至智能设计。
3. **降级路径**：付费版到期未续费，自动降级为免费版。高级海报功能停用，已生成的高级海报保留为静态图片但**不可再编辑**。

### 8.6 技术实现原则

1. **接口拦截**：后端基于租户 `version` 字段对所有 API 进行权限校验（**尤其 AI 生成接口，免费版一律拒绝**）。
2. **合成引擎**：
   - 免费版：使用简单的图片合成（如 GD / Imagick / Canvas），**不做 AI 调用**；
   - 付费版：对接 AI 绘图 API + 主题排版引擎。
3. **前端适配**：免费版隐藏「主题配置」和「AI 生成」按钮，仅展示「上传背景图」入口。

## 九、行业适配性说明

### 9.1 已验证适配行业（小微版 · 到店服务类）

以下业态可直接复用本平台核心逻辑（项目、活动、推广、评价、预约、排班），**且均已配套对应行业模板**（详见第十六章）：

- **休闲娱乐**：桌游、剧本杀、棋牌室、KTV、电竞馆、轰趴馆。
- **生活服务**：足浴、推拿、SPA、美容美发、美甲美睫、洗衣洗鞋、宠物美容（小型）。
- **运动健身**：健身房、瑜伽馆、普拉提、羽毛球/网球/游泳馆、舞蹈室。
- **专业工作室**：摄影写真、理发工作室、家政保洁团队。

### 9.2 明确排除行业

以下业态**不属于小微版范畴**，建议归入**企业版**或不予接入：

- **医疗机构**：综合医院、连锁体检中心、大型宠物医院（执业资质、HIS、医保对接）。
- **大型生产 / 物流**：工厂、仓储物流、快递分拨（MES/WMS/TMS 系统）。
- **教育机构**：K12 学校、大学、大型连锁教培（学籍管理、监管）。
- **大型住宿**：连锁酒店、星级酒店（单体小民宿除外）。
- **政府 / 事业单位**。

#### ⚠️ 关于「零售 / 生鲜（卖菜等）」的专项说明

- **现状**：本平台**小微版暂不将零售/生鲜（卖菜等）列为适用行业**。
- **核心原因**：零售业态**高度依赖库存管理**，而库存模块**不在当前版本范围内**（见第十二章待确认项）。
- **定位**：零售/生鲜属于**后续独立评估**的方向，待「库存管理模块」开发完成后再纳入适用清单。
- **版本兼容性**：由于**免费版的「活动 + 推广码」能力不依赖库存**，理论上零售商家**可先使用免费版做营销获客**；但**付费版的预约/排班体系以「到店服务」为前提**，零售商家升级付费版**暂无明显收益**，因此**整体暂不推荐**。
- **后续动作**：如需支持，应**单独设计并开发「库存管理模块」**，再重新评估行业适配。

### 9.3 边界界定（特殊说明）

- **民宿 / 小型旅馆**：仅限**单体小店**，老板自主经营、房间少、流程简单，可视为小微版（类似桌游包厢管理）；连锁酒店归入企业版。
- **牙科 / 医美诊所**：仅限**医生个人工作室**，规模极小、流程简单，勉强可纳入；连锁机构 / 多角色分工 → 企业版。

## 十、合规与运营边界（基金行业背景）

1. **兼职与披露**
   - 本平台业务与现任职基金公司（资金管控方向）**完全无关**，开发在下班后、使用私人设备与网络完成。
   - 需查阅劳务派遣合同及公司制度，确认是否需申报**外部营利性活动**。

2. **主体与收款**
   - **建议**：注册**个体工商户**作为运营主体，与基金公司**物理隔离**。
   - **收款**：线上**不接入**微信支付商户号，所有交易走**线下**（个人收款码 / 现金），规避资金监管风险。

3. **推广与社交**
   - **严禁**在公司群、项目群、含同事/客户的群内推广。
   - **允许**在纯私人生活群推广，**朋友圈需分组屏蔽**金融圈同事。

## 十一、推广与归因规则

1. **一店一码**：每个租户拥有独立的推广码体系。
2. **归因逻辑**：以**「谁最后扫码」**为准——顾客被多个码引导时，归属最后一个扫码的推广者。
3. **首单识别**：系统自动判断顾客是否为新客，用于发放首单奖励。

## 十三、PC 端菜单划分（权限落地参考）

为体现**「租户管理员造积木，老板搭积木」**的分工，PC 后台菜单建议如下划分：

### 13.1 「系统设置」菜单（仅租户管理员可见）
**原子定义 + 系统控制**：
- **房间管理**：增删改查房间（名称、容量、设备）。
- **项目管理**：增删改查项目（名称、价格、时长、描述）。
- **角色管理**：裂变岗位、定义岗位名称。
- **主题管理**：选择主题、预览。
- **License 管理**：输入密钥、查看版本与有效期。
- **账号管理**：创建/管理「老板」角色账号。
- **行业模板**：选择/切换行业模板（初始化时）。

### 13.2 「经营后台」菜单（老板可见）
**业务编排 + 经营查看**：
- **资源绑定**：
  - **房间-项目绑定**：哪些房间能干哪些活。
  - **项目-角色绑定**：哪些活由哪些人干。
- **排班管理**：把人按角色排到具体日期。
- **预约调度**：日历视图、拖拽订单、强制改状态。
- **活动管理**：发优惠券、搞促销。
- **数据报表**：看谁干得多、谁赚得多。

以**足浴店**为例，端到端演示角色分工：

3. **老板**：把员工（张三、李四）**挂靠**到「洗脚技师」角色 → 发活动 → 拉客 → 预约开搞。

## 十六、行业模板与初始化机制（新增）

> **核心逻辑：Admin 为每个行业预制「标准配置脚手架」，租户管理员一键套用后再按需微调，无需从零开始。**

### 16.1 模板定义（平台管理员 Admin 职责）

1. **概念**：模板是针对**特定行业**预配置的一组**原子数据**及其**业务绑定关系**。
2. **内容**：每个行业模板包含：
   - **房间预设**：常见的空间划分（如：大厅、普通包厢、豪华包厢）。
   - **项目预设**：常见的服务项目（如：足浴 60 分、修脚、SPA 90 分）及其属性（价格、时长）。
   - **角色预设**：常见的岗位裂变（如：洗脚技师、按摩技师、前台）。
   - **绑定关系预设（核心）**：房间-项目、项目-角色的**默认关联**（如：豪华包厢只做 SPA，SPA 只有按摩技师能做）。
3. **管理**：由平台管理员（Admin）在平台后台统一维护，与具体租户**解耦**。

### 16.2 模板套用（租户管理员职责）

1. **时机**：租户创建店铺 / 首次登录后台时。
2. **操作**：系统提示「请选择您的行业」，租户管理员**选择对应行业**（如：足浴）。
3. **系统行为（一键初始化 / 深拷贝）**：
   - 将模板中的**所有房间定义**复制到该租户下（关联 `tenant_id`）；
   - 复制**所有项目定义**；
   - 复制**所有角色定义**（即完成裂变）；
   - 复制**所有绑定关系**。
4. **结果**：租户管理员登录后，**系统已具备基本经营结构**，房间、项目、角色、绑定关系全部就位，无需从零配置。

### 16.3 模板微调（租户管理员职责）

1. **原则**：套用后的数据**完全归属租户**，与模板**脱钩**，可自由修改。
2. **操作**：
   - **新增**：增加房间、项目、角色（如：加一个「VIP 包厢」）。
   - **修改**：修改名称、价格、时长等属性（如：「足浴 60 分」价格 128 → 98）。
   - **删除**：移除不需要的房间、项目。
   - **重绑定**：调整房间-项目、项目-角色的关联关系。
3. **目的**：在平台提供的「标准脚手架」基础上，适配租户自身的个性化经营需求。

### 16.4 模板与版本

1. **脱钩原则**：模板一旦套用，**后续模板更新不影响已套用的租户**。
2. **可选升级**：平台发布新版本模板时，可提示租户，但**需租户管理员手动确认**是否同步更新（避免破坏现有数据）。

## 附录一：四大核心原则（架构基线）

1. **单表原则**：项目采用单表 + `project_type` 类型字段，**禁止分表冗余**。
2. **通用评价原则**：评价针对 `User`，通过 `scene` 字段实现**一套表管全部场景**。
3. **角色挂靠原则**：岗位角色**均挂靠于 `Staff`**，通过**业务标签 + 资源白名单**实现精细化调度。
4. **人工兜底原则**：系统自动计算**仅供参考**，所有资源状态**以老板手动确认为准**。

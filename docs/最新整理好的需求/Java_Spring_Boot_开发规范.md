# 一、核心思想

本规范的目标不是“出错后补救”，而是让错误根本没机会发生。围绕这一核心，建立一套从代码约束、日志标准化、异常分层到修复决策的完整闭环。

- **开发阶段通过判空、页面控件约束、数据库约束，把大部分问题挡在前面。**源头防错：
- **任何异常都能从日志中直接看出类型、原因、是否需要发布。**日志一眼可辨：
- **每一条线上错误都能映射为一个本地单元测试，不依赖具体用户账号。**测试可复现：
- **根据异常类型自动判断“能否不发布修复”，并给出修复方向。**修复有决策：
- **报错来了就按日志定位、去修、验证，来一条解决一条，不做全局扫描。**逐条解决：

## 5.2 判定原则

一句话：异常的根因在“数据 / 配置 / 基础设施”→ 不发布；根因在“代码逻辑”→ 必须发布。

## 5.3 处理流程

**来一条解决一条，不做全局扫描：**

- 根据日志定位到具体组件 + 具体对象 + 具体状态。
- 查排障手册对应章节，找到匹配的 reason。
- 按“发布判定”决定走不发布的修复还是代码发布。
- 执行修复 → 验证 → 完事。
# 六、后端代码约束：防空指针

核心原则：fail-fast，入口处拦截，不让 null 往下流动。

## 6.1 判空规范

- **参数对象判空，抛异常并带字段名**方法入口：
- **判空，抛 BusinessException（带业务语义）**查 DB 返回单条：
- **判空时返回空列表，不返回 null**查 DB 返回列表：
- **包装为 TechnicalException**调外部接口返回 null：
- **使用前确认不为 null**任何中间变量：
# 七、前端页面约束：防脏数据入库

核心原则：能不让用户自由输入就不自由输入。

## 7.1 文本框约束规范

- 每个文本框对应 DB 字段，maxLength = 字段长度（可略留余量）。
- 数字字段：限制小数位数。
- 必填字段：前端标红 *，提交前校验。
- 长度 / 类型超限：前端直接拦截提示，不发起接口调用。
# 八、数据库约束：最后一道防线

## 8.1 ID 自增长规范

- 所有表必须有 id 字段，自增长。
- 前端 / 接口不传 id，由 DB 生成。
- 业务唯一标识（如 order_no）单独建字段，加唯一约束。
- 前端展示用业务编号，不用自增 ID。
# 九、三层联动防线

从前端到数据库，任何一层都能拦住问题，但越靠前越好——前端拦住用户体验最好，DB 拦住是最后保命。

```
前端页面：下拉框控值 + 文本框限类型 / 长度 + 提交前校验
↓
Controller：入参校验（类型、长度、必填），不合法直接返回
↓
Service：入口判空（fail-fast）+ 业务校验 + 外部调用返回判空
↓
DB：NOT NULL / 长度 / UNIQUE / 外键兜底
```

# 十、日志到单元测试的映射

## 10.1 映射流程

一条日志 → 提取 exceptionType + errorCode/component + method + params → 映射到对应单测类 → 用日志里的参数构造入参执行 → 验证异常类型与字段。

## 10.2 单测分类目录

```
test/
├── unit/             正常流程、边界值
├── integration/      集成测试
└── regression/      日志驱动的回归测试
├── business/    BusinessException 对应
├── technical/   TechnicalException 对应
└── bug/         SystemBugException 对应（修完代码后保留防回归）
```


```
## 要求
1. 判定异常分类（业务/技术/代码bug）
2. 给出根因分析
3. 给出修复方向（区分是否需要发布）
4. 如果需要发布：指出涉及的逻辑范围
5. 如果不需要发布：指出具体操作对象
6. 给出验证方式
7. 给出预防建议
```

## 11.2 输出模板

```
## 异常分类
{类型} — {一句话说明}
## 根因分析
{基于日志字段的推理}
## 修复方向
### 发布判定：{需要 / 不需要}
### 具体操作
- {操作1}
- {操作2}
## 验证方式
{怎么确认问题已修复}
## 预防建议
- {建议1}
- {建议2}
```

## 11.3 约束

- AI 输出中的修复方案，最终由人确认后执行。
- AI 不执行任何变更操作，只输出方案。
- 涉及数据变更的，AI 只说明“改什么对象”，不生成具体 SQL（防误执行）。
- 涉及发布的，AI 只说明“改什么逻辑”，不生成完整代码。
# 十二、开发自审清单

每人提交代码前逐条核对：

- 我的方法入口有没有判空关键参数？
- 我查 DB 返回的对象有没有判空？
- 我调外部接口返回有没有判空？
- 前端这个字段能不能用下拉框？
- 文本框长度有没有与 DB 字段对齐？
- 这张新表的 ID 是自增长的吗？
- 非空字段建表时标了 NOT NULL 吗？
- 如果出问题，日志里能看出是哪种异常吗？
# 十三、完整闭环

**线上异常 → 结构化日志（含 exceptionType 分层）→ 人工 / AI 解析 → 查排障手册定位 → 判定发布与否。**

- **执行修复（DB / 配置 / 运维操作）→ 验证。**不需要发布：
- **写回归单测（用日志 params）→ 修代码 → CI 自动跑 → 发布。**需要发布：
所有回归单测保留在 regression/ 目录，CI 每次自动执行，防止回归。处理节奏：来一条解决一条。

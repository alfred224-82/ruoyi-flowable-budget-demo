## 1. 项目概述

### 1.1 项目背景

本项目是一个面向多行业、多规模客户的 SaaS 服务平台。平台以「公众号为总入口」，整合小程序、直播、活动管理、组团、资金管控等能力，通过「业态包 + 版本开关 + 访问通道」三维组合，服务从个体小老板到中大型企业的全谱系客户。

平台的核心设计理念：一套代码底座，承载多种业态。桌游店、社区生鲜店、小企业报销管控等看似不同的业务，底层共用同一套多租户引擎，仅通过配置差异呈现不同的产品形态。

### 1.2 设计目标

- 统一底座：所有客户共用一套后端、一套数据库、一套权限体系，通过 tenant_id 隔离。
- 业态可插拔：新增行业（如健身房、教培）仅需新增业态包 + 文案映射，不动核心表结构。
- 版本可升级：基础版 → 高级版 → 专业版为「解锁功能」，数据全保留，无需迁移。
- 通道可切换：微信小程序 / 公众号 与 企业微信工作台两种访问方式，按版本自动适配。
- 美观兜底：客户上传素材经系统自动处理，保证输出页面始终在预设审美框架内。

### 1.3 目标客户

| 客户类型 | 典型用户 | 核心诉求 |
| --- | --- | --- |
| 个体小老板 | 桌游店、轰趴馆、社区生鲜/菜店 | 发活动、搞拼团、客人报名、公众号通知 |
| 中小企业 | 20-200 人公司、工作室 | 报销管控、预算编制、审批流、科目体系 |
| 中大型企业 | 200 人+ 多子公司组织 | 多租户、多账套、API 对接、自定义审批、审计 |

## 2. 总体架构

### 2.1 三层架构

平台采用清晰的三层结构，确保底座稳定、业态灵活、变更成本最小：

**公共底座层：**多租户隔离（tenant_id）、收支三表、审批引擎、Schema 页面引擎、组队/组团引擎、微信/企微双通道登录、图片处理管线。所有业态共用，不接受业务定制。

**业态包层：**每个行业对应一个「业态包（biz_bundle）」，包含菜单声明、文案映射、Schema 区块排列、引擎策略。通过 feature_flags / menu_overrides / copy / engines 四个维度描述差异。

**租户实例层：**每个客户是一个租户，关联一个业态包（biz_code）、一个版本（edition）、一个访问通道（access_channel），并可叠加单店微调配置（tenant_biz_config）。

### 2.2 入口拓扑

以公众号为总入口，向下延伸两条主干：

```text
公众号（总入口）
 ├─ 小程序：活动管理（组队活动 / 海报宣传活动）
 └─ 直播：视频号（微信内闭环） / 抖音（仅引流）
```

高级版以上客户使用企业微信自建应用作为入口，复用同一底座，仅通道与端形态不同。

### 2.3 核心设计原则

1. 项目即容器：活动、团购、报销项目、培训报名统一为「项目（project）」，靠 type 区分，共用一张表。
2. 引擎靠策略：组队引擎、审批引擎通过策略模式分发，新业态新增子类，引擎源码零改动。
3. 文案靠映射：前端硬编码中文全部改为 t('key')，同一套代码按业态输出不同文案。
4. 单店靠覆盖：租户级配置（tenant_biz_config.module_overrides）微调，不 fork 业态包。

## 3. 租户与业态模型

### 3.1 关键字段

租户（tenant）是平台的核心聚合根，三个字段共同决定其行为：

| 字段 | 取值 | 作用 |
| --- | --- | --- |
| biz_code | boardgame / fresh_food / fund_control / ... | 指向业态包，决定菜单、文案、区块 |
| edition | basic / advanced / pro | 决定功能可见性（feature_flag） |
| access_channel | wechat / wecom | 决定入口形态与消息通道 |

*三者正交组合，例如：basic + wechat = 桌游店小程序；advanced + wecom = 企业报销系统。*

### 3.2 业态包配置示例

每个业态包定义四类差异（以买菜 fresh_food 为例）：

- 菜单：活动管理、今日特价、拼团、门店设置
- 文案映射：signup → 参团、member → 参团人数、full → 成团
- Schema 区块：菜品大图 + 原价/团购价 + 成团人数 + 截止时间 + 去参团按钮
- 引擎策略：组队引擎子类 GroupBuyStrategy（满员 → pending → 老板确认 → closed）

### 3.3 现有能力复用对照

| 底座能力 | 桌游店 | 社区买菜 | 复用度 |
| --- | --- | --- | --- |
| 多租户隔离 | ✅ 直接复用 | ✅ 直接复用 | 100% |
| 登录/权限/小程序壳 | ✅ | ✅ | 90% |
| 收支三表 | ✅ 轻量 | ✅ 扩展货款类型 | 60% |
| Schema 页面引擎 | ✅ 活动页 | ✅ 团购页 | 85% |
| 组队引擎 | ✅ 满员封团 | ✅ 拼团成团 | 80% |
| 图片处理管线 | ✅ | ✅ | 100% |
| SKU/库存/订单 | ❌ | 需新增 | 0% |

*注：社区买菜若仅做「通知 + 拼团」不涉及电商履约，则 SKU/库存/订单无需开发，直接复用活动+组团模型。*

## 5. 功能模块

### 5.1 活动管理（基础版核心）

活动（Activity）是项目（project）的子类型，通过 extra_config 承载业态差异：

| 字段 | 桌游活动 | 买菜团购 | 企业项目 |
| --- | --- | --- | --- |
| type | activity | team_buy | general |
| 核心配置 | 时段、人数上限、报名规则 | 成团人数、原价/团购价、确认 | 预算、里程碑、审批链 |
| 满员语义 | 自动封团 (full) | 待成团 (pending) | 不适用 |

组队引擎统一处理「凑人」逻辑，买菜拼团仅需新增 GroupBuyStrategy 子类（约 15 行），引擎源码零改动。

### 5.2 海报与主题系统

客户可选 4 套预设风格（暗夜桌游、暖光聚会、清新日系、霓虹赛博），每套为完整 Design Token（背景、主色、卡片、文字）。客户可上传 Logo 与海报，系统自动处理保证美观。

**Logo 处理：**必须透明底 PNG，后端自动加与风格匹配的衬底（圆形/圆角 + 毛玻璃），统一缩放到 80×80px。

**海报处理：**比例校验（头图 750×400 / 海报 750×1000，容差 ±5%）、≤200KB、微信 imgSecCheck 违规检测、顶部渐变遮罩（取自预设主色）、自动提取主色推导卡片配色。

**渲染融合：**预设色打底 → 海报盖于其上并带遮罩 → 内容卡片毛玻璃。三层结构固定，无论素材如何组合均不出框。

### 5.3 直播与公告

直播公告采用「有则显示、无则隐藏」机制：公告为直播状态的投影，后端按状态机判定：

| 直播状态 | 距开播/结束 | 是否显示公告 |
| --- | --- | --- |
| 直播中 (living) | — | ✅ 排第一 |
| 预告 (pending) | ≤ 30 分钟 | ✅ 临近提醒 |
| 预告 (pending) | > 30 分钟 | ❌ 隐藏 |
| 刚结束 (offline) | ≤ 10 分钟 | ✅ 可进回放 |
| 超时 / 回放 | > 10 分钟 | ❌ 隐藏 |

无直播时后端返回 has_announcement=false，前端 v-if 不成立，整个公告区不渲染。视频号走微信内闭环（navigateToChannelsLive），抖音仅做引流页。

### 5.4 资金管控（高级版核心）

复用收支三表（receipt / payment / expense），扩展「货款 / 佣金 / 退款」子类型。高级版增加：预算编制、科目三层架构、烂账标记、发票验真、金蝶导出、按金额/部门/职级的条件审批流。

## 6. 项目管理与活动管理合并方案

将「项目」作为通用容器，「活动 / 团购 / 报销项目」作为项目的 type 子类型，共用一张 project 表 + extra_config JSON 承载差异：

**统一参与人：**project_member 表统一存储参与关系，role 区分 owner / manager / member / participant / signup。

**任务与报名分表：**project_task（企业任务：指派、截止、完成）与 project_signup（活动报名：满员、封团、确认）均 FK 指向 project.id，按业态选用。

**菜单按业态分组：**后台统一为「工作台」，按 type 筛选呈现不同视图（项目看板 vs 活动卡片），底层同一张表。

企业客户升级时，活动花销可自动汇总至项目预算，数据无缝打通。

## 7. 小程序代码与部署策略

### 7.1 核心结论

只维护一套代码，按版本采用不同部署方式：

| 版本 | 部署方式 | 说明 |
| --- | --- | --- |
| 基础版 | 共用一个小程序（平台 AppID） | 公众号菜单带 ?tenant=xxx 跳转，反向识别租户加载数据 |
| 高级版 | 独立小程序（客户 AppID） | 同一套代码换配置（AppID、tenant、主题）编译上传 |
| 专业版 | 独立小程序 + 可选独立部署 | 代码同套 + 定制分支 |

### 7.2 租户识别方式

- URL 参数：小程序路径带 ?tenant=boardgame_001，直接定位。
- 公众号反向识别：跳转不带参，启动时通过来源公众号 AppID 反查 tenant。
- 登录后绑定：用户登录后按账号归属确定 tenant 上下文。

首页需提供「门店选择 / 搜索」入口，既用于过审，也用于用户切换门店。

### 7.3 共用小程序的注意事项

- 微信审核：首页不可空白，需有实质「门店列表」功能。
- openid 绑定：同一 openid 可跨租户，需 user_tenant_bind 表维护多归属，登录时明确当前 tenant 上下文。
- 支付分账：若接入线上收钱，共用商户号需在后端做虚拟账户区分（短期不接支付可忽略）。
- 独立部署脚本：CI/CD 一键切换配置编译，降低人工出错。

## 8. 非功能性需求

| 类别 | 要求 |
| --- | --- |
| 隔离 | tenant_id 强隔离，所有查询必须带租户条件 |
| 安全 | 图片上传经 MIME、尺寸、大小、微信 imgSecCheck 四重校验 |
| 性能 | 公告缓存 TTL 5 分钟 + 状态变更主动失效；图片衍生图异步生成 |
| 可扩展 | 新行业 = 新 biz_bundle + 文案映射 + Schema 模板，不动核心表 |
| 合规 | 一次性订阅消息、企微应用消息，避免骚扰；主体独立、收款分离 |

## 11. 身份识别与登录模型（小微版核心）

> 来源：《小微版完整方案》v10.0 第0章。本章是全文档的第一原则，所有菜单、登录、权限逻辑都服从它。

### 11.1 五个全局约束

| # | 规则 | 说明 |
|---|------|------|
| 1 | **全平台 = 一个微信小程序 = 一个 appid** | 老板/业务员/顾客全部进同一个小程序，不拆包、不区分 appid |
| 2 | **后端以手机号为主键建立用户** | 一个手机号 = 一个 `sys_user`，跨端、跨租户唯一 |
| 3 | **身份只用 `租户号 + 角色` 区分** | appid / 登录渠道**不参与**身份与权限判定 |
| 4 | **只有老板有 PC 后台；其余全部落在小程序** | 老板额外拥有小程序入口（仅看报表/改报价） |
| 5 | **appid 只做合法性校验，不做业务区分** | 后端仅验证请求是否来自我方小程序，取到手机号即完事 |

### 11.2 手机号为主键的用户建立规则

```
小程序 / PC 登录（均走手机号）
  ├── phone 已存在 → 直接登录，返回该用户在各租户的角色
  └── phone 不存在 → 自动注册 sys_user，再按场景建 user_tenant_role
```

| 场景 | 是否自动建用户 | 是否自动建租户关联 | 角色 |
|------|--------------|------------------|------|
| 老板首次扫码/登录（租户已建） | ✅ | ✅ 绑定到该租户 | boss |
| 业务员被平台管理员录入手机号 | 已是用户则绑定，否则待其首次登录补全 | ✅ | salesman |
| 顾客预约/到店付 | ✅ | ❌（顾客无需租户角色，走轻量档案） | customer（可选） |

> **原则：手机号是唯一身份锚点。** 同一个手机号换了端、换了租户，都是同一个 `sys_user`。

### 11.3 租户号 + 角色判定流程

识别顺序（后端统一执行，**无 appid 判断**）：

```
① 手机号             →  定位 sys_user（不存在则自动注册）
② 租户号            →  定位数据范围（多租户时让用户选/从场景带入）
③ 租户 + 角色       →  查角色模板 → 菜单 + perms
④ client_type 过滤  →  按当前前端壳裁剪菜单（PC 全量/小程序精简）
```

> 第④步的「当前前端壳」由调用接口时明确指定（PC 端请求传 `client_type=pc`，小程序端请求传 `client_type=mini`），而不是靠 appid 反查。**appid 在任何业务判断中都不出现。**

### 11.4 多租户选择流程

```
登录成功 → 查 user_tenant_role 得到租户列表
  ├── 仅 1 个租户 → 直接进入，锁定 tenant_id
  ├── 多个租户 → 展示「我的店铺」列表（含角色标签），用户选择后锁定
  └── 0 个租户（纯顾客）→ 走扫码/链接场景带入 tenant_id
```

一旦选定租户，本次会话所有请求携带 `tenant_id`；后端 MyBatis 拦截器自动拼接租户条件，杜绝越租户查询。

## 12. 标准角色集与角色映射机制

> 来源：《小微版完整方案》v10.0 第二章（v9.0 核心设计原则）。
> **角色不分版本定义，权限不分版本硬编码。** 所有版本（小微版、企业版基础/高级/专业）的角色，都来自同一套系统级「标准角色集」。

### 12.1 标准角色集（系统级，admin 定义）

全部版本共用 `sys_role` 这一张表，不分小微/企业、不分行业。新增角色只在此表加一行 + 绑定权限，各版本/各租户即可按需映射。

| 标准角色 code | 名称 | 身份定位 | 主要出现版本/场景 |
|--------------|------|---------|------------------|
| `boss` | 老板 | 最高权限身份（管理端+报表） | 全部版本 |
| `salesman` | 业务员 | 一线服务人员（移动端） | 小微版通用 |
| `customer` | 顾客 | 消费端访客（移动端） | 小微版通用 |
| `project_manager` | 项目经理 | 管项目+团队审批 | 企业版（高级/专业） |
| `expense_staff` | 报销人员 | 提交/查看报销单 | 企业版（基础/高级/专业） |
| `finance` | 财务 | 审核/打款/科目管理 | 企业版（高级/专业） |

> **原则**：角色 code 是「身份」不是「菜单位单」。同一个 `salesman`，在桌游店叫「助教」，在买菜店叫「配送员」，在健身房叫「教练」——**code 不变，只变显示名**。

### 12.2 业务角色 = 标准角色 + 租户内显示名

行业/租户差异 = 只改显示名，不改 code。平台管理员的「角色映射」就是做这件事——从标准角色集挑出本租户要用的，改成本地化名字。

| 标准角色 code | 小微·桌游店 | 小微·买菜 | 小微·健身房 | 企业版·高级版 |
|--------------|------------|----------|-----------|-------------|
| `boss` | 桌游老板 | 菜店老板 | 健身老板 | 老板 |
| `salesman` | 助教 | 配送员 | 教练 | （通常不映射） |
| `customer` | 顾客 | 买家 | 会员 | （通常不映射） |
| `project_manager` | — | — | — | 项目经理 |
| `expense_staff` | — | — | — | 报销人员 |
| `finance` | — | — | — | 财务 |

> 表中「—」表示该租户未映射此角色（平台管理员把它禁用即可）。

### 12.3 两层职责分离

| 层级 | 操作者 | 能做的事 | 不能做的事 |
|------|--------|---------|----------|
| **系统层** | admin | 定义标准角色、绑定菜单/区块、维护行业模板、维护角色模板 | 改具体租户的业务数据 |
| **租户层** | 平台管理员 | **角色映射**：挑选/改名/启用停用 + 把用户分配到角色 | 新建角色 code、改角色权限（菜单/区块） |
| **业务层** | 老板 | 日常经营（定价、结算、看报表） | 改角色、改权限 |
| **业务层** | 业务员/顾客 | 按角色用功能 | — |

平台管理员「角色映射」具体操作（小微版和企业版共用同一套界面）：

```
平台管理员 → 角色管理
├── ① 挑选：从标准角色集勾选本租户需要的角色
├── ② 改名：把标准角色显示为本地化名字（salesman → 「助教」/「主持人」）
├── ③ 启用/禁用：不用的角色直接禁用
├── ④ 分配用户：把具体用户挂到某个角色上（可多对多）
└── ⑤ 调整顺序：在管理后台的显示排序
```

> **平台管理员全程不涉及菜单、perms、区块权限**——这些由 admin 在角色模板里预置好了。

### 12.4 角色模板（菜单 + 区块配方）

标准角色 → 绑定哪些菜单 + 哪些小程序区块。小微版、企业版各一套角色模板，但都引用同一套标准角色集。

**小微版角色模板：**

| 标准角色 | PC 后台 | 微信小程序 | 绑定菜单 |
|---------|---------|-----------|--------|
| **boss** | ✅ 全量管理 | ✅ 报表+改报价 | 经营概览/预约管理/结算/报表中心/定价管理/推广发布/店铺管理 |
| **salesman** | ❌ | ✅ 排班/收入/打卡 | 我的排班/我的收入/打卡 |
| **customer** | ❌ | ✅ 浏览/预约/到店付 | 浏览店铺/预约服务/我的预约/查看收款方式（无在线支付） |

**企业版角色模板（基础/高级/专业共用机制，按版本增减）：**

| 标准角色 | PC 后台 | 微信小程序 | 绑定菜单（示例） |
|---------|---------|-----------|----------------|
| **boss** | ✅ | ✅ 报表/审批概览 | 预算科目/报销审批/科目余额/报表中心/项目管理（高级/专业） |
| **expense_staff** | ❌（或基础录入） | ✅ 我的报销单 | 提交报销/我的报销单/我的待办 |
| **project_manager** | ✅（高级/专业） | ✅ 我的项目 | 项目管理/团队报销审批/项目预算 |
| **finance** | ✅（高级/专业） | ❌ 或轻量审核 | 报销审核/打款队列/科目管理/月度结算 |

> **版本差异（基础→高级→专业）的实现方式**：同一套角色模板 + 不同版本勾选不同菜单范围（在角色模板记录上加 `version_type` 字段区分），**不是**新建角色 code，也不是复制多套模板。

## 13. 行业模板（小微版专属）

> 来源：《小微版完整方案》v10.0 第三章。

**为什么只有小微版需要行业模板：**

| | 小微版 | 企业版 |
|--|--------|--------|
| 需要行业模板 | ✅ | ❌ |
| 原因 | 预约/定价/结算逻辑因行业而异 | 报销/预算逻辑跨行业通用 |
| 差异解决方式 | 系统预置行业模板 | 用户自建科目 |

**行业模板内容：**

```
行业模板（industry_template）
├── 行业编码/名称（board_game / market / gym / spa）
├── 业务角色映射（桌游老板→boss, 助教→salesman, 顾客→customer）
└── 预置数据
     ├── 服务分类示例（房间/助教/游戏）
     ├── 结算规则示例（按单量周结）
     └── 单位库示例（小时/斤/节/人）
```

行业模板可预置默认页面配置（`page_block_config`），租户创建时自动初始化，老板之后可自行调整。

| 行业 | boss 首页默认区块 | customer 首页默认区块 |
|------|------------------|---------------------|
| 桌游店 | 本周收入+助教提成 | 助教照片墙+活动+预约 |
| 买菜 | 今日团购+配送结算 | 今日菜品+套餐+下单 |
| 健身房 | 课程收入+教练结算 | 教练墙+课表+约课 |

> **新增行业只需配行业模板（含页面默认配置），小程序零改动。**

## 14. 单小程序架构与 client_type 菜单过滤

> 来源：《小微版完整方案》v10.0 第一、六、九章。

### 14.1 端的定义

| 端 | 载体 | appid 作用 | 谁用 | 说明 |
|----|------|-----------|------|------|
| **PC 后台** | 浏览器 Web | 无 | **仅老板+平台管理员+admin** | 重管理：定价、结算、收支、配置、用户/角色 |
| **微信小程序** | 微信内（全平台唯一一个小程序） | **仅做合法性校验，业务零区分** | **老板+业务员+顾客全部** | 轻量操作、随时输入；按角色动态渲染视图 |

**关键规则：**
- ❌ 不区分「业务员一个小程序、顾客一个小程序、老板一个小程序」
- ✅ 全平台 = 一个微信小程序 = 一个 appid，所有角色共用入口，登录后按角色渲染不同视图
- ✅ appid 不进任何业务判断，只用来验明「这是我方小程序」
- ✅ 老板有两个前端壳：PC 后台（日常管理）+ 同一小程序（只看报表/改报价）
- ✅ 只有老板有 PC 后台；业务员、顾客全部落在唯一小程序里

### 14.2 client_type 过滤规则

`sys_menu` 新增 `client_type` 字段（pc / mini / both），标识菜单属于哪个前端壳：

| 前端壳 | client_type 过滤 | 说明 |
|--------|-----------------|------|
| PC 后台 | `pc` + `both` | 返回 PC 全量菜单 |
| 微信小程序 | `mini` + `both` | 返回小程序精简菜单 |

> 因为所有角色共用一个小程序，这里不判断角色、不判断 appid，只按 `client_type` 过滤菜单——老板在小程序里因为菜单被 `client_type=mini` 过滤，天然只剩「报表+定价」。

### 14.3 菜单加载链路

```
登录请求
  ├── 参数：phone（+ tenantId，小程序从场景带入/PC 多租户则选）
  └── 前端壳标识：PC 请求传 client_type=pc；小程序请求传 client_type=mini

→ ① phone → sys_user；校验状态
→ ② tenantId → 校验该用户在此租户的关联（user_tenant_role）
→ ③ role_code → 查角色模板（tenant_type + industry_type + role_code）
→ ④ 查 sys_menu（仅该租户 + client_type 匹配）
→ ⑤ 组装 perms 集合 + 菜单树 → 返回 token/登录态
→ ⑥ PC 前端/小程序前端各自按 perms 渲染
```

**端×角色速览表：**

| 角色 | PC 后台 | 微信小程序（唯一） | 身份识别依据 |
|------|---------|-------------------|-------------|
| admin | ✅ 全部系统管理 | ❌（不提供小程序入口） | role_code |
| 平台管理员 | ✅ 用户/角色/定价/配置 | ❌ | role_code |
| **老板** | ✅ 订单/结算(记账)/收支/报表/推广 | ✅ **报表+改报价** | role_code=boss |
| 业务员 | ❌ | ✅ 排班/收入/打卡 | role_code=salesman |
| 顾客 | ❌ | ✅ 浏览/预约/到店付(不在线支付) | role_code=customer |

## 15. 小程序模块化页面架构（page_block_config）

> 来源：《小微版完整方案》v10.0 第十三、十四章。
> **核心思想：页面 = 壳 + 区块配置。** 所有角色共用同一个页面壳，由后台配置的「区块（Block）清单」决定谁看到什么。加角色不加页面，只加配置；加功能不加分支，只加区块组件。

### 15.1 区块组件库

每个区块是自包含的小组件：自己拉数据、自己渲染、自己处理点击。它不关心「你是谁」，只关心「是否被配置显示+传了什么参数」。

| 区块 key | 名称 | 典型使用角色 | module_type |
|---------|------|------------|-------------|
| `revenue_week` | 本周收入概览 | boss | micro |
| `revenue_received` | 已结算收入 | salesman | micro |
| `revenue_pending` | 待结算收入 | salesman/boss | micro |
| `staff_photo_list` | 员工/助教照片墙 | customer | micro |
| `activity_banner` | 活动推荐 | customer | micro |
| `quick_booking` | 快速预约入口 | customer | micro |
| `my_schedule` | 我的排班 | salesman | micro |
| `checkin_entry` | 打卡入口 | salesman | micro |
| `shop_info` | 店铺信息卡 | all | micro |
| `notice_bar` | 消息提醒 | boss | micro |
| `expense_approve_count` | 待审批报销数 | boss | enterprise |
| `budget_execution_rate` | 预算执行率 | boss | enterprise |
| `my_expense_list` | 我的报销单 | expense_staff | enterprise |
| `quick_new_expense` | 快速发起报销 | expense_staff | enterprise |

> **组件库只增不减：加新功能 = 新增一个区块组件 + 注册进组件库，不改任何页面。**

### 15.2 页面配置模型

核心表 `page_block_config`：

| 字段 | 说明 |
|------|------|
| tenant_id | 租户（可继承系统默认） |
| role_code | boss/salesman/customer |
| page_key | 'home'/'mine'/'booking'/'report' |
| block_key | 区块 key（指向组件库） |
| module_type | micro/enterprise（区分区块来源） |
| sort_order | 排序 |
| show_flag | 是否显示 |
| block_params | JSON：区块自定义参数 |

**渲染流程（小程序端）：**

```
① 进入任意页面（如首页 home）
② 请求 GET /page/config?pageKey=home（tenantId+roleCode 由后端从 token 取）
③ 后端按 roleCode+pageKey 查 page_block_config → 返回区块列表（有序、带参数）
④ 前端循环渲染：<component is="{{item.blockKey}}" data="{{item.params}}" />
⑤ 每个区块组件各自调自己的接口拿数据
```

老板/平台管理员可在 PC 后台「页面装修」中勾选区块、拖拽排序、设置参数，完全不用改代码。

### 15.3 配置与权限的双层过滤

```
配置层（page_block_config）  →  老板自己拖的区块清单
        ↓
权限层（perms / sys_role_menu） →  该角色实际有权看到的菜单/功能
        ↓
最终渲染 = 配置 ∩ 权限
```

- 老板在装修后台勾掉的区块 → 配置层就不返回 → 前端不渲染
- 老板勾上了但角色无权限的区块 → 权限层过滤掉 → 前端不渲染
- 只有既被配置、又有权限的区块才最终显示

> **配置是「个性化排版」，权限是「安全底线」，配置永远不能突破权限。**

## 16. V1 零支付合规设计

> 来源：《小微版完整方案》v10.0 第十二章。
> **结论先行：小微版 V1 只做「预约+线下收款+系统记账+结算单」，系统不碰任何资金。** 这是当前阶段合规成本最低、上线最快的方案。

### 16.1 合规红线：二清

| 场景 | 是否合规 | 原因 |
|------|---------|------|
| 顾客付款→平台商户号→老板→助教 | ❌ **二清（二次清算）** | 用户付款先到平台商户号，再由平台分发给二级商户/个人，属无证经营支付业务 |
| 系统代老板调转账接口给助教 | ❌ 二清 | 平台成为资金清算节点 |
| 系统代发工资（哪怕老板点按钮触发） | ❌ 需支付资质 | 「代付」属支付结算行为，需牌照或与持牌机构合作 |

> **核心红线：只要「付款/代付动作」由系统调用支付接口完成，且资金经过平台控制账户→即涉嫌二清。**

### 16.2 V1 方案：资金不经平台

```
顾客 ──线下付──→ 老板（老板自己的收款码/现金/POS，钱直进老板账户）
老板  ──线下付──→ 助教（微信/银行/现金，老板自己转）
                        │
                        ↓（只记账，不碰钱）
              ┌──────────────────┐
              │  本 SaaS 系统      │
              │  预约/收款标记      │
              │  结算单/流水        │
              │  报表               │
              └──────────────────┘
```

**系统定位：经营管理+流水记账工具，不是支付机构** → 完全避开二清。

### 16.3 各端收款/结算菜单语义

| 角色/端 | 菜单 | 是否涉及支付 | 说明 |
|---------|------|------------|------|
| 顾客/小程序 | 预约提交、查看收款方式 | ❌ | 只生成「待到店付」订单，不调支付接口 |
| 老板/PC | 标记订单「已收款」 | ❌ | 老板线下已收后打勾，仅记流水 |
| 老板/PC | 生成结算单 | ❌ | 系统算出助教应发金额 |
| 老板/PC | **标记已线下发放** | ❌ | 老板线下转账后点状态，不调转账接口 |
| 老板/小程序 | 报表/改价 | ❌ | 纯查看与配置 |
| 助教/小程序 | 我的收入/打卡 | ❌ | 只看「待发/已发」金额 |

> **全系统零支付接口调用。** 「确认发放/打款」的语义全部改为「标记状态」。
> **V2+ 若需在线支付**：采用微信支付服务商模式，每个租户自己进件为子商户（`sub_mchid`），顾客付款直进老板子商户号；助教提成走微信官方分账接口（持牌机构执行分账，平台不经手）。V1 不做，仅预留扩展点。

## 17. 服务与定价体系（小微版）

> 来源：《小微版完整方案》v10.0 第七章。
> 通用模型：`服务分类 → 服务项目(价格/单位/计价方式)` 支持所有行业。这套体系不区分 appid/渠道，谁有权限（按角色）谁就能通过接口操作。

**数据模型：**

| 表 | 关键字段 | 说明 |
|----|---------|------|
| `service_category` | tenant_id, name, industry_type | 服务分类（房间/助教/蔬菜/肉菜/私教课...） |
| `service_item` | tenant_id, category_id, name, price, unit, pricing_type | 服务项目（名称+价格+单位+计价方式） |
| `price_change_log` | tenant_id, item_id, old_price, new_price, operator, time | 改价历史日志（老板小程序改价也记录） |

**行业示例：**

| 行业 | 服务分类示例 | 服务项目示例 |
|------|------------|------------|
| 桌游店 | 房间/助教/附加 | 小房间 50元/小时（按时长）；初级助教 30元/小时 |
| 社区买菜 | 蔬菜/肉菜/套餐 | 白菜 2.5元/斤（按重量）；家庭套餐A 68元/份 |
| 健身房 | 私教课/团课 | 减脂私教 300元/节（按次）；瑜伽课 50元/节 |
| 汤泉 | 门票/按摩 | 成人票 88元/人（按人）；中式按摩 128元/60分钟 |

> 平台管理员通过 PC 后台「服务与定价」自由配置；老板在小程序上只做「临时改报价」（只暴露价格字段，改价确认记录到价格调整日志）。

## 18. 预约/结算业务闭环（小微版 V1）

> 来源：《小微版完整方案》v10.0 第十一章。

```
顾客小程序预约房间+助教 → 生成「待到店付」订单（系统不收钱）
        ↓
到店后：老板用自己收款码/现金/POS 线下收款（资金直进老板账户，不经平台）
        ↓
老板 PC 标记订单「已收款」 → 自动记「房间收入/助教服务费」流水
        ↓
助教小程序打卡确认完成
        ↓
老板 PC 发起周结 → 系统自动汇总单量 → 算出助教应发金额 → 生成结算单
        ↓
老板线下转账给助教（微信/银行/现金）→ 回来点「标记已线下发放」
        ↓
系统改结算单状态为「已发」+ 记录一笔「助教工资」支出流水（纯记账）
        ↓
老板小程序看周报：营收 - 助教工资 - 房租水电 = 净利
        ↓
（临时要调价）老板小程序改助教时薪 → 即时生效 + 记录日志
```

**资金流 vs 信息流（关键）：**
- **资金流**：顾客→老板（线下）→助教（线下），**平台全程不经手**
- **信息流**：预约/收款标记/结算单/流水/周报，全部在系统里跑

**老板全程操作：**
- PC：标记收款（每单）+ 确认结算/标记已发（1次/周）
- 小程序：看报表（每天）+ 改报价（偶尔）

> **系统定位：经营管理+记账工具，不是支付机构。** 这是 V1 合规的基石。

## 19. 定时任务与多租户（XXL-JOB）

> 来源：《小微版完整方案》v10.0 第十五章。
> 系统采用 XXL-JOB 作为分布式调度器。原生 XXL-JOB 没有「租户」概念，任务跑在调度线程池里，没有 HTTP 请求、没有登录用户，MyBatis-Plus 的 `TenantLineInnerInterceptor` 取不到 `tenant_id`。

### 19.1 任务分类

| 任务类型 | 典型例子 | 是否需要租户上下文 |
|---------|---------|------------------|
| **平台级** | 清理 `sys_job_log`/租户到期检查/刷新字典缓存 | 否 → `TenantHelper.clear()` 或标 `@TenantIgnore` |
| **租户级通用** | 小微版每日营收快照/预约过期自动关单/企业版月结 | **是 → 遍历活跃租户，逐个 set** |
| **版本限定** | 企业版高级版每月1号生成预算执行报表 | **是 → 遍历时按 `version_type` 过滤** |

> 小微版 V1 典型租户级任务：每天 23:59 生成当日营收快照写 `micro_daily_revenue`、预约过期自动关单、顾客7天未到店打标签——这些都必须按租户执行。

### 19.2 @TenantJob 注解 + 切面机制

> **关键原则：不按租户建 Job。XXL-JOB 调度中心只配「一个 Handler」，Handler 内部自己遍历租户、逐个切上下文。** 1000个租户 = 1条 XXL-JOB 任务，而不是1000条。

```java
@Target({ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
public @interface TenantJob {
    boolean parallel() default false;   // 是否并行执行，默认串行
    String[] versions() default {};     // 限定版本：micro/enterprise_adv/enterprise_pro/空=不限
}
```

切面执行流程：查所有活跃租户 → 按 versions 过滤 → 逐个 `TenantHelper.setTenantId` → `point.proceed()` → finally `TenantHelper.clear()`；单租户异常 catch 隔离，不抛回 XXL-JOB。

业务 Handler 写法（几乎零改造）：

```java
@XxlJob("microDailyRevenueJob")
@TenantJob(versions = {"micro"})   // 只跑小微版租户
public void buildDailyRevenue() {
    revenueService.buildTodaySnapshot();  // TenantHelper.getTenantId() 已有值，MP 自动拼 tenant_id
    XxlJobHelper.handleSuccess("ok");
}
```

### 19.3 平台级任务处理

```java
@XxlJob("cleanJobLogJob")
public void cleanJobLog() {
    TenantHelper.clear();   // 确保查 sys_job_log 不分租户
    jobLogService.cleanHistory(30);
    XxlJobHelper.handleSuccess();
}
```

也可在 Mapper 方法上标 `@TenantIgnore`（RuoYi-Vue-Plus 自带），显式跳过租户拼接。

**异步/多线程注意**：`TenantHelper` 基于 ThreadLocal，子线程拿不到父线程 tenantId；必须用 `TenantHelper.execute(tenantId, () -> {...})` 显式传入，否则子线程查库 `tenant_id` 为 null。

**自检速查：**

| 检查项 | 要点 |
|-------|------|
| 一个 Handler 服务全量租户 | XXL-JOB 不按租户建多条任务 |
| `@TenantJob` 切面遍历 | set→proceed→clear，finally 必清 |
| 单租户异常隔离 | catch 后不抛回 XXL-JOB |
| 平台级任务清上下文 | `TenantHelper.clear()` / `@TenantIgnore` |
| 版本过滤 | `@TenantJob(versions=...)` |
| 异步线程传上下文 | 禁依赖 ThreadLocal 继承 |
| 调度配置与 `sys_job` 无关 | Cron/报警统一在 XXL-ADMIN |

### M21 核心设计哲学与技术实现要点

> **设计哲学**：「零新增业务表、复用既有 `booking_order` + `service_item`，扩展信息 JSON 化存 `remark`」，配合功能开关（`FEAT_SELF_BOOKING`）和权限键（`micro:selfBooking:*` / `micro:resourceStatus:*` / `micro:resourcePrice:*`）做小微版隔离，资源状态用日志表（`resource_status_log`）驱动流转与审计。仅新增 `resource_status_log`（状态审计日志）与 `staff_pricing`（助教小时单价）两张表，预约主数据、房间资源均复用既有表结构。

**① remark JSON 扩展信息存储与解析**

自助预约不新增预约明细表，主资源写入 `booking_order` 标准列（`service_item_id` / `staff_user_id` / `service_name` / `booking_time` / `amount`），可选关联资源与时段等扩展信息序列化为 JSON 存入 `booking_order.remark`：

```json
{
  "bookingType": "staff",
  "mainResourceId": 5,
  "optionalProjectIds": [],
  "optionalStaffIds": [],
  "optionalRoomIds": [4],
  "bookingTimeSlot": "09:00-11:00",
  "customerName": "张三",
  "remark": "顾客备注"
}
```

- **写入**：`submitSelfBooking()` 用 `LinkedHashMap` 保持字段顺序，`objectMapper.writeValueAsString()` 序列化；序列化失败时降级为原始文本 remark（fail-soft，不阻断下单）。
- **解析**：`parseRemark()` 用 `objectMapper.readValue(..., TypeReference<Map<String,Object>>)` 反序列化，空串或异常均返回 `Collections.emptyMap()`（容错）；`toLong()` / `toLongList()` 做类型安全转换（兼容 Number 与 String）。
- **消费场景**：① `releaseResources()` 取消预约时解析出全部关联资源逐个释放；② `getBookedResourceIds()` 查空闲房间时解析当天订单的 `mainResourceId` + `optionalRoomIds` 做已占用排除。

**② 订单号生成规则**

`genOrderNo()`：`"SB" + yyyyMMddHHmmss + 4 位随机数字`（如 `SB202610101530120042`）。前缀 `SB`（Self-Booking）刻意区别于既有预约的 `BK` 前缀，便于在 `booking_order` 混合表中按订单号前缀区分「自助预约」与「Boss/顾客常规预约」来源。

**③ in_use（使用中）状态的落地现状与补全建议**

资源三态设计为 `idle`（空闲）→ `reserved`（预约中）→ `in_use`（使用中）→ `idle`。当前 V1 实现状态：

| 流转 | 触发点 | V1 是否落地 |
|------|--------|:-----------:|
| `idle → reserved` | `submitSelfBooking()` 提交预约 | ✅ 已实现（主资源 + 可选助教 + 可选房间） |
| `reserved → idle` | `releaseResources()` 取消预约 / `manualReleaseResource()` Boss 手动释放 | ✅ 已实现 |
| `reserved → in_use` | `resourceInUseFlowJob` 定时任务（每 10 分钟，T21.8） | ✅ 已实现：按预约时间窗（bookingTime + remark.bookingTimeSlot，缺失兜底 2 小时）+ 订单状态推进 |
| `in_use → idle` | `resourceInUseFlowJob`（结束/超窗/完成/爽约）+ `releaseResources()` 取消预约 | ✅ 已实现（定时任务兑底 + 取消即时释放） |

> **实现说明（T21.8 已落地）**：① 房间状态存 `service_item.resource_status` 列，助教状态无持久化列、由最新一条 `resource_status_log` 推导（`getCurrentResourceStatus()` 已针对 staff 增强，保障定时任务幂等）；② 新增 `resourceInUseFlowJob`（`MicroBizJob`，每 10 分钟，`@TenantJob(versions={"micro"})`）调用 `advanceResourceStatusByTime()`，扫描当天预约按时间窗推进 `reserved → in_use`、`in_use → idle` 并写 `resource_status_log`（`operatorId=null`，`reason=系统自动流转`）；③ 时段缺失时兜底服务时长 `DEFAULT_IN_USE_HOURS=2` 小时。
>
> **后续增强（可选）**：与 M22 员工排班联动——排班的上/下班时点可作为助教 `in_use` 状态更精确的触发信号（替代固定 2 小时兜底）；Boss PC 「开始服务/核销」手动触发可另立任务。

### 6.2 菜单命名规范（铁律）

1. **系统抽象，行业具象**：菜单层统一使用系统抽象词（员工、房间、活动、任务、固定支出）；行业差异仅体现在角色名、项目名、字段文案；**禁止**为特定行业新增菜单或修改菜单文案。
2. **财务模块命名**：小微版仅存在「固定支出」；房租/水电/工资等均为**标签**而非财务科目；**禁止**出现“固定资产”“折旧”“摊销”“预算”等企业版术语。
3. **周期配置归属**：时间单位由 Admin 全局定义；具体周期规则由租户管理员定义并保存。
4. **合规模块归属**：语音合规总开关与底库由 Admin 全局控制；具体录音策略由租户管理员配置；合规记录由老板查看。
5. **推广模块归属**：我的推广码（老板/员工/顾客均可见）；拉新奖励配置（**仅老板可配置，唯一入口**）；平台功能总开关（由 Admin 控制）。

### 6.3 角色与首页定位

| 角色 | 默认首页 | 核心职责 |
|------|---------|----------|
| **Admin** | 🏠 平台驾驶舱 | 平台治理、License、字典、大盘监控 |
| **租户管理员** | 🏠 企业概览（工作台） | **配置自检**（原子数据/周期/合规），**不处理**业务待办与异常 |
| **老板** | 🏠 经营驾驶舱 | **经营决策+业务异常处理+拉新奖励配置**（唯一配置权） |
| **员工** | 🏠 工作台 | 任务执行+我的推广码 |
| **顾客** | 🏠 发现页 | 消费预约+我的推广码（邀请有礼） |

**职责边界铁律：**
1. **租户管理员**：只关心“配置对不对”，不处理业务待办与预约异常，不配置推广奖励。
2. **老板**：只关心“生意好不好”，全权处理业务待办与异常，**唯一**拥有拉新奖励配置权。
3. **员工/顾客**：小程序端均可查看“我的推广码”，仅查看本人推广记录与奖励，不可配置。
4. **Admin**：只管平台级，不碰租户具体业务数据。

## 八、小微版专属开发规范（合并自母文档第四章 12~19 条）

> 以下规范仅适用于小微版开发，完整规范（1~19 条）见母文档第四章。

12. **身份与角色规范**：① 手机号为唯一身份锚点；② appid 不参与身份与权限判定；③ 标准角色集全版本共用，**禁止新增角色 code**；④ 平台管理员只做角色映射，**禁止**分配 `system:menu:*` 或 `system:role:edit`；⑤ `sys_menu.client_type` 为菜单端过滤唯一依据。
13. **V1 零支付规范**：① 全系统禁止集成支付 SDK；② 「确认发放」改为「标记已线下发放」；③ 顾客端禁止在线支付入口；④ 资金流全程不在平台过手；⑤ V2+ 必须采用微信支付服务商模式（**禁止平台统一收款码**）。
14. **模块化页面与 XXL-JOB 规范**：① 小程序页面=单一页面壳+区块配置，加角色不加页面只加配置；② 区块组件只增不改；③ XXL-JOB 租户级任务必须 `@TenantJob`，一个 Handler 服务全量租户；④ 平台级任务必须 `TenantHelper.clear()` 或 `@TenantIgnore`。
15. **分档与角色硬隔离规范**：① `tenant.version_type` 分档差异只体现在 `role_template` 菜单范围；② lite→pro 升级=UPDATE+刷新缓存，**禁止 DDL 与数据搬迁**；③ `sys_role.tenant_type_scope` 为角色产品线归属唯一标记，可选角色列表**必须**按 `tenant_type` 数据源层过滤。
16. **防爽约与黑名单规范**：① 仅 `micro_pro` 生效；② 主动取消不计入 `no_show_count`；③ 满 3 次自动拉黑；④ 唯一出口为老板手动移出；⑤ 移出后 `no_show_count` 保留不清零；⑥ 按 `tenant_id` 隔离。
17. **任务状态标注规范**：① 四态（✅/🟡/🔄/🆕）；② 按 SQL/BE/PC/MP 四赛道取证；③ 桩实现不计为赛道完成；④ 需线上环境验收的动作不计 ✅；⑤ 第二章为唯一权威状态源。
18. **推广分销与激励规范**：① 仅小微版启用，由 `FEAT_PROMOTION_DISTRIBUTION` 整体开/关；② 推广码永久有效、一人一码；③ 归因只认最后一次扫码；④ 奖励只给拉新且仅一次；⑤ 员工现金延续 V1 零支付；⑥ 首单判定与推广归属两条线独立。
19. **通用评价与点赞规范**：① 评价针对用户非角色；② `scene` 区分场景，一套表管全部；③ 仅 micro_pro 启用；④ 禁止自己评价自己；⑤ 同一订单不可重复评价；⑥ 图片走 `imgSecCheck`；⑦ 综合评分可聚合所有场景；⑧ 老板可屏蔽但后台保留原始数据。

## 九、小微版相关防串验收用例（合并自母文档第五章 #25~#35）

> 完整 35 条防串用例见母文档第五章。以下仅列小微版相关用例。

| # | 场景 | 操作 | 预期 |
|---|------|------|------|
| 25 | appid 业务判断串 | 检查全部业务代码是否存在 appid 参与业务判断 | 业务代码中无 appid/渠道判断；appid 仅在网关签名校验中 |
| 26 | 角色映射越权串 | 平台管理员尝试新建角色 code、访问 `system:menu:*` | 无新建角色 code 入口；无菜单管理权限；返回 403 |
| 27 | client_type 菜单过滤串 | 老板用小程序登录，检查是否含 PC 专属菜单 | 只返回 `client_type=mini/both` 菜单；PC 专属菜单不出现 |
| 28 | V1 零支付串 | 全代码搜索支付 SDK 调用；检查顾客端在线支付入口 | 全代码无支付 SDK；顾客端无在线支付按钮；结算仅改状态+记流水 |
| 29 | 模块化页面权限串 | 老板勾选无权限区块，检查小程序是否渲染 | 配置 ∩ 权限双层过滤；无权限区块不返回不渲染 |
| 30 | XXL-JOB 租户串 | 检查是否按租户建多条任务；检查 `@TenantJob(versions={"micro"})` 是否在企业版执行 | 每个 Handler 仅一条任务；企业版无执行记录；单租户异常被 catch 隔离 |
| 31 | 角色可见性硬隔离串 | 小微租户可选列表是否含企业角色；尝试跨线映射 | 小微只返回 boss/salesman/customer；跨线写入被拒（数据源层过滤） |
| 32 | 小微版分档菜单串 | `micro_lite` 登录检查是否出现预约/结算菜单 | lite 档仅推广+活动浏览页；预约/结算/报表不可见且接口拦截 |
| 33 | 防爽约黑名单串 | 累计爽约 3 次后检查黑名单；老板移出后复测 | 满 3 次自动拉黑；仅老板可移出；跨租户隔离；仅 micro_pro 生效 |
| 34 | 推广分销版本串 | 非小微版租户尝试推广功能 | 四项均返回「当前版本不支持」；员工现金无支付接口 |
| 35 | 评价场景版本串 | 非小微版/小微免费版尝试评价功能 | 返回「当前版本不支持」（`FEAT_RATING` 拦截）；仅 micro_pro 可用 |

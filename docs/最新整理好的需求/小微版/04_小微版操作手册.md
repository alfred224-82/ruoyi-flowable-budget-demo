# 资金管控系统 · 小微版操作手册

**版本**：v1.9（对齐 v1.33 · 新增 §5.14 行业「是否可语音」开关 · §5.15 活动设置增强）
**日期**：2026-09-21
**适用对象**：小微版租户（老板 boss、业务员 salesman、顾客 customer）、平台管理员（platform_admin）、平台运营（admin）
**文档定位**：指导小微版门店从零配置系统、跑通「预约 → 到店付 → 人员结算 → 营收快照」业务闭环、使用单小程序三视图与模块化页面、管理分档与防爽约机制、运营推广分销与拉新激励、配置租户管理员菜单与主题、管理活动图片与背景主题、维护首页盈亏指标与每月固定支出

> **v1.14 小微版说明**：依据《小微版完整方案》v10.5（增量 v10.1~v10.5）、《多业态SaaS平台需求规格说明书》v1.0 第 11~19 章与《资金管控系统开发任务文档》v1.14 M15 里程碑（T15.1~T15.32），小微版是面向**个体门店/小微商户**（桌游店、买菜生鲜、健身房、汤泉美容）的轻量经营 SaaS。核心特征：**手机号即身份、一店一租户、老板 + 业务员 + 顾客三视图、PC 管理端 + 微信小程序双端**。★**V1 零在线支付合规**：全系统仅「到店付」，无在线收款、无支付分账、无顾客在线付款菜单（`micro:customer:pay` 不存在），结算只记账不打款。小微版**不含**企业版资金管控重能力（预算编制/科目三层/报销管控/规则引擎/发票验真/项目容器/多组织等），相关脚本不在本目录部署。
>
> **v1.14 新增能力**：① 小微版分档（micro_lite 免费·仅推广 / micro_pro 收费·全经营，升级=菜单扩围零迁移）；② 角色可见性硬隔离（`sys_role.tenant_type_scope`）；③ 资金平台管理菜单收纳（menu_id=1300~1359，与若依「系统管理」并列）+ 版本档位管理（`system:edition:*`）；④ 新建租户级联（产品线→档位→行业→角色预览）；⑤ 三层控制模型（角色模板天花板 ∩ 页面装修排版）；⑥ lite 档活动浏览页（`micro:activity:browse`）；⑦ 防爽约/黑名单机制（`customer_credit`/`no_show_record`/`noShowCheckJob`，仅 micro_pro）。
>
> **v1.16 新增能力（M16 推广分销与激励）**：依据《推广分销与激励方案》v1.0 与任务文档 v1.16 M16 里程碑（T16.1~T16.12）。★**仅小微版启用**，由功能开关 `FEAT_PROMOTION_DISTRIBUTION`（feature_flag 第 34 项，组 E）统一控制，基础版/高级版/专业版不部署、不建表、不开放入口（三列开关均 = 0，接口层 `@RequireFeature` 拦截）。能力含：① 推广码（门店码/个人码，一人一码·永久有效）；② 扫码归因（谁最后扫码业绩归谁·交接点锁定不回溯）；③ 拉新奖励（仅一次·员工现金走线下发放/顾客站内优惠券·V1 零支付）；④ 首单识别（按手机号+活动独立判断·与归属解耦）；⑤ 老板 PC 推广分销管理菜单 7180~7188 + 员工小程序 7340~7342 + 顾客小程序 7440~7442。
>
> **v1.28~v1.30 新增能力**：① 租户管理员菜单（platform_admin 三件套：版本升级/角色映射/人员管理，与 admin 超管菜单完全隔离）；② 推广分销管理按渠道拆分为业务员推广 + 顾客推广两个子菜单，奖励记录独立；③ boss 活动图片上传（logo/poster）+ 背景主题选择（4 套预设主题）；④ platform_admin 小程序全局主题选择（默认 4 套）+ 首页欢迎语「【租户名称】管理系统 欢迎您！【用户名】」；⑤ boss 首页盈亏三指标（本月收入/支出/盈利）+ 每月固定支出管理（`monthly_fixed_cost`）。
>
> **v1.31 新增能力（T15.38 原子资源管理）**：platform_admin「原子资源管理」目录（menu_id 7510）补齐 V3.7 §4.2 四原子中缺失的「项目管理」与「房间/空间管理」，与既有「角色管理（角色映射）」「员工库（人员管理）」归入同一目录；房间/空间建模为 `service_category.category_type='space'` 分类下的 `service_item`（元/小时按时长计价，零新表）；项目/房间数据与角色映射自愈同模式，租户首次进入或建租户时从 admin 行业模板 `preset_config.projects/rooms` 自动初始化落库（幂等仅空表补录，不覆盖存量）。详见 §5.13。

### 0.3 角色与身份模型（三视图）

- **标准角色集**：全版本共用**同一张 `sys_role` 表**（不存在「小微版角色表」与「企业版角色表」两张表）。小微版使用其中三个标准角色：
  - `boss`（老板，role_id=9201）：PC 全量管理 + 小程序看报表/改价/提醒
  - `salesman`（业务员，role_id=9206，M15_07 新增）：仅小程序排班/收入/打卡；可被租户改名为「助教/配送员/教练/技师」
  - `customer`（顾客，role_id=9207，M15_07 新增）：仅小程序浏览/预约/到店付；可免密轻登
- **★角色可见性硬隔离（v1.14 新增）**：`sys_role.tenant_type_scope` 标记角色产品线归属（`micro`/`enterprise`/`both`）：
  - `boss`、`platform_admin` = `both`（两条产品线共用）
  - `salesman`、`customer` = `micro`（小微版专属，企业版租户不可见）
  - `manager`、`employee`、`finance` = `enterprise`（企业版专属，小微版租户不可见）
  - 可选角色列表接口在 SQL 数据源层按 `tenant_type` 过滤，跨产品线角色在查询阶段即被排除，不依赖前端隐藏
- **平台管理员**（`platform_admin`，role_id=9205）：租户组织管理员，**只能做角色映射（挑选/改名/启停/分配用户），不能新建角色 code、不能改角色权限**（权限永远由 admin 在 `role_template` 预置）。
- **身份主键**：手机号为主键——一个手机号 = 一个 `sys_user`，跨端跨租户唯一；`user_tenant_role` 支持「一人多租户、一租户多角色」。
- **★分档与角色关系（v1.14 新增）**：micro_lite / micro_pro 共用同一套标准角色（boss/salesman/customer），**不新增角色 code**。分档差异仅体现在 `role_template.version_type` 绑定的菜单范围：lite 档 boss 仅推广/店铺/设置，pro 档 boss 含全经营。升级 lite→pro = `UPDATE tenant.version_type` + 刷新菜单缓存，角色 code / 用户 / 业务数据**零迁移**。

### 1.2 admin 平台侧预置（行业模板 + 角色模板）

> 行业模板与角色模板为**系统级共享数据**，由 admin 在 M15_02/M15_07/M15_10 脚本预置，门店开通时无需重复配置。

**操作路径**：资金平台管理菜单（1300）→ 行业模板管理（7000）/ 角色模板管理（7005）

**预置内容**：
1. **行业模板**（`industry_template`）：内置 board_game(桌游店)/market(买菜生鲜)/gym(健身房)/spa(汤泉美容) 四行业，每行业含 `preset_config`（服务分类示例/结算规则/单位库）
2. **行业角色映射**（`industry_role_map`）：每行业 3 条业务角色名→标准角色 code（如桌游店：桌游老板→boss、助教→salesman、顾客→customer）
3. **角色模板配方**（`role_template`）：
   - version_type='micro'（原始配方，M15_07）：boss/salesman/customer 各一条
   - ★version_type='micro_lite'（免费档，M15_10）：boss 仅推广发布/店铺管理/系统设置；salesman/customer 仅活动浏览页
   - ★version_type='micro_pro'（收费档，M15_10）：= lite 集合 ∪ 经营集合（预约/结算/收支/报表/定价/人员管理/顾客管理）

**验收检查**：
```sql
-- 四行业模板就绪
SELECT industry_code, industry_name, status FROM industry_template ORDER BY sort_order;  -- 预期 4 行
-- 每行业 3 条角色映射
SELECT industry_code, COUNT(*) FROM industry_role_map GROUP BY industry_code;            -- 预期各 3
-- ★小微版分档配方完整（micro + micro_lite + micro_pro）
SELECT version_type, role_code, JSON_LENGTH(menu_keys) menus, JSON_LENGTH(block_keys) blocks
  FROM role_template WHERE version_type IN ('micro','micro_lite','micro_pro');
-- 预期：9 行（micro 3 + micro_lite 3 + micro_pro 3）

-- ★lite 档 boss 无预约/结算/报表 perms
SELECT JSON_CONTAINS(menu_keys, '"micro:booking:list"') AS has_booking,
       JSON_CONTAINS(menu_keys, '"micro:settle:list"') AS has_settle,
       JSON_CONTAINS(menu_keys, '"micro:report:weekly"') AS has_report
  FROM role_template WHERE version_type='micro_lite' AND role_code='boss';
-- 预期：全部 0

-- ★pro 档为 lite 超集
SELECT JSON_CONTAINS(menu_keys, '"micro:booking:list"') AS has_booking,
       JSON_CONTAINS(menu_keys, '"micro:customer:unblacklist"') AS has_unblacklist
```

## 二、核心业务流程测试（预约 → 到店付 → 结算闭环）

> **业务闭环**：顾客预约（待到店付）→ 到店服务 → 老板标记已收款（写 `cash_flow` income）→ 完成服务 → 周期结算（待发放）→ 老板线下转账后标记已线下发放（写 `cash_flow` expense）→ 每日营收快照。

### 2.1 顾客预约流程（V1 零支付）★小微版边界

**流程**：顾客小程序选服务 → 选时间 → 提交预约 → 生成「待到店付」订单（★不触发任何在线支付）

**操作角色**：顾客（张顾客小程序登录，可免密轻登）
**操作路径**：小程序·顾客 → 预约服务（7410）→ 选择服务项目（7411）→ 选择时间（7412）→ 提交预约（7413）

**操作步骤**：
1. 浏览店铺（7401）查看服务项目与价格
2. 选择服务项目（如「大房间 80 元/小时」）
3. 选择到店时间、数量/时长
4. 点击「提交预约」→ 生成订单，`pay_status=PENDING_PAY`（待到店付）、`order_status=PENDING_SERVICE`（待服务）

**验收检查**：
```sql
SELECT order_no, customer_phone, service_name, amount, pay_status, order_status
  FROM booking_order WHERE tenant_id = <租户ID> ORDER BY create_time DESC LIMIT 1;
-- 预期：pay_status='PENDING_PAY'（★非「已支付」），order_status='PENDING_SERVICE'

-- ★V1 零支付合规：全库无在线支付 perms 菜单
SELECT COUNT(*) FROM sys_menu WHERE perms = 'micro:customer:pay';   -- 预期 0
```

> **关键边界（T15.12/T15.23）**：顾客端**只有** `micro:customer:payInfo`（查看收款方式，展示「到店付/老板收款码」提示文案），**没有** `micro:customer:pay`（在线支付）。提交预约**绝不调用**任何支付/下单支付接口。

### 2.2 老板确认收款流程（线下收款仅标记）

**流程**：顾客到店消费 → 老板 PC/小程序「完成服务」+「标记已收款」→ 写 `cash_flow` 收入流水

**操作角色**：老板（王老板 PC 登录）
**操作路径**：小微运营 → 预约/订单管理 → 预约列表（7111）→ 完成服务（7115）

**操作步骤**：
1. 找到目标预约订单（状态筛选「待服务」）
2. 顾客到店付现/扫老板收款码后，点击「完成服务」→ `order_status=COMPLETED`
3. 标记已收款 → `pay_status=RECEIVED`、`pay_time=NOW()`，同步写一条 `cash_flow`（flow_type=income，related_type=booking）

**验收检查**：
```sql
SELECT order_no, pay_status, order_status, pay_time, complete_time FROM booking_order WHERE id = <订单ID>;
-- 预期：pay_status='RECEIVED'，order_status='COMPLETED'

SELECT flow_type, category, amount, related_order_id FROM cash_flow
 WHERE tenant_id = <租户ID> AND related_type = 'booking' ORDER BY create_time DESC LIMIT 1;
-- 预期：flow_type='income'，amount=订单金额（★纯记账口径，非支付流水）
```

### 2.3 业务员打卡 / 确认完成服务

**操作角色**：业务员（李助教小程序登录）
**操作路径**：小程序·业务员 → 我的排班（7301）/ 打卡（7320）→ 确认完成服务（7321）

**验收检查**：
- 业务员仅见「我的排班/我的收入/打卡」三类菜单（`client_type=mini`），看不到任何管理类菜单
- 我的收入（7310）按本周（7311）/本月（7312）/每单明细（7313）展示，数据源于本人 `staff_user_id` 的已完成订单

### 2.4 人员结算流程（只记账不打款）★小微版边界

**流程**：老板发起结算 → 选员工 + 周期 → 自动汇总单量算应发金额 → 生成「待发放」结算单 → 线下转账后「标记已线下发放」

**操作角色**：老板（王老板 PC 登录）
**操作路径**：小微运营 → 人员结算 → 发起结算（7121）→ 选择员工+周期（7122）→ 生成结算单（7123）→ 标记已线下发放（7124）

**操作步骤**：
1. 选择被结算员工（李助教）+ 结算周期（如本周）
2. 系统自动汇总周期内完成单量（`total_orders`）→ 按结算规则算应发金额（`total_amount`）
3. 生成结算单，`pay_status=PENDING`（待发放）
4. ★老板**线下转账**给员工后，回来点击「标记已线下发放」→ `pay_status=PAID_OFFLINE`、`marked_by`/`marked_time` 记录，同步写 `cash_flow`（flow_type=expense，category=工资结算）

**验收检查**：
```sql
SELECT settle_no, staff_name, period_start, period_end, total_orders, total_amount, pay_status
  FROM staff_settlement WHERE tenant_id = <租户ID> ORDER BY create_time DESC LIMIT 1;
-- 预期：生成时 pay_status='PENDING'；标记后 pay_status='PAID_OFFLINE'（★仅标记，不调支付接口）

SELECT flow_type, category, amount FROM cash_flow
 WHERE tenant_id = <租户ID> AND related_type = 'settlement' ORDER BY create_time DESC LIMIT 1;
-- 预期：flow_type='expense'，category='工资结算'
```

> **关键边界（T15.13/T15.14）**：「标记已线下发放」**只改状态、只记账**，绝不调用任何支付/转账/代付接口。全系统无支付 SDK。

### 2.5 收支记录（现金流水）

**操作路径**：小微运营 → 收支记录 → 收入流水（7131）/ 支出流水（7133）/ 支出预警设置（7135）

**说明**：
- 收入流水：订单收款自动写入 + 手动补录（7132）
- 支出流水：工资结算自动写入 + 手动补录线下已付（房租/水电/采购，7134）
- 支出预警：设置月度上限提醒（`micro:budgetAlert:edit`），超限触发老板小程序消息提醒

### 2.6 经营概览与报表

**操作路径**：小微运营 → 经营概览（7101）/ 报表中心（7140）

**概览内容**：
- **今日概览**（老板小程序 7202）：实时营收/净利
- **经营周报/月报**（7141/7142）：自动生成
- **利润报表**（7143）：收入 − 支出 = 净利
- **资金水位**（7145）：现金流水趋势
- **收支明细导出**（7144）

**验收检查**：
```sql

SELECT revenue_date, gross_income, total_expense, net_profit, order_count
  FROM micro_daily_revenue WHERE tenant_id = <租户ID> ORDER BY revenue_date DESC LIMIT 7;
-- 预期：uk_tenant_date 保证每日一行，重跑不重复
```

## 四、微信小程序（单小程序 + 三视图 + 引导态）

### 4.1 单小程序架构 + client_type 端过滤

### 5.7 防爽约/黑名单机制（v1.14 新增，T15.31/T15.32，仅 micro_pro）

**核心表**：

| 表名 | 归属 | 用途 |
|------|------|------|
| `customer_credit` | 租户级 | 顾客信誉（累计爽约次数 + 黑名单状态），UNIQUE(tenant_id,user_id)，version 乐观锁 |
| `no_show_record` | 租户级 | 爽约明细（每次一行，可追溯），marked_by=system/boss |
| `booking_order.expire_time` | 租户级 | 预约过期时间（booking_time+15min），noShowCheckJob 判定基准 |

**防爽约闭环流程**：
1. 顾客预约（`order_status=PENDING_SERVICE`，`expire_time=booking_time+15min`）
2. 过期未到店未取消 → `noShowCheckJob` 扫描 → `order_status=NO_SHOW` + `customer_credit.no_show_count+1` + `no_show_record`（marked_by=system）
3. `no_show_count>=3` → `is_blacklisted=1`（原子操作，version 乐观锁防并发重复计数）
4. 黑名单顾客提交预约被拒（接口拦截）+ 活动推送名单过滤（`is_blacklisted=0`）
5. 老板 PC「顾客管理」移出（`micro:customer:unblacklist`）→ `is_blacklisted=0` + `no_show_count` 保留不清零 + 恢复预约/推送

**关键约束**：
- ★主动取消（CANCELLED）**不计入** no_show_count
- ★仅 micro_pro 生效，lite 租户跳过（`@TenantJob(versionTypes={"micro_pro"})`）
- ★跨租户隔离：A 店黑名单不影响该用户在 B 店预约
- ★老板手动移出为**唯一解除出口**，系统不自动解除

**顾客管理菜单**（老板 PC，挂「小微运营」7100 下）：

|---------|---------|-------|------|
| 7170 | 顾客管理 | micro:customer:list | 信誉/爽约次数/黑名单状态 + 爽约明细 |
| 7171 | 移出黑名单 | micro:customer:unblacklist | ★唯一解除出口 |
| 7172 | 查看爽约明细 | micro:customer:creditDetail | no_show_record 完整历史 |

## 六、推广分销与激励（M16，v1.16 新增，仅小微版）

> 依据《推广分销与激励方案》v1.0 与《资金管控系统开发任务文档》v1.16 M16 里程碑（T16.1~T16.12）。★**版本边界**：推广分销与激励为**小微版专属**能力，由功能开关 `FEAT_PROMOTION_DISTRIBUTION` 统一控制（feature_flag 第 34 项，组 E）；基础版/高级版/专业版**不部署、不建表、不开放入口**（三列开关均 = 0，接口层 `@RequireFeature` 拦截）。四个校验点（生成推广码 / 扫码归因 / 拉新奖励发放 / 老板后台配置）统一走本开关，禁止在业务代码散落版本判断。

### 6.1 推广分销业务全景

**一句话**：老板/员工/顾客都能生成专属推广码 → 新客扫码进店 → 谁最后扫码业绩归谁 → 新客首次消费触发一次性拉新奖励（员工得现金、顾客得优惠券）→ 新客本人另享首单活动优惠。

| 角色 | 能做什么 | 得什么奖励 |
|------|---------|-----------|
| 老板（boss） | 后台看全员推广数据/归因/业绩、配置奖励内容与首单活动、启停推广码 | —（管理者视角） |
| 业务员（salesman） | 小程序生成/分享个人推广码、看自己的推广数据 | 拉新成功 → **现金奖励**（V1 走「标记已线下发放」，不调支付接口） |
| 顾客（customer） | 小程序生成/分享个人推广码、看拉新数据 | 拉新成功 → **站内优惠券**（非现金，自动到账） |

### 6.2 推广码规则（T16.1 / T16.5，一人一码·永久有效）

- **门店码**：`scene = t=租户ID`（如 `t=001`），指向门店，无个人归属
- **个人推广码**：`scene = t=租户ID&r=角色&u=用户ID`（如 `t=001&r=c&u=23`），带推广人身份
- ★`scene_param ≤ 32 字符`（微信小程序码 scene 长度硬限制）
- ★**一人一码、永久有效**：`promotion_code` 以 `UNIQUE(tenant_id,user_id,code_type)` 保证；**无过期/续期字段**；首次点击生成后一直复用同一个码
- ★**离职/禁用只关 status**：推广码禁用后，新扫码不再归因；禁用前已发生的消费照常计入（不改历史业绩）

### 6.3 扫码归因规则（T16.6，谁最后扫码业绩归谁·不回溯）

- **归因只认最后一次扫码**：`promotion_attribution` 以 `UNIQUE(tenant_id,customer_user_id)` 维护顾客的「当前推广人」，每次扫码更新 `last_scan_time`
- ★**交接点锁定不回溯**：`last_scan_time` 即业绩「交接点」，交接之前已产生的业绩锁定归原推广人，不因后续换码而追溯改写
- ★**从未扫码 = 自然流量**：`promoter_user_id` 为 NULL，不计任何推广人业绩
- ★**禁用推广人不更新归因**：被扫的推广码若 `status=禁用`，本次扫码不更新归因关系
- 跨租户隔离：A 店归因关系不出现在 B 店（tenant_id 过滤）

### 6.4 拉新奖励规则（T16.2 / T16.3 / T16.7，仅一次·V1 零支付）

- ★**触发规则固定不可改**：`promotion_reward_config.trigger_rule` 恒为 `NEW_CUSTOMER`（拉新 = 被推广顾客**首次消费**）；老板后台**唯一可变项是奖励内容**（折扣力度 / 送什么 / 每拉新奖多少），规则本身不可改
- ★**拉新奖励仅一次**：`promotion_reward_record` 以 `UNIQUE(tenant_id,customer_user_id)` 保证同一被拉新顾客只触发一次；后续二次消费/活动消费**不再**给推广人奖励
- **员工现金奖励（V1 零支付延续）**：`issue_status` 走 `PENDING`（待发放）→ 老板「标记已线下发放」→ `PAID_OFFLINE` + 记 `cash_flow`/`staff_settlement`，★**绝不调用任何支付/转账接口**
- **顾客优惠券奖励**：写 `coupon_record`（`source=promotion`）→ 系统自动到账 `ISSUED`，`expire_time = receive_time + coupon.valid_days`
- 奖励发放后回传通知推广人小程序（T16.9，走 M13 IMessageProvider 微信订阅消息，`notified=1`）

### 6.5 首单识别规则（T16.4 / T16.8，按手机号+活动独立判断·与归属解耦）

- ★**首单以手机号为唯一识别维度、按活动独立判断**：`first_order_record` 以 `UNIQUE(tenant_id,activity_id,customer_phone)`；同一手机号同一活动仅一条（=已享受过），不同活动独立计数，防重复薅羊毛
- ★**首单判定（管优惠）与推广归属（管业绩）两条线独立**：换码/换推广人**不影响**「已享受活动」事实；判定只看手机号 + 活动，不看扫了谁的码
- 闭环：顾客扫码进店 → 参加活动 → 查 `first_order_record`：无记录 = 首客，享首单优惠（如 8 折/立减/送礼品）+ 写记录；有记录 = 老客，仅常规优惠

### 6.6 菜单与操作路径（老板 PC + 员工/顾客小程序）

**老板 PC「推广分销管理」（7180~7188，挂小微运营 7100 下，client_type=pc）**：

| menu_id | 菜单名 | perms | 说明 |

## 八、常见问题与排查

### 8.1 顾客无法在线付款

**现象**：顾客小程序预约后找不到「在线支付」按钮。

**说明**：这是 **V1 零支付合规的预期行为**，非缺陷。小微版 V1 仅支持「到店付」，无在线收款/支付分账。顾客端只有 `micro:customer:payInfo`（收款方式提示），无 `micro:customer:pay`。

**解决方案**：顾客到店后付现或扫老板收款码，老板在 PC/小程序「标记已收款」即可。

### 8.2 员工结算无法自动打款

**现象**：人员结算「标记已线下发放」后没有实际转账。

**说明**：这是 V1 零支付边界（T15.13/T15.14）的预期行为——结算**只记账不打款**，`staff_settlement.pay_status` 仅 `PENDING`/`PAID_OFFLINE`。老板须**线下自行转账**后回来点「标记已线下发放」改状态。

### 8.3 平台管理员无法新建角色 / 改权限

**现象**：平台管理员在业务角色管理只能改名/启停，不能新建角色 code、不能改菜单权限。

**说明**：这是角色映射机制的设计边界——权限永远由 admin 在 `role_template` 预置，平台管理员只能做映射（挑选/改名/启停/分配用户）。如需新角色配方，联系平台运营（admin）在角色模板管理（7005）配置。

### 8.4 小程序首页区块与角色不符 / 串视图

**排查步骤**：
1. 检查 `client_type` 端过滤是否生效（PC 不应返回 mini 菜单）
2. 检查 `page_block_config`（配置）∩ `role_template.menu_keys`（权限）双层过滤
3. 检查 `module_type=micro`（企业版角色不应返回小微版区块）
4. 多绑定手机号是否弹出「选择门店」页 + 选对角色视图（`is_primary`）

### 8.5 定时任务在企业版租户误执行

**排查步骤**：
1. 检查 Handler 是否标注 `@TenantJob(versions={"micro"})`
2. 检查 `TenantJobAspect` 切面是否部署（M15_08 前置）
3. 检查调度中心每个 Handler 是否仅一条任务（未按租户建多条）

### 8.6 防爽约/黑名单相关问题（v1.14 新增）

**现象1**：lite 档顾客预约后未被判定爽约。

**说明**：这是预期行为。`noShowCheckJob` 标注 `@TenantJob(versionTypes={"micro_pro"})`，lite 档租户跳过爽约判定。lite 档无预约履约闭环，不触发防爽约机制。

**现象2**：顾客被拉黑后无法预约。

**说明**：这是防爽约机制的预期行为。累计爽约满 3 次自动拉黑（`is_blacklisted=1`），黑名单顾客提交预约被接口拦截。

**解决方案**：老板在 PC「顾客管理」（7170）找到目标顾客 → 点击「移出黑名单」（7171，`micro:customer:unblacklist`）→ `is_blacklisted=0`，`no_show_count` 保留不清零，顾客恢复预约能力。

**现象3**：A 店拉黑的顾客在 B 店仍可预约。

**说明**：这是跨租户隔离的预期行为。`customer_credit` 按 `UNIQUE(tenant_id, user_id)` 隔离，A 店黑名单不影响该用户在 B 店预约。

### 8.7 评价相关问题（v1.24 新增，v1.25 补充）

**现象1**：顾客小程序看不到「评价」入口。

**说明**：评价仅在小微版付费版（`micro_pro`）启用。lite 档顾客看不到评价入口是预期行为。同时仅已完成订单才显示评价入口。

**现象2**：非小微版租户调评价接口报「当前版本不支持」。

**说明**：这是预期行为。评价体系由 `FEAT_RATING`（第 35 项开关，basic/advanced/pro 三列均 = 0）统一控制，非小微版付费版租户调任一评价接口均被拦截。

**现象3**：顾客尝试给自己评价被拦截。

**说明**：这是禁止自评的预期行为。`user_rating` 表设计中 `target_user_id` ≠ `author_user_id`，Java 层校验 + 数据库 UNIQUE 约束双重保障，顾客不能评价自己。

**现象4**：同一顾客同一订单评价两次被拦截。

**说明**：这是防重的预期行为。`user_rating` 以 `UNIQUE(tenant_id,target_user_id,author_user_id,scene,order_id)` 保证同一顾客对同一服务人员同一场景同一订单仅能评价一次。

**现象5**：老板回复评价后想再次修改回复。

**说明**：一条评价仅能回复一次（`reply_content` 非空即已回复），Java 层拦截重复回复。如需修改，须先屏蔽该评价再重新处理。

### 8.8 分档升级后菜单未更新（v1.14 新增）

**现象**：lite→pro 升级后 boss 登录仍看不到经营菜单。

**排查步骤**：
1. 检查 `sys_tenant.version_type` 是否已更新为 `micro_pro`
2. 检查菜单缓存是否已刷新（重新登录或清除 Redis 缓存）
3. 检查 `role_template` 中 `version_type='micro_pro'` 的配方是否存在（M15_10 是否已执行）

### 8.8 推广分销相关问题（v1.16 新增）

**现象1**：非小微版租户（基础版/高级版/专业版）看不到「推广分销管理」菜单，调推广接口报「当前版本不支持此功能」。

**说明**：这是**预期行为**。推广分销为小微版专属，由 `FEAT_PROMOTION_DISTRIBUTION`（feature_flag 第 34 项，basic/advanced/pro 三列均 = 0）统一控制；老板 PC 推广菜单 7180~7188 按开关渲染，非小微版不可见，接口层 `@RequireFeature` 拦截。基础版/高级版/专业版目录不部署 M16_01~M16_03 脚本。

**现象2**：顾客换扫了另一个员工的推广码，之前的业绩会不会被改？

**说明**：不会。归因只认「最后一次扫码」，`last_scan_time` 即业绩交接点；交接之前已产生的业绩锁定归原推广人，**不回溯改写**（T16.6）。之后的新消费才归新推广人。

**现象3**：同一个顾客第二次消费，推广人为什么没再拿到拉新奖励？

**说明**：这是**预期行为**。拉新奖励仅在「被推广顾客首次消费」时触发**一次**（`promotion_reward_record` 以 `UNIQUE(tenant_id,customer_user_id)` 保证）；后续二次消费/活动消费不再给推广人奖励，活动优惠只给顾客本人（`coupon_record.source=activity`）。

**现象4**：员工拉新奖励显示「待发放」但没有实际到账。

**说明**：这是 V1 零支付边界。员工现金奖励 `issue_status=PENDING`（待发放），须老板**线下自行转账**后在后台「标记已线下发放」→ `PAID_OFFLINE` + 记 `cash_flow`，★系统绝不调用任何支付/转账接口。顾客奖励为站内优惠券，系统自动到账（`ISSUED`）。

**现象5**：顾客换了推广码后，之前享受过的首单优惠还能再享一次吗？

**说明**：不能。首单判定只看「手机号 + 活动」（`first_order_record` 以 `UNIQUE(tenant_id,activity_id,customer_phone)`），与扫了谁的码**解耦**；换码/换推广人不影响「已享受活动」事实。同一手机号参加**不同活动**才独立计数（可享该活动首单优惠）。

#### 9.5.6 菜单总表说明

1. **PC 端菜单授权链路**：`admin` 在 `role_template` 预置 `menu_keys`（权限天花板）→ 租户创建时按 `version_type × role_code` 解析 JSON → 关联 `sys_menu.perms` → 写入 `sys_role_menu` → 角色登录即见对应菜单。
2. **小程序端页面过滤**：`pages.json` 统一注册全部页面 → `App.vue` 登录分流 → `MICRO_TAB_CONFIG` 按 `role + version_type` 过滤不可见 Tab → 非授权页面入口隐藏（硬隔离，非打包剔除）。
3. **lite 档 vs pro 档**：lite 档 boss PC 仅推广发布/店铺管理/系统设置；salesman/customer 小程序 lite 档仅开放「查看活动情况 + 我的推广码」2 个页面。pro 档为 lite 超集，升级 = `role_template` 切换，菜单扩围零迁移。
4. **功能开关控制**：推广分销（`FEAT_PROMOTION_DISTRIBUTION`，第 34 项）控制 7180~7188 / 7340~7342 / 7440~7442 菜单可见性；评价与点赞（`FEAT_RATING`，第 35 项）控制 7160~7164 菜单可见性；两开关 basic/advanced/pro 三列均 = 0，仅小微版按 `version_type` 判定启用。
5. **活动浏览页跨角色共用**：`pages/micro/activity/browse.vue` 为 boss/salesman/customer 三角色共用同一页面，lite/pro 均可访问，且支持匿名（无需登录）访问。

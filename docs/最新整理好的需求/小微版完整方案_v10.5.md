# 小微经营平台完整设计方案 v10.5

> 核心定位：**帮个体老板管清楚每一笔生意的钱**
> 技术底座：若依框架（RBAC 权限 + 多租户）+ XXL-JOB 分布式调度
> 版本：v10.5（**v10.5 新增「防爽约 / 黑名单机制」（5.6.1 节 + 第十六章 `customer_credit` / `no_show_record` 表）：顾客预约后爽约累计 3 次自动拉黑，此后活动推送默认不推、禁止新预约，仅老板在「顾客管理」手动移出才恢复**；v10.2 角色可见性硬隔离 + v10.3 新增「资金平台管理菜单」：本平台全部 admin 管理菜单统一收纳到若依的一个一级目录「资金平台管理菜单」下，与若依原生「系统管理」并列；并新增「版本档位管理」菜单，供 admin 在创建/编辑租户时选择版本**；**v10.4 新增「三层控制模型」（第 2.6 节）：admin 通过角色模板定"权限天花板"、平台管理员通过页面装修定"排版"、最终渲染取两者交集，小程序区块可由配置动态变化，非固定死**；沿用 v10.0 第十五章「定时任务与多租户」）

---

> **v9.0 核心设计原则（角色篇）**
>
> - **角色不分版本定义，权限不分版本硬编码**。所有版本（小微版 lite/pro、企业版基础/高级/专业）的角色，都来自**同一套系统级「标准角色集」**。
> - **系统管理员（admin）**：定义标准角色集 + 给每个角色绑定权限（菜单/区块）。
> - **平台管理员（各租户）**：不做权限配置，只做**角色映射**——从标准角色集里挑选本租户需要的角色、改名（助教→主持人）、启用/禁用、并把用户分配到角色。
> - **版本差异**：由「角色模板（哪些标准角色 + 哪些菜单/区块）」决定，不靠新增角色 code。企业版高级版多出的"项目经理/报销人员/财务"，本质是标准角色集里的几条记录，与小微版的"业务员/顾客"平级。
>
> **v10.1 新增（小微版分档）**：小微版不再是一档，拆为 **`micro_lite`（轻量版·免费，仅推广：发海报/活动预告/公众号通知）** 与 **`micro_pro`（经营版·收费，放开预约/打卡/结算/报表/定价等全部经营功能）**。
> 两档**共用同一套角色集与菜单表**，仅「角色模板里勾选的菜单范围」不同；升级 = 菜单自动扩围，**零代码、零迁移**。
>
> **v10.2 新增（角色可见性硬隔离，见 2.1.0 节）**：虽然物理上同在一张 `sys_role` 表，但每个角色用 `tenant_type_scope` 标记归属（micro/enterprise/both）。
> **平台管理员在「角色映射」时，后端按本租户产品线过滤可选角色列表——小微版只看 boss/salesman/customer，企业版只看 boss/project_manager/expense_staff/finance，跨线角色直接不可见（不是"禁用"，是数据源层面过滤）。**
> 这条规则与 lite/pro 分档**正交**：lite/pro 决定"菜单多少"，`tenant_type_scope` 决定"角色能不能出现"，二者互不影响。

## 第 0 章 身份识别总纲（v7.0 第一原则）

> 本章是全文档的第一原则，所有菜单、登录、权限逻辑都服从它。

### 0.1 五个全局约束

| # | 规则 | 说明 |
|---|------|------|
| 1 | **全平台 = 一个微信小程序 = 一个 appid** | 老板 / 业务员 / 顾客 全部进同一个小程序，不拆包、不区分 appid |
| 2 | **后端以手机号为主键建立用户** | 一个手机号 = 一个 `sys_user`，跨端、跨租户唯一 |
| 3 | **身份只用 `租户号 + 角色` 区分** | appid / 登录渠道 **不参与**身份与权限判定 |
| 4 | **只有老板有 PC 后台；其余全部落在小程序** | 老板额外拥有小程序入口（仅看报表 / 改报价） |
| 5 | **appid 只做"合法性校验"，不做业务区分** | 后端仅验证"请求是否来自我方小程序"，取到手机号即完事 |

### 0.2 两个维度的职责（一句话区分）

> v7.0 起**不再使用 appid / 渠道识别角色**，只认下面两个：

```
租户号    → 你现在是「哪个店」，决定「数据隔离」
角色      → 你能「干什么」，决定「菜单 / 权限」
```

| 维度 | 取值 | 谁给的 | 变了没 |
|------|------|--------|--------|
| 租户号 | A001 / B002 ... | 扫码 / 分享链接 / 选租户页 | 一个用户可跨多个租户 |
| 角色 | boss / salesman / customer | `user_tenant_role` 关联表 | 同一用户在不同租户可不同 |

> **说明**：PC 后台和微信小程序是两个"前端壳"，但**走的是同一套身份**——同一个手机号 + 同一个租户号 + 同一个角色。
> 区别只在 `sys_menu.client_type`（菜单标记自己属于 PC 还是小程序），后端据此返回不同菜单，**与 appid / 登录渠道无关**。

### 0.3 识别顺序（后端统一执行）

```
① 手机号             →  定位 sys_user（不存在则自动注册）
② 租户号            →  定位数据范围（多租户时让用户选 / 从场景带入）
③ 租户 + 角色       →  查角色模板 → 菜单 + perms
④ client_type 过滤  →  按"当前前端壳"裁剪菜单（PC 全量 / 小程序精简）
```

> 第 ④ 步的"当前前端壳"由**调用接口时明确指定**（PC 端请求就取 pc/both，小程序端请求就取 mini/both），
> 而不是靠 appid 反查。**appid 在任何业务判断中都不出现。**

### 0.4 一个用户跨租户的示例

```
手机号 138xxxx = sys_user #1
  ├── 租户 A（XX桌游店）   → boss               → PC后台(全量) + 小程序(报表/定价)   [小微版]
  ├── 租户 B（YY买菜）    → salesman           → 同一个小程序(排班/收入/打卡)        [小微版]
  ├── 租户 C（ZZ健身房）   → salesman           → 同一个小程序(排班/收入/打卡)        [小微版]
  └── 租户 D（某设计公司）  → project_manager    → PC后台(项目/审批) + 小程序(我的项目) [企业版高级版]
```

→ 无论用 PC 还是小程序登录，后端都只看 `tenant_id + role_code`，返回对应菜单。
→ **`boss` / `salesman` / `project_manager` 全部来自同一套 `sys_role` 标准角色集**，区别只在租户的角色映射里挑了哪些、叫什么名字。

```
┌──────────────────────────────────────────────────────────────┐

                       │ 新建租户（版本 + 行业模板）
                       ↓
┌──────────────────────────────────────────────────────────────┐

│                      │                                       │
│  ★平台管理员做         │   ★平台管理员做                       │
│   「角色映射」：        │    「角色映射」：                      │

│  （项目经理/报销人员/   │   （助教/配送员/教练...）             │
│   财务/老板）          │   lite→pro：菜单扩围，零迁移            │
│   ※只可见企业版角色     │    ※只可见小微版角色                  │
│         ↓ 全部引用同一套标准角色集 ↓                           │

        ↑ 共用：租户后台 / 标准角色集 / 角色模板 / 若依底座

### 1.1 端的定义（v7.0：一个 App + 一个 PC）

| 端 | 载体 | appid 作用 | 谁用 | 说明 |
|----|------|-----------|------|------|
| **PC 后台** | 浏览器 Web | 无 | **仅老板 + 平台管理员 + admin** | 重管理：定价、结算、收支、配置、用户/角色 |
| **微信小程序** | 微信内（**全平台唯一一个小程序**） | **仅做合法性校验，业务零区分** | **老板 + 业务员 + 顾客 全部** | 轻量操作、随时输入；按角色动态渲染视图 |

**关键规则（v7.0）：**
- ❌ 不区分"业务员一个小程序、顾客一个小程序、老板一个小程序"
- ✅ **全平台 = 一个微信小程序 = 一个 appid**，所有角色共用入口，登录后按角色渲染不同视图
- ✅ **appid 不进任何业务判断**（不区分角色、不区分行业、不区分租户），只用来验明"这是我方小程序"
- ✅ 老板有**两个前端壳**：PC 后台（日常管理） + 同一小程序（只看报表 / 改报价）
- ✅ **只有老板有 PC 后台**；业务员、顾客、以及移动场景的老板 → 全部落在这个唯一小程序里
- ✅ 用户以**手机号**建立，小程序手机号一键登录即完成"注册 or 绑定"

### 1.2 为什么这样分

| 使用场景 | 端 | 理由 |
|---------|----|------|
| 配置服务项目和价格 | PC | 表格多、输入量大，PC 方便 |
| 给助教做周结、**标记已线下发放** | PC | 要核对、审批，PC 稳妥（只记账不打款） |
| 手动补录房租水电 | PC | 偶发、表单长 |
| 老板出门在外看今天赚多少 | **小程序** | 移动必选 |
| 老板临时改一个项目报价 | **小程序** | 快速 |
| 助教看排班、打卡、看收入 | **小程序** | 人在店里，手机随身 |
| 顾客预约、**到店付** | **小程序** | 扫码即用、免安装（V1 不在线支付） |

## 二、角色权限模型

> **v9.0 核心变化：角色映射从「小微版专属」升级为「全版本统一机制」。**
> 小微版、企业版（基础/高级/专业）**不再各自定义角色**，而是共用**同一套系统级标准角色集**。
> 企业版高级版的项目经理、报销人员、财务，与小微版的助教、配送员一样，都是标准角色集里的普通成员。

### 2.1 标准角色集（系统级 · 一套大集合 · admin 定义）

> **全部版本共用这一张表**，不分小微/企业、不分行业。
> 新增角色只在此表加一行 + 绑定权限，各版本/各租户即可按需映射。

| 标准角色 code | 名称 | 身份定位 | 主要出现版本/场景 |
|--------------|------|---------|------------------|
| `boss` | 老板 | 最高权限身份（管理端 + 报表） | 全部版本 |
| `salesman` | 业务员 | 一线服务人员（移动端） | 小微版通用 |
| `customer` | 顾客 | 消费端访客（移动端） | 小微版通用 |
| `project_manager` | 项目经理 | 管项目 + 团队审批 | 企业版（高级/专业） |
| `expense_staff` | 报销人员 | 提交/查看报销单 | 企业版（基础/高级/专业） |
| `finance` | 财务 | 审核/打款/科目管理 | 企业版（高级/专业） |

> **原则**：角色 code 是"身份"不是"菜单位单"。同一个 `salesman`，在桌游店叫"助教"，在买菜店叫"配送员"，在健身房叫"教练"——**code 不变，只变显示名**。

#### 2.1.0 ★ 每个标准角色的「产品线归属」（`tenant_type_scope`）—— 平台管理员可见性的硬隔离依据

> **v10.2 新增硬隔离规则**：虽然所有角色**物理上同在一张 `sys_role` 表**（一套大集合），但**逻辑上每个角色都属于某一条产品线**，由 `sys_role.tenant_type_scope` 字段标记。
> **平台管理员在「角色映射」时拉取"可选角色列表"，后端强制按本租户的 `tenant_type` 过滤，只返回归属相符的角色——跨产品线的角色直接不可见，而不是"可见但禁用"。**

| 标准角色 code | tenant_type_scope | 说明 |
|--------------|------------------|------|
| `boss` | **both**（两条线都有） | 老板是通用身份，小微版、企业版都出现 |
| `salesman` | **micro** | 仅小微版（业务员/助教/配送员/教练） |
| `customer` | **micro** | 仅小微版（顾客/会员） |
| `project_manager` | **enterprise** | 仅企业版 |
| `expense_staff` | **enterprise** | 仅企业版 |
| `finance` | **enterprise** | 仅企业版 |

> **字段取值**：`micro` / `enterprise` / `both`（默认 `both` 仅限 `boss` 这类跨线通用身份）。
> **隔离效果**：
> - 桌游店（`tenant_type=micro`）的平台管理员 → 可选列表 = `boss` + `salesman` + `customer`，**`project_manager` / `expense_staff` / `finance` 根本不会出现**（连"禁用"按钮都看不到）
> - 设计公司（`tenant_type=enterprise`）的平台管理员 → 可选列表 = `boss` + `project_manager` + `expense_staff` + `finance`，**`salesman` / `customer` 不会出现**
>
> **这就是"不能串"的落地方式**：不是靠前端隐藏，而是**后端可选角色接口直接按 `tenant_type_scope` 过滤**，从数据源上切断跨线。

#### 2.1.1 标准角色 → 权限绑定（admin 的职责）

```
admin 在「角色模板」里给每个标准角色绑定：
├── 菜单集合（PC 后台菜单 + 小程序菜单，通过角色模板按版本区分）
└── 小程序区块集合（page_block_config，通过 module_type 区分 micro/enterprise）
```

> **关键点**：admin 定义"角色能干嘛"；**版本差异体现在「角色模板」里绑的菜单/区块不同**，而不是靠新增角色 code。

### 2.2 业务角色 = 标准角色 + 「租户内显示名」马甲

> **行业/租户差异 = 只改显示名，不改 code。**
> 平台管理员的「角色映射」就是做这件事——**从标准角色集挑出本租户要用的，改成本地化名字**。

| 标准角色 code | 小微·桌游店 | 小微·买菜 | 小微·健身房 | 小微·汤泉 | 企业版·高级版 |
|--------------|------------|----------|-----------|----------|-------------|
| `boss` | 桌游老板 | 菜店老板 | 健身老板 | 汤泉老板 | 老板 |
| `salesman` | 助教 | 配送员 | 教练 | 技师 | （通常不映射） |
| `customer` | 顾客 | 买家 | 会员 | 顾客 | （通常不映射） |
| `project_manager` | — | — | — | — | 项目经理 |
| `expense_staff` | — | — | — | — | 报销人员 |
| `finance` | — | — | — | — | 财务 |

> 表中"—"表示该租户**未映射此角色**（平台管理员把它禁用即可）。

### 2.3 两层职责分离（v9.0 权限铁律）

> **系统管理员管「身份与权限」（定义标准角色 + 绑定菜单/区块）；**
> **平台管理员管「租户内的映射与分配」（挑角色 + 改名 + 启停 + 分用户）。**
> **两层严格隔离，平台管理员永远碰不到菜单权限。**

| 层级 | 操作者 | 能做的事 | 不能做的事 |
|------|--------|---------|-----------|
| **系统层** | admin | 定义标准角色、绑定菜单/区块、维护行业模板、维护角色模板 | 改具体租户的业务数据 |
| **租户层** | 平台管理员 | **角色映射**：挑选/改名/启用停用 + 把用户分配到角色 | 新建角色 code、改角色权限（菜单/区块） |
| **业务层** | 老板 | 日常经营（定价、结算、看报表） | 改角色、改权限 |
| **业务层** | 业务员/顾客 | 按角色用功能 | — |

#### 2.3.1 「角色映射」具体能做什么（平台管理员视角）

> 这是 v9.0 的统一动作，**小微版和企业版共用同一套操作界面**：

```
平台管理员 → 角色管理
├── ① 挑选：从标准角色集勾选本租户需要的角色
│     ★ 后端按 tenant_type_scope 自动过滤可选列表（详见 2.1.0），只列出本产品线角色
│     （桌游店只能看到 boss/salesman/customer；企业版只能看到 boss/project_manager/expense_staff/finance）
│     → boss 默认必选且不可删（每个租户必有老板）
├── ② 改名：把标准角色显示为本地化名字（salesman → "助教" / "主持人"）
├── ③ 启用/禁用：不用的角色直接禁用（如桌游店禁用 customer）
├── ④ 分配用户：把具体用户挂到某个角色上（可多对多）
└── ⑤ 调整顺序：在管理后台的显示排序
```

> **平台管理员全程不涉及菜单、perms、区块权限**——这些由 admin 在角色模板里预置好了。
> **关键**：平台管理员"挑选角色"时**看不到跨产品线的角色**（如小微版看不到 `project_manager`），因此**物理上不可能把企业版角色映射进小微租户**，从机制上杜绝"串线"。

### 2.4 企业版高级版的角色映射示例（重点）

> 企业版高级版的"项目经理/报销人员/老板/财务"，**和小微版的"助教/配送员"走完全一样的映射流程**（挑选→改名→启停→分用户）：

| 步骤 | 平台管理员操作 | 等价于小微版的 |
|------|--------------|-------------|
| ① 挑选角色 | 勾选：boss / project_manager / expense_staff / finance（**企业版可选列表，由 `tenant_type_scope=enterprise` 自动限定**） | 桌游店勾选 boss/salesman/customer（**小微版可选列表，由 `tenant_type_scope=micro` 自动限定**） |
| ② 改名 | 财务 → "出纳兼财务"（可选） | salesman → "助教" |
| ③ 启用/禁用 | （全部启用） | （customer 启用） |
| ④ 分配用户 | 张三 → project_manager；李四 → expense_staff | 张三 → salesman |
| ⑤ 用户登录 | 张三登录 → 角色=project_manager → 拿到对应菜单+区块 | 同左 |

> **机制完全一样，区别只在「从标准角色集里挑了哪些」和「显示名叫什么」——而「能挑哪些」由 `tenant_type_scope` 硬隔离自动决定，平台管理员无需、也无法手动过滤。**

### 2.5 跨版本标准角色 vs 版本专属角色的边界

| 问题 | 答案 |
|------|------|
| 企业版需要新角色（如项目经理）怎么办 | **admin 在标准角色集加一行** `project_manager`（`tenant_type_scope=enterprise`）+ 绑企业版菜单；各租户平台管理员即可映射。**不改框架、不加版本分支代码** |
| 小微版租户能看到项目经理这个角色吗 | **看不到（硬隔离）**。`tenant_type_scope=micro` 的小微租户，可选角色接口**只返回 boss/salesman/customer**，`project_manager/expense_staff/finance` 根本不出现在列表里。这不是"禁用"，而是**数据源层面过滤** |
| 企业版租户能看到 salesman/customer 吗 | **同样看不到**。`tenant_type_scope=enterprise` 的企业租户，可选列表只有 boss/project_manager/expense_staff/finance，**小微版角色不会出现** |
| **两条线角色会不会串** | **不会**。隔离发生在两个层面：① **可选角色列表**（平台管理员映射时）按 `tenant_type_scope` 过滤；② **菜单/区块**（角色模板）按 `tenant_type` + `version_type` 过滤。两层叠加，小微版租户**在任何界面、任何接口都拿不到企业版角色** |
| 不同版本同一角色的菜单不同怎么办 | 靠**角色模板按版本区分**（第四章），同一 `boss` 在小微版绑小微菜单、在企业版绑企业版菜单 |
| 能自定义租户专属角色吗（如"店长助理"） | v9.0 **不支持自建角色 code**，只能从标准角色集挑选 + 改名。如需新身份 → 提给 admin 加到标准角色集（并指定 `tenant_type_scope`） |

> **好处**：新增版本/行业 = 配置角色模板 + 行业模板，**零代码改动**；权限模型一套打天下。

### 2.6 三层控制模型：权限是"天花板"，装修是"排版"（v10.5 沿用）

> **核心问题**：小程序里顾客/助教能看到哪些区块——是固定死的，还是可以由 admin / 老板配置动态变化？
> **答案：不是固定死的，是三层叠加、从上到下控制的。** 这正是整套权限体系能"零代码打通、按需装修"的根本机制。

#### 2.6.1 三层权责（谁决定"能看到什么"）

```
┌──────────────────────────────────────────────────────────────┐
│ 第①层：admin（系统管理员）· PC「资金平台管理菜单」             │
│   → 角色模板（role_template）                                 │
│   → 决定"这个角色在 lite / pro 档下，理论上有哪些菜单 & 区块"  │
│   → 这是「天花板」：天花板以下的才能被配置                     │
├──────────────────────────────────────────────────────────────┤
│ 第②层：平台管理员（各租户老板）· PC「页面装修」                │
│   → 页面区块配置（page_block_config）                         │
│   → 从"有权限的区块"里勾选 / 排序 / 显示 / 隐藏               │
│   → 这是「排版」：老板自己决定首页放什么、不放什么             │
├──────────────────────────────────────────────────────────────┤
│ 第③层：最终渲染（小程序端）                                   │
│   → 后端返回 = 第①层权限 ∩ 第②层配置                         │
│   → 前端按返回的区块列表动态渲染（<component is> 拼积木）      │
└──────────────────────────────────────────────────────────────┘
```

> **一句话**：admin 定"你能用什么"（天花板），平台管理员定"你怎么摆"（排版）。
> **lite 档天花板低（只有活动），pro 档天花板高（预约/打卡/结算全开）；天花板以下的，老板可以随便拖、随便隐藏、随便排序。**

#### 2.6.2 可配置性矩阵（逐项明确"谁能改"）

| 场景 | 能不能改 | 谁改 | 改什么 |
|------|:---:|------|--------|
| lite 版顾客能看到「预约服务」入口 | ❌ 不能 | — | admin 在角色模板里**没给 lite 绑预约权限**，天花板封死 |
| pro 版顾客能看到「预约服务」入口 | ✅ 能（已解锁） | admin 已配置 | 角色模板里 pro 档绑了 `micro:customer:book` |
| pro 版老板想把「快速预约」从首页挪到第二屏 | ✅ 能 | 平台管理员（PC 装修） | 拖拽排序，改 `sort_order` |
| pro 版老板想把「活动推荐」从首页去掉 | ✅ 能 | 平台管理员（PC 装修） | 取消勾选，改 `show_flag = 0` |
| pro 版老板想给顾客首页加「我的优惠券」区块 | ❌ 不能（除非 admin 先开发） | — | 需 admin 先在**区块组件库**新增该组件 + 绑权限，老板才能勾选 |

> **边界**：老板能改的是"已有区块的显隐与排序"，**不能凭空造出新区块 / 新权限**——那是 admin 的职责（开发组件 + 写进角色模板）。

#### 2.6.3 数据库层面的体现（天花板 ∩ 排版）

```sql
-- 第①层：admin 定天花板（角色模板，按 档位 + 角色 绑定权限）
role_template:
  version_type = 'micro_lite',  role_code = 'customer'
  → menu_keys = ["micro:customer:shop", "micro:promo:list"]        -- lite：只有活动
role_template:
  version_type = 'micro_pro',   role_code = 'customer'
  → menu_keys = ["micro:customer:shop", "micro:customer:book",
                  "micro:promo:list", ...]                        -- pro：全量

-- 第②层：平台管理员定排版（页面装修，tenant 级覆盖）
page_block_config:
  tenant_id = 123, role_code = 'customer', page_key = 'home'
  → [{block_key: 'activity_banner', show_flag: 1, sort: 1},
     {block_key: 'quick_booking',  show_flag: 0, sort: 2}]        -- 老板把预约隐藏了

-- 第③层：最终返回 = 角色模板有权限 ∩ 装修配置了显示 → 顾客首页只显示「活动推荐」
```

#### 2.6.4 与前面规则的协同关系

| 已有规则 | 在三层模型中的位置 |
|---------|------------------|
| "lite 版顾客/助教只能看活动" | 第①层：admin 在角色模板里，lite 档只绑 `micro:promo:*` 权限，其余全不绑 |
| "pro 版全功能放开" | 第①层：admin 在角色模板里，pro 档绑定全部 `micro:*` 权限 |
| "老板可以自己装修页面" | 第②层：`page_block_config`（第十六章） |
| "升级后自动解锁" | 租户 `version_type: lite → pro`，角色模板自动切换到 pro 档菜单范围，**老板装修区自动多出新区块可勾选** |
| "小程序不通用 PC「资金平台管理菜单」" | PC 菜单走 `sys_menu`，小程序区块走 `page_block_config`，**但权限标识（perms）同源同体系** |

> **关键结论**：小程序端**不需要、也不应该**把 PC 的「资金平台管理菜单」搬进去（顾客/助教根本不用"租户管理/角色模板"这些 admin 功能）。
> 小程序用**扁平区块列表**（`page_block_config`）驱动，"谁能看到什么区块"仍由**同一套 perms + 角色模板**判定——**这是 PC 菜单权限在小程序端的投射，底层同源、两端一致**。

#### 2.6.5 升级时的行为（零迁移再次印证）

```
lite 档 tenant                        pro 档 tenant
├── 角色模板：仅 promo 权限            ├── 角色模板：promo + book + settle + ...
├── 装修区可用区块：{活动}             ├── 装修区可用区块：{活动, 预约, 结算, ...}
└── 顾客首页 = {活动}                  ├── 老板可自由勾选/排序/隐藏任一区块
                                        └── 顾客首页 = 老板排版后的结果
        ↑                                        ↑
   升级 = UPDATE version_type        装修区自动扩展，无需重建，历史配置保留
```

> **升级不会改变老板已有的装修配置**（已勾选的区块继续保持），只是"解锁更多可选区块"供其勾选——所以**升级是纯增量、零风险**。

### 3.1 为什么只有小微版需要

## 四、角色模板（菜单 + 区块配方）

> 标准角色 → 绑定哪些菜单 + 哪些小程序区块。
> **小微版、企业版各一套角色模板**，但**都引用同一套标准角色集**（第二章 2.1）。

### 4.1 小微版角色模板（v10.1 拆为两档：lite 免费 / pro 收费）

> **核心变化**：小微版不再是一档，而是拆为 **`micro_lite`（轻量版·免费）** 与 **`micro_pro`（经营版·收费）** 两档。
> 两档**共用同一套标准角色集、同一套菜单表**，差异只体现在「角色模板里勾选的菜单范围不同」——完全复用现有的 `version_type` 机制，**不新增角色 code、不复制模板**。

#### 4.1.0 分档总览（一图看清）

| 维度 | **micro_lite（轻量版）** | **micro_pro（经营版）** |
|------|------------------------|------------------------|
| **定价** | 🆓 **永久免费** | 💰 **收费（参考 499 元/月，首月 299 体验）** |
| **定位** | 只会"发"——发海报、发活动预告、公众号通知 | 放开**全部经营功能**：预约 + 打卡 + 结算 + 报表 + 定价 |
| **核心场景** | 老板做推广、攒客流，暂不需要管账 | 老板要管清楚每一笔生意的钱（= 原小微版全量） |
| **是否含预约** | ❌ | ✅ |
| **是否含结算/报表/定价** | ❌ | ✅ |
| **业务员/顾客角色** | ✅ **只读**：salesman / customer 各有一个「活动浏览页」（看海报/预告/店铺介绍），除此之外无任何功能 | ✅ salesman / customer 全量（排班/收入/打卡 + 浏览/预约/到店付） |
| **升级路径** | → 一键升级到 pro（菜单自动扩展，数据全保留） | — |

#### 4.1.1 micro_lite（轻量版·免费）—— 只有推广

> 老板唯一诉求：**把人引来**。功能极简，只保留"发海报 / 发活动预告 / 公众号通知"相关菜单。
> **不含预约、不含打卡、不含结算、不含报表、不含定价。**
>
> **但 lite 版并非"只有一个老板"**：老板发出来的活动/预告/海报，**顾客（customer）和助教（salesman）都需要一个"活动浏览页"来看**——
> 所以这两个角色在 lite 档**被映射、但只绑定一个只读页面**，其余功能全部关闭。

| 标准角色 | PC 后台 | 微信小程序 | 绑定菜单 |
|---------|---------|-----------|---------|
| **boss** | ✅ 仅推广配置 | ✅ 发预告/看传播 | **推广发布**（发海报/活动预告/公众号推送）/ 店铺信息设置 / 收款方式说明 |
| **salesman** | — | ✅ **活动浏览页（只读）** | **活动浏览页**（看本店海报/活动预告/店铺介绍）—— **仅此一个页面，无排班/收入/打卡** |
| **customer** | — | ✅ **活动浏览页（只读）** | **活动浏览页**（看本店海报/活动预告/店铺介绍）—— **仅此一个页面，无预约/我的预约/收款方式** |

> **小程序侧（lite 版）**：
> - **顾客 / 助教打开小程序，只看到「活动浏览页」**——本店海报、活动预告、店铺介绍，只读，无需登录即可浏览；
> - **没有**"预约服务 / 我的预约 / 排班 / 我的收入 / 打卡"等任何入口（`role_template` 里这些菜单未勾选）。
> - 顾客无需登录即可看，助教/顾客若尚未绑定租户，走分享链接或扫码带入 `tenant_id` 即可。
>
> **PC 侧（lite 版）**：老板 PC 后台只开放「推广发布 / 店铺管理 / 系统设置」三个菜单组，预约/结算/收支/报表菜单**不可见**。

#### 4.1.1.1 lite 档「活动浏览页」说明（salesman / customer 共用页面，按角色渲染）

> 顾客和助教看的**是同一个页面**（同一套活动数据源），只是入口/角色不同；页面本身**只读、公开、零交互**：
>
> - **数据来源**：与老板 PC「推广发布」发布的活动/海报/预告同表（`promotion_activity`），按 `tenant_id` 过滤，**只看自己店**；
> - **无需登录**：顾客扫码/点分享链接即可看，不要求绑定手机号、不产生预约单；
> - **不支持动作**：页面上**没有任何按钮**能跳到"预约 / 报名 / 支付 / 打卡"（这些菜单在 lite 档未授权）；
> - **升级到 pro 后**：顾客页面**自动扩展**出"预约服务 / 我的预约"，助教页面**自动扩展**出"排班/收入/打卡"——因为 `role_template` 刷新了菜单范围，页面壳与区块配置不变，只是多了入口。

| 维度 | lite 档（免费） | 升级到 pro 档后 |
|------|----------------|----------------|
| **customer 看到的** | 活动浏览页（只读：海报/预告/介绍） | 活动浏览页 + **预约服务 / 我的预约 / 收款方式** |
| **salesman 看到的** | 活动浏览页（只读：海报/预告/介绍） | 活动浏览页 + **我的排班 / 我的收入 / 打卡** |
| **底层页面壳** | 同一个 `home` + 区块配置 | 同一个 `home` + 区块配置（多了授权区块） |
| **代码改动** | 无需新增页面壳，只靠 `role_template` + `page_block_config` 控制 | 自动生效，零改造 |

#### 4.1.2 micro_pro（经营版·收费）—— 全部经营功能

> = **lite 的全部推广功能** + **预约 / 打卡 / 结算 / 报表 / 定价** 全量经营功能。
> 这是**原"小微版"的完整功能集**，现归入 pro 档。

| 标准角色 | PC 后台 | 微信小程序（同一小程序） | 绑定菜单 |
|---------|---------|------------------------|---------|
| **boss** | ✅ 全量管理 | ✅ 报表 + 改报价 | 经营概览 / 预约管理 / 结算 / **报表中心(小程序重点)** / **定价管理(小程序可改报价)** / 推广发布 / 店铺管理 |
| **salesman** | ❌ | ✅ 排班/收入/打卡 | 我的排班 / 我的收入 / 打卡 |
| **customer** | ❌ | ✅ 浏览/预约/到店付 | 浏览店铺 / 预约服务 / 我的预约 / 查看收款方式（**无在线支付**） |

> **关键**：pro 档的菜单 = lite 档菜单 **∪** 经营类菜单（预约/结算/收支/报表/定价/人员管理）。
> 升级时**只需把 boss 角色的菜单范围从 lite 集合扩展到 pro 集合**，角色 code、用户、业务数据全部不动。

#### 4.1.3 lite → pro 升级机制（菜单级扩围，零迁移）

```
tenant.version_type: micro_lite  →  micro_pro
        ↓ （仅此一步，其余自动生效）
role_template 刷新：boss 菜单从「lite 集合」扩展到「pro 集合」
        ↓
- 角色 code 不变（仍是 boss/salesman/customer）
- 用户不变、业务数据不变（lite 期间产生的推广数据、活动浏览数据完整保留）
- salesman / customer 角色**在 lite 档就已启用，只是各自只有「活动浏览页」这一个只读页面**；升级到 pro 档后，**同一角色追加**排班/收入/打卡（salesman）、预约/我的预约（customer）等菜单——角色本身不增删、不切换
- 原"预约/结算/报表"菜单即时可见、可操作（表结构一直存在，仅受权限控制）
```

> **这就是为什么能"零代码打通"**：预约/结算/报表等表在小程序侧**始终部署**，lite 档只是通过角色模板把这些菜单"关掉"，
> pro 档再把它们"打开"。升级 = 一条 `UPDATE tenant SET version_type='micro_pro'` + 菜单缓存刷新。

### 4.2 企业版角色模板（基础/高级/专业共用机制，按版本增减）

> 企业版各版本（基础/高级/专业）同样通过「角色模板」绑定菜单，引用的仍是标准角色集。
> **高级版相比基础版多映射了 `project_manager` / `finance` 等角色**（即角色模板里多选几行），不是另起一套。

| 标准角色 | PC 后台 | 微信小程序 | 绑定菜单（示例） |
|---------|---------|-----------|----------------|
| **boss** | ✅ | ✅ 报表/审批概览 | 预算科目 / 报销审批 / 科目余额 / 报表中心 / 项目管理（高级/专业） |
| **expense_staff** | ❌（或基础录入） | ✅ 我的报销单 | 提交报销 / 我的报销单 / 我的待办 |
| **project_manager** | ✅（高级/专业） | ✅ 我的项目 | 项目管理 / 团队报销审批 / 项目预算 |
| **finance** | ✅（高级/专业） | ❌ 或轻量审核 | 报销审核 / 打款队列 / 科目管理 / 月度结算 |

> **版本差异（基础→高级→专业）的实现方式**：
> - **同一套角色模板 + 不同版本勾选不同菜单范围**（在角色模板记录上加 `version_type` 字段区分）。
> - **不是**新建角色 code，也不是复制多套模板。
> - 例：`boss` 这个角色，基础版模板绑「预算+报销+报表」，高级版模板在此基础上**追加**「项目管理/团队审批」。
>
> **`version_type` 完整取值（v10.1）**：小微线 = `micro_lite` / `micro_pro`；企业线 = `basic` / `advanced` / `pro`。
> 小微线的分档逻辑（lite→pro）与企业线（basic→advanced→pro）**完全同构**，都靠"同一角色 + 不同菜单范围"实现。

### 4.3 角色模板 × 小程序区块（模块化）

> 角色模板除绑定菜单外，还绑定**小程序首页等页面的区块**（第十三章模块化架构）。
> 区块同样按 `module_type` 区分来源（micro / enterprise），标准角色在不同版本里展示不同区块：

| 标准角色 | lite 区块（推广） | pro 区块（经营，module_type=micro） | 企业版区块（module_type=enterprise） |
|---------|------------------|-----------------------------------|------------------------------------|
| `boss` | notice_bar / poster_publish_entry | revenue_week / revenue_pending / notice_bar | expense_approve_count / budget_execution_rate / project_overview |
| `salesman`（小微 lite/pro）/ `expense_staff`（企业） | activity_browse（lite：活动浏览页）/ revenue_received / my_schedule / checkin_entry（pro 追加） | revenue_received / my_schedule / checkin_entry | my_expense_list / quick_new_expense / my_todo |
| `customer`（小微 lite/pro） | activity_browse（lite：活动浏览页）/ 预约/我的预约（pro 追加） | 浏览店铺 / 预约服务 / 我的预约 | — |

> **结论**：标准角色 + 角色模板（菜单+区块）这套机制，**同时服务小微版和企业版**；企业版高级版的"项目经理/报销人员/财务"与小维版的"业务员/顾客"地位完全平等。

| ├── 活动推送过滤 | 后端 | F | micro:promo:pushFilter | 黑名单顾客**默认不推送**活动/预告 |
| └── 老板移出黑名单 | PC / 小程序 | F | micro:customer:unblacklist | 老板在「顾客管理」手动移除 → 恢复推送与预约 |

> **没有 `micro:customer:pay`（在线支付）菜单，顾客端零支付代码。**

### 5.6.1 防爽约机制（v10.5 新增 · 仅 `micro_pro`）

> **背景**：顾客预约后放鸽子（爽约）会造成桌游/买菜/健身房等行业的排班与库存浪费。
> **规则**：单个顾客**累计爽约 3 次即自动拉黑**——此后**活动推送默认不推给他**，且**禁止提交新预约**，
> 直到**老板在「顾客管理」里手动将其移出黑名单**。
> **生效范围**：仅 `micro_pro`（有预约功能）；`micro_lite` 无预约，自然无爽约判定。

#### 爽约判定的触发时机

```
顾客提交预约 → booking_order(status='pending', expire_time=预约时间+15分钟)
  │
  ├── 顾客到店 → 老板标记「已完成」→ status='completed'      （正常，不计分）
  ├── 顾客主动取消（开约前）→ status='cancelled'             （不算爽约）
  └── 过期未到店 → 【触发爽约判定】
       ├── 方案A（推荐）：XXL-JOB 定时扫描 expire_time 已过且仍 pending 的单
       └── 方案B：老板点「标记爽约」
            → status='no_show'
            → customer_credit.no_show_count += 1
            → if no_show_count >= 3 → is_blacklisted = 1
```

> **关键**：爽约以「**预约时间已过且未到店、未主动取消**」为准，**主动取消不算爽约**（避免误伤）。
> 判定由**定时任务**（第十五章 `@TenantJob`，版本过滤 `versionTypes={micro_pro}`）逐租户扫描，单租户异常不影响其他租户。

#### 黑名单的两层效果

| 效果 | 触发条件 | 表现 |
|------|---------|------|
| **① 禁止新预约** | `is_blacklisted=1` | 小程序「提交预约」按钮置灰/接口拒绝（前端提示"预约已达上限，请联系商家"） |
| **② 活动推送过滤** | `is_blacklisted=1` | 订阅消息 / 模板消息推送名单**自动剔除**该顾客，**默认不推** |

> 两层效果**同时生效且不可被顾客自行解除**——只有老板有权移除。

#### 解除方式（唯一出口 = 老板手动）

```
老板 PC「顾客管理」→ 找到该顾客 → 点「移出黑名单」
  → is_blacklisted = 0
  → no_show_count 保留（作为历史记录，不清零，便于老板判断）
  → 立即恢复：可提交新预约 + 重新进入活动推送名单
```

> **设计取舍**：
> - **不清零爽约次数**——老板能看见此人历史"信誉"，再次拉黑有依据；
> - **若老板希望彻底清白，可二次确认后手动清零**（可选操作，非默认）；
> - **跨租户隔离**：爽约记录按 `tenant_id` 隔离，A 店的黑名单**不影响**该用户在 B 店的正常预约（一人可跨多店）。

## 六、微信小程序端架构（v7.0 · 全平台单一小程序）

### 6.1 一个 app，三个角色视图

> **全平台（桌游店 / 买菜 / 健身房 / 汤泉 ...）共用同一个微信小程序、同一个 appid。**
> appid **不区分角色、不区分行业、不区分租户、不参与权限判断**——它只证明"请求来自我方小程序"。

```
微信小程序（唯一 appid · 全平台共用）
│
├── 入口：手机号一键登录（wx.login + getPhoneNumber）
│
├── 身份识别（不依赖 appid，只看租户号 + 角色）
│     ├── ① 手机号       → 定位 sys_user（无则注册）
│     ├── ② 租户号       → 定位数据范围（多租户则选一个）
│     └── ③ 角色         → boss / salesman / customer
│
├── 路由到对应视图（同一包内按角色动态渲染）
│     ├── boss      → 老板视图（lite=推广发布；pro+=报表+定价快改+经营）
│     ├── salesman  → 业务员视图（lite=活动浏览页；pro+=排班+收入+打卡）
│     └── customer  → 顾客视图（lite=活动浏览页；pro+=浏览+预约+支付）
│
└── 共用能力
     ├── 消息推送（订阅消息）
     ├── 分享海报
     └── 扫码进入带租户号的场景

> **V1 无支付能力：** 不集成微信支付收款、不代发工资、不调任何转账接口。
> 资金流全程不在平台过手——老板用自己的收款码/现金/POS 线下收，系统只做记账与结算单。
```

**为什么这样做是对的：**
- 一个小程序包 + 角色路由 → 无需拆包、无需多 appid、无需多套发布流程
- **appid 完全退出业务判断**，换小程序 / 加小程序都不影响后端逻辑
- 菜单权限仍由后端 perms 控制，前端只是"按 perms 显隐"——**视图不同 ≠ 权限不同**
- 新增行业（理发店、美容院）**只加行业模板，小程序零改动**

### 6.2 租户号怎么带入小程序

| 进入方式 | 租户号来源 |
|---------|-----------|
| **扫码进店**（店里二维码） | 码中带 `tenant_id`，进入即锁定 |
| **分享链接 / 海报** | URL 参数 `?tenantId=A001` |
| **已有账号登录**（老板/业务员已绑定某租户） | 登录后若**只有一个租户**→直接进入；**多个租户**→弹出租户选择页 |
| **顾客首次预约** | 走分享链接带入，无需注册；手机号即账号 |

> 顾客**不需要选租户、不需要登录**：扫码/点链接即锁定租户，手机号快捷验证只为支付与"我的预约"。

### 6.3 小程序菜单权限来源（与 PC 共用同一套）

```
登录（手机号 + tenantId + client_type=mini）
  → ① 定位 sys_user
  → ② 查 user_tenant_role → tenant_id + role_code
  → ③ role_code + tenant_type + industry_type → 角色模板 → menu_keys
  → ④ 端过滤（client_type = mini）：只保留 mini/both 的菜单
  → ⑤ 返回 perms 集合 → 小程序按 perms 显隐页面/按钮
```

**关键点：`sys_menu.client_type`（pc / mini / both）决定同一角色在两端看到的不同菜单。**
老板的 boss 角色在小程序端**只返回报表 + 定价快改的菜单**，所以天然看不到结算管理、用户管理——无需单独角色。

### 6.4 端 × 角色 速览表

| 角色 | PC 后台 | 微信小程序（唯一） | 身份识别依据 |
|------|---------|-------------------|-------------|
| admin | ✅ 全部系统管理 | ❌（不提供小程序入口） | role_code |
| 平台管理员 | ✅ 用户/角色/定价/配置 | ❌ | role_code |
| **老板** | ✅ 订单/结算(记账)/收支/报表/推广 | ✅ **报表 + 改报价** | role_code = boss |
| 业务员 | ❌ | ✅ 排班/收入/打卡 | role_code = salesman |
| 顾客 | ❌ | ✅ 浏览/预约/**到店付(不在线支付)** | role_code = customer（或无账号轻登） |

> 后端只看 `租户号 + 角色`：**同一老板用 PC** → 返回 pc 菜单；**同一老板用小程序** → 返回 mini 精简菜单。
> 角色不变、租户不变，只是 `client_type` 变了，菜单随之裁剪。**全程没有 appid 判断。**

## 八、租户创建流程

### 8.0 ★ Admin「新建租户」页面规范（v10.3 新增）

> **核心原则：所有「产品线 / 版本档位」的可选值，都由 admin 在「新建租户」这一步选定；选定后写入 `tenant`，成为该租户后续一切（角色可见性、菜单范围、计费）的唯一依据。**
> 也就是说——**版本不是在别处配置的附属项，而是"建租户"表单本身必填的两个核心字段**。

#### 8.0.1 页面字段清单（admin 必填 / 选填）

| 字段 | 类型 | 必填 | 可选范围 | 写入 `tenant` 字段 | 说明 |
|------|------|------|---------|-------------------|------|
| 租户名称 | input | ✅ | 自由输入 | `tenant_name` | 如「XX桌游店」 |
| **产品线（tenant_type）** | radio | ✅ | `小微版(micro)` / `企业版(enterprise)` | `tenant_type` | **第一步选，决定后面版本档位的候选集** |
| **版本档位（version_type）** | select | ✅ | **由产品线级联**（见 8.0.2） | `version_type` | 默认取该产品线的免费档 |
| 行业模板（industry_type） | select | 小微版必填 / 企业版隐藏 | **由产品线级联**（小微版显示行业模板，企业版无） | `industry_type` | 企业版隐藏此字段（企业版无需行业模板，角色由平台管理员直接映射） |
| 平台管理员账号 | input | ✅ | 手机号 | `admin_user_id` | 指定本租户的平台管理员 |

#### 8.0.2 ★ 级联规则（页面交互核心）

> **产品线一旦选定，版本档位和行业模板的下拉选项即被锁死在该产品线内——这与 2.1.0 节的「角色硬隔离」同源，都是靠 `tenant_type` 做数据源过滤。**

```
┌─────────────────────────────────────────────────────────────┐
│  新建租户                                                    │
│                                                             │
│  ① 产品线：  ◉ 小微版    ○ 企业版                           │
│       │                                                     │
│       ▼（选「小微版」后，下方两个下拉自动级联）               │
│                                                             │
│  ② 版本档位： [micro_lite 轻量版·免费 ▾]                    │
│        可选 = { micro_lite(免费), micro_pro(收费499/月) }    │
│        ※ 默认选中 micro_lite                                │
│                                                             │
│  ③ 行业模板： [桌游店 ▾]                                     │
│        可选 = { 桌游店, 社区买菜, 健身房, 汤泉, ... }        │
│        ※ 企业版时此字段隐藏                                  │
│                                                             │
│  ④ 租户名称： [XX桌游店               ]                     │
│  ⑤ 平台管理员： [138xxxx（手机号）     ]                     │
│                                                             │
│  [ 确定创建 ]                                               │
└─────────────────────────────────────────────────────────────┘
```

**级联对照表（同一个下拉，不同产品线给出不同候选）：**

| 产品线（第①步） | 版本档位候选（第②步） | 行业模板候选（第③步） | 创建后默认启用的角色 |
|-----------------|---------------------|---------------------|-------------------|
| **小微版（micro）** | `micro_lite`（默认·免费）/ `micro_pro`（收费） | 行业模板列表（桌游店/买菜/健身房/汤泉…） | boss / salesman / customer（全部启用，lite 档只开推广菜单） |
| **企业版（enterprise）** | `basic`（默认）/ `advanced` / `pro` | （**隐藏**，企业版无行业模板） | boss（+ 该版本档位对应角色：basic→仅 boss；advanced/pro→boss + project_manager + expense_staff + finance） |

> **关键**：这里第②步的"版本档位候选"与第③步的"行业模板候选"，**用的是和 9.2「可选角色列表过滤」完全同一套思路——按 `tenant_type` 过滤数据源**，前端下拉直接拿到的是已过滤列表，不存在"选了小微版却出现 basic/advanced"的可能。

#### 8.0.3 为什么版本必须在建租户时选（设计理由）

| 维度 | 说明 |
|------|------|
| **角色隔离的前提** | `tenant_type_scope` 硬隔离依赖 `tenant.tenant_type`；版本档位决定"菜单多少"。两者都必须在建租户时就落库，否则创建后再改等于事后打补丁 |
| **计费起点** | 收费档（micro_pro / basic 及以上）从创建那一刻起开始计费周期；免费档（micro_lite / basic）不计费。计费任务（第十五章 XXL-JOB）启动时读取的就是这两个字段 |
| **菜单初始化** | Step2 查 `role_template` 需要 `tenant_type + version_type + role_code`，三个参数全部来自建租户表单 |
| **不可事后跨产品线变更** | 已创建的租户**不允许**把 `tenant_type` 从 micro 改成 enterprise（会破坏角色/数据隔离）；只能在同一产品线内升降版本（如 micro_lite ↔ micro_pro）。如需跨线，必须**另建租户** |

#### 8.0.4 级联的数据来源（后端接口）

```
GET /admin/tenant/version-options?tenantType=micro
  → 返回 [ {key:"micro_lite", name:"轻量版", fee:0},
            {key:"micro_pro",  name:"经营版", fee:499} ]

GET /admin/tenant/industry-options?tenantType=micro
  → 返回 [ {code:"board_game", name:"桌游店"}, ... ]
     （tenantType=enterprise 时返回 []，前端据此隐藏该字段）

GET /admin/tenant/default-role-preview?tenantType=micro&versionType=micro_lite
  → 返回该产品线+版本下"将默认启用的角色"预览，供 admin 确认
     （小微版 = boss/salesman/customer；企业版按版本档位返回）
```

> 前端「确定创建」时一次性提交 `{tenantType, versionType, industryType, tenantName, adminPhone}`，后端事务内完成 ①②③ 全部初始化。

### 8.1 完整创建流程（基于 8.0 页面提交）

```
① admin 在「新建租户」页面填写（字段详见 8.0.1）：
   ├── 产品线：小微版（tenant_type = micro）
   ├── 版本档位：micro_lite（默认·免费）或 micro_pro（收费）   ← ★ 8.0.2 级联选出
   ├── 行业模板：桌游店                                        ← ★ 小微版必填，企业版隐藏
   ├── 租户名称：XX桌游店
   └── 平台管理员账号：138xxxx

② 系统自动初始化（事务）：
   ├── Step1 查行业模板 → 业务角色映射（桌游老板→boss, 助教→salesman, 顾客→customer）
   ├── Step2 查角色模板（tenant_type + version_type + role_code）
   │     → boss/salesman/customer 的菜单集合
   │     ★ 仅加载 tenant_type_scope ∈ {本租户 tenant_type, 'both'} 的角色，**不引入跨产品线角色**
   │     ★ micro_lite 只绑"推广菜单集"；micro_pro 才扩为"推广∪经营菜单集"（见 4.1 / 十八章）
   ├── Step3 生成 tenant_role / tenant_role_mapping（桌游老板/助教/顾客）→ 映射到标准角色
   ├── Step4 绑定菜单（复制 sys_role_menu 到该租户）
   ├── Step5 写入预置数据（服务分类/结算规则示例）
   ├── Step6 指定平台管理员账号（绑定为 tenant 的 platform_admin）
   └── Step7 初始化计费记录（免费档=未激活计费；收费档=开始计费周期，见十八章）

③ 平台管理员（PC）配置：
   ├── 角色映射（挑/改名/启停——可选范围已被 tenant_type_scope 硬隔离，见 9.2）
   ├── 服务与定价（具体价格）
   ├── 员工档案
   └── 结算规则

④ 日常使用（全部走同一个小程序 + PC）：
   ├── 老板：PC 做结算/收支，小程序看报表/改价
   ├── 业务员：小程序打卡/看收入
   └── 顾客：小程序预约/支付
```

> **要点**：第①步的 `tenant_type` + `version_type` 一旦落库，第②③步的所有行为（角色范围、菜单范围、是否计费）就被唯一确定——**这是"版本由 admin 在建租户时选定"这一规则的落点**。

## 九、若依整合（最小化改动 + 防权限遗漏）

### 9.1 改动清单

| 对象 | 改动 | 说明 |
|------|------|------|
| `sys_user` | 以 `phone` 作为业务唯一键（登录主键） | 手机号一键登录 |
| 新建 `user_tenant_role` | 用户 × 租户 × 角色 关联 | 支持一人多租户、多角色 |
| `sys_role` | 标准角色集（role_code） | **一套大集合**，全版本共用：boss/salesman/customer/project_manager/expense_staff/finance... |
| `sys_menu` | +`client_type`(pc/mini/both) | **关键：标识菜单属于哪个前端壳** |
| `sys_menu` | 菜单项按"前端壳"拆分记录 | 同一功能在 PC/小程序可以是不同菜单 |
| 新建 `industry_template` + `industry_role_map` | 行业模板 + 业务角色映射 | 小微版专属 |
| 新建 `tenant_role_mapping` | **角色映射表**（全版本通用） | 平台管理员把标准角色映射到租户（改名+启停） |
| 新建 `role_template` | 角色模板（菜单配方） | 按版本 × 标准角色（企业版通过 version_type 区分基础/高级/专业） |
| 小程序端鉴权接口 | 基于手机号 + tenantId | 返回 token + perms（**不涉及 appid 业务判断**） |

> **`sys_menu.client_type` 是全平台单小程序的关键：**
> - 同一个 boss 角色 → PC 返回「结算管理 / 用户管理」，小程序只返回「报表 / 定价」
> - **不靠 appid 区分端，靠 `client_type` 过滤**
> - 若依原生 `sys_role_menu` 机制不动，只是在此之上给每条菜单加端标签

### 9.2 菜单加载链路（PC 与小程序统一）

```
登录请求
  ├── 参数：phone（+ tenantId，小程序从场景带入 / PC 多租户则选）
  └── 前端壳标识：PC 请求传 client_type=pc；小程序请求传 client_type=mini
     （这个标识由前端直接声明，不靠 appid 反查）

→ ① UserDetailsServiceImpl / 小程序登录接口
→ ② phone → sys_user；校验状态
→ ③ tenantId → 校验该用户在此租户的关联（user_tenant_role）
→ ④ role_code → 查角色模板（tenant_type + industry_type + role_code）
→ ⑤ 查 sys_menu（仅该租户 + client_type 匹配）
→ ⑥ 组装 perms 集合 + 菜单树 → 返回 token / 登录态
→ ⑦ PC 前端 / 小程序前端 各自按 perms 渲染
```

**可选角色列表过滤（平台管理员「角色映射」时调用，v10.2 硬隔离）：**

```
GET /tenant/role/optional-list?tenantId=xxx
  → ① 取该租户的 tenant_type（micro / enterprise）
  → ② SELECT role_code FROM sys_role
        WHERE tenant_type_scope IN (tenant_type, 'both')   ← ★ 关键过滤
        [AND status = enabled]
  → ③ 返回过滤后的角色列表（小微版只返回 boss/salesman/customer；企业版只返回 boss/project_manager/expense_staff/finance）
  → ④ 前端在此列表内做"挑选/改名/启停"，**无法选到跨产品线角色**
```

> **为什么是硬隔离**：此接口是平台管理员能看到的"全部可选角色"的**唯一数据源**，过滤在此处发生，意味着跨线角色在数据库查询阶段就被排除，**不依赖前端隐藏、不依赖管理员自觉**。

**client_type 过滤规则（后端固定）：**

| 前端壳 | client_type 过滤 | 说明 |
|--------|-----------------|------|
| PC 后台 | `pc` + `both` | 返回 PC 全量菜单 |
| 微信小程序 | `mini` + `both` | 返回小程序精简菜单 |

> 因为**所有角色共用一个小程序**，这里**不判断角色、不判断 appid**，只按 `client_type` 过滤菜单——
> 老板在小程序里因为菜单被 `client_type=mini` 过滤，天然只剩"报表 + 定价"。

### 9.3 防"看得见没权限"措施

| 措施 | 说明 |
|------|------|
| 平台管理员无 `system:menu:*` | 改不了菜单 |
| 平台管理员无 `system:role:edit` | 改不了权限绑定 |
| 老板小程序 perms 仅 `micro:report:*` + `micro:service:edit` | 天然看不到结算/用户管理 |
| 每个菜单/按钮强制填 `perms` | `micro:模块:操作` 格式 |
| perms 前缀隔离 | enterprise:* / micro:* |
| 前后端双校验 | `@PreAuthorize` + `v-hasPermi`（PC）/ 小程序权限过滤 |
| **小程序端按钮也走 perms** | 不因"在小程序里"而绕过，防止视图漏控 |
| 改权限后清 Redis + 重登录 | 缓存刷新 |
| **手机号 + 租户号 双重校验** | 防止越租户访问他人数据（数据权限） |

## 十、用户身份识别与租户路由（v7.0 · 不用 appid）

### A. 手机号为主键的建立规则

```
小程序 / PC 登录（均走手机号）
  ├── phone 已存在 → 直接登录，返回该用户在各租户的角色
  └── phone 不存在 → 自动注册 sys_user，再按场景建 user_tenant_role
```

| 场景 | 是否自动建用户 | 是否自动建租户关联 | 角色 |
|------|--------------|------------------|------|
| 老板首次扫码/登录（租户已建） | ✅ | ✅ 绑定到该租户 | boss |
| 业务员被平台管理员录入手机号 | 已是用户则绑定，否则待其首次登录补全 | ✅ | salesman |
| 顾客预约/支付 | ✅ | ❌（顾客无需租户角色，走轻量档案） | customer（可选） |

> **原则：手机号是唯一身份锚点。** 同一个手机号换了端、换了租户，都是同一个 `sys_user`。

### B. 租户号 + 角色 判定（伪代码 · 无 appid 判断）

```java
// 小程序 / PC 通用登录接口
// clientType 由前端壳直接传入（PC="pc"，小程序="mini"），不从 appid 推导
public LoginResp login(String phone, Long sceneTenantId, ClientType clientType) {

    // ① 手机号：建立/定位用户
    SysUser user = userService.getOrCreateByPhone(phone);

    // ② 租户号：确定数据范围
    Long tenantId = resolveTenantId(user, sceneTenantId); // 场景带入 or 让用户选

    // ③ 角色：查该用户在此租户的角色
    String roleCode = userTenantRoleMapper.selectRole(user.getId(), tenantId);

    // ④ 菜单：按 clientType 过滤（mini 精简 / pc 全量）
    Set<String> perms = loadPerms(tenantId, roleCode, clientType);

    return new LoginResp(user, tenantId, roleCode, perms);
}
```

> **注意：方法签名里没有 appid。** appid 的校验（"是不是我方小程序"）放在网关/拦截器里单独做，
> 通过与业务无关的微信签名校验完成；通过后直接走上面的纯业务逻辑。
> 这样将来加 H5 / 支付宝小程序 / 自有 App，只需新增一个 `clientType`，业务逻辑零改动。

### C. 多租户选择流程

```
登录成功 → 查 user_tenant_role 得到租户列表
  ├── 仅 1 个租户 → 直接进入，锁定 tenant_id
  ├── 多个租户 → 展示"我的店铺"列表（含角色标签）
  │     用户选择 → 锁定 tenant_id
  └── 0 个租户（纯顾客）→ 走扫码/链接场景带入 tenant_id
```

**一旦选定租户，本次会话所有请求携带 `tenant_id`；后端 MyBatis 拦截器自动拼接租户条件，杜绝越租户查询。**

## 十一、业务闭环（桌游店示例 · V1 线下收款版）

```
顾客小程序预约房间+助教 → 生成「待到店付」订单（系统不收钱）
        ↓
到店后：老板用自己收款码/现金/POS 线下收款（资金直进老板账户，不经平台）
        ↓
老板 PC 标记订单「已收款」 → 自动记"房间收入/助教服务费"流水
        ↓
助教小程序打卡确认完成
        ↓
老板 PC 发起周结 → 系统自动汇总单量 → 算出助教应发金额 → 生成结算单
        ↓
老板**线下**转账给助教（微信/银行/现金）→ 回来点「标记已线下发放」
        ↓
系统改结算单状态为「已发」+ 记录一笔"助教工资"支出流水（纯记账）
        ↓
老板小程序看周报：营收 - 助教工资 - 房租水电 = 净利
        ↓
（临时要调价）老板小程序改助教时薪 → 即时生效 + 记录日志
```

**资金流 vs 信息流（关键）：**
- **资金流**：顾客 → 老板（线下）→ 助教（线下），**平台全程不经手**
- **信息流**：预约/收款标记/结算单/流水/周报，全部在系统里跑

**老板全程操作：**
- PC：标记收款（每单）+ 确认结算/标记已发（1次/周）
- 小程序：看报表（每天）+ 改报价（偶尔）

> **系统定位：经营管理 + 记账工具，不是支付机构。** 这是 V1 合规的基石。

## 十二、支付与合规设计（V1 关键决策）

> **结论先行：小微版 V1 只做「预约 + 线下收款 + 系统记账 + 结算单」，系统不碰任何资金。**
> 这是当前阶段**合规成本最低、上线最快**的方案。

### 12.1 为什么不能在系统里"代发工资"

若让资金经过平台，会触发支付合规红线：

| 场景 | 是否合规 | 原因 |
|------|---------|------|
| 顾客付款 → **平台商户号** → 老板 → 助教 | ❌ **二清（二次清算）** | 用户付款先到平台商户号，再由平台分发给二级商户/个人，属**无证经营支付业务** |
| 系统代老板调转账接口给助教（资金经平台） | ❌ 二清 | 同上，平台成为资金清算节点 |
| 系统代发工资（哪怕老板点按钮触发） | ❌ 需支付资质 | "代付"属支付结算行为，需牌照或与持牌机构合作；涉及算薪还需人力/委托代征资质 |

> **核心红线：只要"付款/代付动作"由系统调用支付接口完成，且资金经过平台控制账户 → 即涉嫌二清。**

### 12.2 V1 合规方案：资金不经平台

```
顾客 ──线下付──→ 老板（老板自己的收款码/现金/POS，钱直进老板账户）
老板  ──线下付──→ 助教（微信/银行/现金，老板自己转）
                        │
                        ↓（只记账，不碰钱）
              ┌──────────────────┐
              │  本 SaaS 系统      │
              │  预约 / 收款标记    │
              │  结算单 / 流水      │
              │  报表               │
              └──────────────────┘
```

**系统定位：经营管理 + 流水记账工具，不是支付机构** → 完全避开二清。

### 12.3 各端收款/结算菜单（V1 已落地到菜单）

| 角色/端 | 菜单 | 是否涉及支付 | 说明 |
|---------|------|------------|------|
| 顾客 / 小程序 | 预约提交、查看收款方式 | ❌ | 只生成「待到店付」订单，**不调支付接口** |
| 老板 / PC | 标记订单「已收款」 | ❌ | 老板线下已收后**打勾**，仅记流水 |
| 老板 / PC | 生成结算单 | ❌ | 系统算出助教应发金额 |
| 老板 / PC | **标记已线下发放** | ❌ | 老板线下转账后**点状态**，不调转账接口 |
| 老板 / 小程序 | 报表 / 改价 | ❌ | 纯查看与配置 |
| 助教 / 小程序 | 我的收入 / 打卡 | ❌ | 只看"待发/已发"金额 |

> **全系统零支付接口调用。** "确认发放/打款"的语义全部改为「标记状态」。

### 12.4 合规边界速查

| 收款方式 | 是否合规 | 说明 |
|---------|---------|------|
| 老板用自己的微信/支付宝当面付收款码 | ✅ | 钱直接进**老板**商户号，与平台无关 |
| 顾客到店现金 / 老板自有 POS | ✅ | 老板自行管理 |
| **平台统一收款码（钱进平台商户号）** | ❌ **二清** | 严禁 |
| 系统代老板/助教调起支付（钱经平台再分） | ❌ **二清** | 严禁 |

### 12.5 后续若要在线支付（V2+，正确姿势）

> 待真有规模、确需在线收款时，**不碰资金归集**，采用微信支付**服务商模式**：

- 每个租户（桌游店）**自己进件**为子商户（`sub_mchid`），顾客付款**直进老板子商户号**
- 助教提成走微信**官方分账接口**（持牌机构执行分账，平台不经手）
- 平台只做「下单/查询/对账」的信息通道

→ 这样资金始终不经过平台，合规由微信支付持牌主体承担。**V1 不做，仅预留扩展点。**

### 12.6 给老板的一句话

> **系统帮你算清每笔生意赚多少、助教该发多少、每周净剩多少；钱你自己收、自己发，系统不碰一分钱。**

## 十三、小程序模块化页面架构

> **核心思想：页面 = 壳 + 区块配置。**
> 不是"boss/salesman/customer 各写一套首页"，而是**所有角色共用同一个页面壳**，由后台配置的"区块（Block）清单"决定谁看到什么。
> 加角色不加页面，只加配置；加功能不加分支，只加区块组件。

### 13.1 为什么不用三套页面

| 做法 | 问题 |
|------|------|
| ❌ `boss/home`、`salesman/home`、`customer/home` 三套 | 重复代码、维护成本高；加一个角色就要加一套页面 |
| ✅ 一个 `home` 壳 + 区块组件库 + 配置驱动 | 一套页面，三种样子，全由配置决定 |

**页面唯一、区块可复用、配置可后台编辑**——这是与"全角色共用一个小程序"一致的设计哲学。

### 13.2 区块组件库（一套，全角色共用）

> 每个区块是自包含的小组件：自己拉数据、自己渲染、自己处理点击。
> **它不关心"你是谁"，只关心"是否被配置显示 + 传了什么参数"。**

| 区块 key | 名称 | 典型使用角色 | 说明 |
|---------|------|------------|------|
| `revenue_week` | 本周收入概览 | boss | 营收/净利/环比 |
| `revenue_received` | 已结算收入 | salesman | "已经收到的钱" |
| `revenue_pending` | 待结算收入 | salesman | "老板还没发的部分" |
| `staff_photo_list` | 员工/助教照片墙 | customer | 顾客首页看谁在服务 |
| `activity_banner` | 活动推荐 | customer | 老板发布的优惠 |
| `quick_booking` | 快速预约入口 | customer | 一键选服务+时间 |
| `my_schedule` | 我的排班 | salesman | 今日/近期安排 |
| `checkin_entry` | 打卡入口 | salesman | 确认完成服务 |
| `shop_info` | 店铺信息卡 | all | 店名/营业时间/地址 |
| `notice_bar` | 消息提醒 | boss | 结算提醒/预警 |

→ **组件库只增不减：加新功能 = 新增一个区块组件 + 注册进组件库，不改任何页面。**

### 13.3 页面配置模型

**核心表 `page_block_config`：**

```sql
page_block_config
├── id
├── tenant_id          -- 租户（可继承系统默认）
├── role_code          -- boss / salesman / customer
├── page_key           -- 'home' / 'mine' / 'booking' / 'report' ...
├── block_key          -- 区块 key（指向组件库）
├── sort_order         -- 排序
├── show_flag          -- 是否显示
├── block_params       -- JSON：区块自定义参数
└── update_time
```

**默认配置示例（桌游店 · 首页 `home`）：**

| 角色 | page_key | block_key | 顺序 | 参数 |
|------|----------|-----------|------|------|
| boss | home | revenue_week | 1 | {period:'week'} |
| boss | home | revenue_pending | 2 | — |
| boss | home | notice_bar | 3 | — |
| boss | home | shop_info | 9 | — |
| salesman | home | revenue_received | 1 | — |
| salesman | home | revenue_pending | 2 | — |
| salesman | home | my_schedule | 3 | — |
| salesman | home | checkin_entry | 4 | — |
| customer | home | staff_photo_list | 1 | {role:'salesman'} |
| customer | home | activity_banner | 2 | — |
| customer | home | quick_booking | 3 | — |
| customer | home | shop_info | 9 | — |

→ **同一个首页壳：**
- **boss** → 收入数据（本周收入 + 待结算 + 提醒）
- **salesman** → 自己的收入 + 排班 + 打卡
- **customer** → 助教照片 + 活动 + 预约入口

### 13.4 渲染流程（小程序端）

```
① 进入任意页面（如首页 home）
② 请求 GET /page/config?pageKey=home
   （tenantId + roleCode 由后端从 token 取，前端不传）
③ 后端按 roleCode + pageKey 查 page_block_config
   → 返回该角色该页面的区块列表（有序、带参数）
④ 前端 home.wxml 循环渲染：
   <block wx:for="{{blocks}}" wx:key="blockKey">
     <component is="{{item.blockKey}}" data="{{item.params}}" />
   </block>
⑤ 每个区块组件各自调自己的接口拿数据
```

**前端伪代码：**

```html
<!-- pages/home/home.wxml -->
<view class="home">
  <block wx:for="{{blocks}}" wx:key="blockKey">
    <template is="{{item.blockKey}}" data="{{item}}"/>
  </block>
</view>
```

```javascript
// 各区块各自拉数据，互不干扰
Component({
  properties: { params: Object },
  attached() { this.fetchData() }
})
```

### 13.5 老板在 PC 后台"装修页面"（配置 = 拼积木）

> 老板/平台管理员从组件库里勾选区块、排序、设参数，**完全不用改代码**。

```
页面装修（PC 后台）
├── 选择要装修的页面：首页
├── 选择角色：boss / salesman / customer（三个 tab）
│
├── boss 首页  ← 拖拽排序
│     [✅] 本周收入概览
│     [✅] 待结算提醒
│     [✅] 消息通知
│     [✅] 店铺信息
│     [＋] 添加区块 → 从组件库选
│
├── 业务员 首页
│     [✅] 已结算收入
│     [✅] 待结算收入
│     [✅] 我的排班
│     [✅] 打卡入口
│
└── 顾客 首页
      [✅] 助教照片墙
      [✅] 活动推荐
      [✅] 快速预约
      [✅] 店铺信息
```

**配置能力：** 勾选/取消、拖拽排序、设置参数、恢复默认。

### 13.6 扩展到其他页面（同一套机制）

| 页面 key | boss 看到的 | salesman | customer |
|---------|------------|----------|----------|

### 13.9 好处与边界

| 好处 | 说明 |
|------|------|
| 一套页面，零重复 | 加角色不加页面，只加配置 |
| 老板可自助装修 | 不用找开发改首页 |
| 新增区块成本低 | 写一个组件 + 注册进组件库 |
| 天然适配多行业 | 不同行业配不同区块（买菜店放"今日团购"，健身房放"课表"） |
| 与权限解耦 | 页面（区块）和菜单（权限）两套配置各自独立 |

> **权限边界不变：** 区块的显示仍受 `perms` 管控（后端按角色返回区块清单时，自动剔除无权限的区块），
> 所以"配置了但没权限"的区块不会显示——**配置 ≠ 越权，最终以 perms 为准**。

## 十四、页面装修与权限的协同（重要）

> 页面配置（`page_block_config`）决定"区块怎么排"，权限（`perms`）决定"区块能不能出现"。
> 两者是**双层过滤**，缺一不可：

```
配置层（page_block_config）  →  老板自己拖的区块清单
        ↓
权限层（perms / sys_role_menu） →  该角色实际有权看到的菜单/功能
        ↓
> 最终渲染 = 配置 ∩ 权限

- 老板在装修后台**勾掉**的区块 → 配置层就不返回 → 前端不渲染
- 老板**勾上了**但角色**无权限**的区块 → 权限层过滤掉 → 前端不渲染
- 只有**既被配置、又有权限**的区块才最终显示

→ **配置是"个性化排版"，权限是"安全底线"，配置永远不能突破权限。**

## 十五、定时任务与多租户（XXL-JOB）

> **背景**：系统采用 **XXL-JOB** 作为分布式调度器，执行器集成在后台服务中。原生 XXL-JOB 没有"租户"概念，任务跑在调度线程池里，没有 HTTP 请求、没有登录用户，**MyBatis-Plus 的 `TenantLineInnerInterceptor` 取不到 `tenant_id`**，SQL 就不会拼租户条件——要么报错、要么查到平台表。
> **目标**：哪些自动任务需要按租户执行，就让它们在执行时**手动切入租户上下文**；平台级任务则明确清掉上下文。

### 15.1 任务分类：谁需要租户上下文

| 任务类型 | 典型例子 | 是否需要租户上下文 |
|---------|---------|-------------------|
| **平台级** | 清理 `sys_job_log` / 租户到期检查 / 刷新字典缓存 | 否 → `TenantHelper.clear()` 或标 `@TenantIgnore` |
| **租户级通用** | 小微版每日营收快照 / 预约过期自动关单 / 企业版月结 | **是 → 遍历活跃租户，逐个 set** |
| **版本限定** | 企业版高级版每月 1 号生成预算执行报表 | **是 → 遍历时按 `version_type` 过滤** |

> 小微版 V1（零支付、只记账）典型的租户级任务：**每天 23:59 生成当日营收快照写 `micro_daily_revenue`**、**预约过期自动关单**、**顾客 7 天未到店打标签**——这些都**必须按租户执行**。

### 15.2 核心机制：`@TenantJob` 注解 + `TenantJobAspect` 切面

> **关键原则：不按租户建 Job。XXL-JOB 调度中心只配「一个 Handler」，Handler 内部自己遍历租户、逐个切上下文。** 1000 个租户 = 1 条 XXL-JOB 任务，而不是 1000 条。

**（1）注解：**

```java
@Target({ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
public @interface TenantJob {
    /** 是否并行执行，默认串行（避免瞬时打满 DB 连接） */
    boolean parallel() default false;
    /** 限定产品线 tenant_type：micro / enterprise / 空=不限 */
    String[] versions() default {};

    /** 限定版本档位 version_type：micro_lite / micro_pro / basic / advanced / pro / 空=不限 */
    String[] versionTypes() default {};
}
```

**（2）切面（遍历租户 + 切上下文 + 异常隔离）：**

```java
@Aspect
@Component
@RequiredArgsConstructor
public class TenantJobAspect {

    private final SysTenantMapper tenantMapper;

    @Around("@annotation(tenantJob)")
    public Object around(ProceedingJoinPoint point, TenantJob tenantJob) throws Throwable {
        // 查所有活跃租户，并按 versions 过滤版本
        List<SysTenant> tenants = tenantMapper.selectActiveTenants();
        if (tenantJob.versions().length > 0) {
            tenants = tenants.stream()
                .filter(t -> ArrayUtils.contains(tenantJob.versions(), t.getVersionType()))
                .collect(Collectors.toList());
        }
        if (tenantJob.parallel()) {
            tenants.parallelStream().forEach(t -> runInTenant(t, point));
        } else {
            for (SysTenant t : tenants) {
                runInTenant(t, point);
            }
        }
        return null;
    }

    private void runInTenant(SysTenant tenant, ProceedingJoinPoint point) {
        try {
            // RuoYi-Vue-Plus 用 TenantHelper；原版若依的 TenantContextHolder 同理
            TenantHelper.setTenantId(tenant.getTenantId());
            MDC.put("tenantId", String.valueOf(tenant.getTenantId()));
            point.proceed();                        // 执行业务方法
        } catch (Throwable e) {
            XxlJobHelper.log("租户[" + tenant.getTenantId() + "]任务失败: " + e.getMessage());
            log.error("租户[{}]定时任务异常", tenant.getTenantId(), e);
            // 单租户失败不影响其他租户（⚠️ 必须 catch，不能抛回 XXL-JOB）
        } finally {
            TenantHelper.clear();
            MDC.remove("tenantId");
        }
    }
}
```

**（3）业务 Handler 写法（几乎零改造）：**

```java
@Component
public class MicroRevenueXxlJob {

    @Autowired
    private MicroDailyRevenueService revenueService;

    @XxlJob("microDailyRevenueJob")
    @TenantJob(versions = {"micro"}, versionTypes = {"micro_pro"})   // 只跑小微版·经营版（lite 无收支数据，跳过）
    public void buildDailyRevenue() {
        // 此处 TenantHelper.getTenantId() 已有值，MP 自动拼 tenant_id
        revenueService.buildTodaySnapshot();
        XxlJobHelper.handleSuccess("ok");
    }
}
```

XXL-JOB 调度中心只配一条任务：JobHandler = `microDailyRevenueJob`、Cron = `0 0 0 * * ?`、参数留空（租户列表由切面自己查）。

### 15.3 平台级任务：不标注解即可

```java
@XxlJob("cleanJobLogJob")
public void cleanJobLog() {
    TenantHelper.clear();   // 确保查 sys_job_log 不分租户
    jobLogService.cleanHistory(30);
    XxlJobHelper.handleSuccess();
}
```

> 也可在 Mapper 方法上标 `@TenantIgnore`（RuoYi-Vue-Plus 自带），显式跳过租户拼接。

### 15.4 与「版本 / 行业模板」联动

- **版本过滤**：`@TenantJob(versions = {"enterprise_adv", "enterprise_pro"})` 已解决——切面只遍历指定版本租户。
- **行业级更细开关**（如"只有桌游店才跑助教排班快照"）：在业务方法里再判断 `if (!IndustryTemplate.match(tenant, "boardgame")) return;`；精细到租户粒度时，可扩展一张 `tenant_job_whitelist(tenant_id, job_handler)` 表控制。
- **V1 阶段**：用 `versions` 过滤足够。

### 15.5 为什么不"按租户在 XXL-JOB 建多条任务"

另一种做法：调度中心给每个租户建一条任务，参数传 `{"tenantId":123}`，Handler 里 `XxlJobHelper.getJobParam()` 解析后 set。

**缺点**：1000 个租户 = 1000 条任务，调度中心页面爆炸，**Cron 改一次要改 1000 处**。只适合租户极少、且要物理隔离的场景——SaaS 不选它。

### 15.6 异步 / 多线程坑（必看）

若业务里用了 `@Async` 或线程池：
- `TenantHelper` 基于 **ThreadLocal，子线程拿不到父线程 tenantId**；
- 必须自己包装线程池，或用 `TenantHelper.execute(tenantId, () -> {...})` 把上下文显式传入；
- 否则子线程查库 `tenant_id` 为 null，MP 拦截器可能抛异常或查成平台数据。

### 15.7 日志与排查

- 切面已在 MDC 放 `tenantId`，日志框架配上 `[%X{tenantId}]` 即可按租户检索；
- 单租户异常已隔离，XXL-JOB 任务整体仍显示"成功"；**排查需依赖 `XxlJobHelper.log()` 与业务日志**；
- 如需在 `sys_job_log`（XXL-JOB 执行日志表）里看到 tenant_id，可在 log 前缀统一拼 `[tid=123]`。

### 15.8 自检速查（本模块）

| 检查项 | 要点 |
|-------|------|
| 一个 Handler 服务全量租户 | XXL-JOB 不按租户建多条任务 |
| `@TenantJob` 切面遍历 | set → proceed → clear，finally 必清 |
| 单租户异常隔离 | catch 后不抛回 XXL-JOB |
| 平台级任务清上下文 | `TenantHelper.clear()` / `@TenantIgnore` |
| 版本过滤 | `@TenantJob(versions=...)` |
| 异步线程传上下文 | 禁依赖 ThreadLocal 继承 |
| 调度配置与 `sys_job` 无关 | Cron/报警统一在 XXL-ADMIN |

## 十八、小微版分档与计费（v10.1 新增）

> 本章把第四章的分档设计落地为**可配置、可计费、可升级**的完整机制。

### 18.1 分档定义（权威）

| 字段 | micro_lite（轻量版） | micro_pro（经营版） |
|------|---------------------|---------------------|
| `tenant.tenant_type` | micro | micro |
| `tenant.version_type` | `micro_lite` | `micro_pro` |
| 定价 | 🆓 永久免费 | 💰 收费 |
| 功能范围 | **仅推广**：发海报 / 活动预告 / 公众号通知 / 店铺信息；**顾客/助教各有「活动浏览页」（只读）** | **lite 全部 + 经营全量**：预约 / 打卡 / 结算 / 收支 / 报表 / 定价 / 人员管理 |
| 映射角色 | `boss` + `salesman`(活动浏览页) + `customer`(活动浏览页) | `boss` + `salesman` + `customer`（全量菜单） |
| 小程序顾客/助教入口 | 活动浏览页（只读：海报/预告/店铺介绍，**无需登录、无预约/打卡/收入**） | 浏览 / 预约 / 我的预约 / 到店付（customer）；排班 / 收入 / 打卡（salesman） |
| 目标客户 | 只想做推广、攒客流的老板 | 要管清楚每一笔生意钱的老板 |

> **一句话**：lite = "会发 + 让人看"；pro = "会发 + 让人看 + 会管"。两档**只差菜单范围，不差架构**。
> **lite 档的"活动浏览页"是关键**：老板发的活动/预告/海报，顾客和助教都能看到——这是免费版也有"引流闭环"的原因；但**只能看、不能约、不能打卡、不能报名**，要互动就必须升级 pro。

### 18.2 功能矩阵（lite vs pro 逐菜单对照）

> ✅ = 该档开放；❌ = 该档通过角色模板**关闭**（表结构仍在，仅权限不可见）。

| 功能模块（boss 视角） | micro_lite | micro_pro |
|----------------------|:----------:|:---------:|
| **推广发布**（海报/活动预告/公众号推送） | ✅ | ✅ |
| 店铺信息设置 / 收款方式说明 | ✅ | ✅ |
| 经营概览 / 仪表盘 | ❌ | ✅ |
| 预约 / 订单管理 | ❌ | ✅ |
| 服务分类 / 服务项目 / 套餐 / 定价 | ❌ | ✅ |
| 人员结算（标记已线下发放） | ❌ | ✅ |
| 收支记录（收入/支出流水 + 补录） | ❌ | ✅ |
| 报表中心（周报/月报/利润） | ❌ | ✅ |
| 员工档案 / 结算规则 | ❌ | ✅ |
| 支出预警 / 预算 | ❌ | ✅ |
| **salesman 角色**（排班/收入/打卡） | 🔵 **活动浏览页（只读）** | ✅ 全量（活动浏览 + 排班/收入/打卡） |
| **customer 角色**（预约/我的预约） | 🔵 **活动浏览页（只读）** | ✅ 全量（活动浏览 + 预约/我的预约） |

> 🔵 = **只读访问**：lite 档下 salesman / customer **都能看到本店的活动浏览页**（海报/预告/店铺介绍），但**没有任何可操作功能**（无预约、无打卡、无收入、无报名）。`micro:activity:browse` 菜单对这两个角色开放，其余经营菜单关闭。

### 18.3 计费规则

> 定价对齐「文档2（多业态 SaaS PRD）」的 499 元/月标准。

| 计费方式 | 价格 | 说明 |
|---------|------|------|
| micro_lite | 🆓 0 元 / 永久 | 免费，不限时长 |
| micro_pro 首月 | 299 元 | 体验价，仅首月 |
| micro_pro 月付 | 499 元 / 月 | 按 30 天周期，到期不续则降级为 lite |
| micro_pro 包年（推荐） | 4790 元 / 年 | 499 × 12 × 0.8 ≈ 4790（8 折），日均约 13 元 |

> 校验：499 × 12 = 5988；5988 × 0.8 = 4790.4 ≈ 4790（取整）；包年比月付省约 1198 元。

### 18.4 升级 / 降级流程（核心：菜单级扩围，零迁移）

```
┌─────────────────────────────────────────────────────────┐
│  老板在 PC 后台点击「升级到经营版」                       │
│  → 后端创建订单（首月 299 / 月付 499 / 包年 4790）        │
│  → 支付成功（或试用激活）                                 │
│  → 事务内：                                               │
│     ① UPDATE tenant SET version_type = 'micro_pro'       │
│     ② 刷新 role_template 缓存（boss 菜单扩为 pro 集合）    │
│     ③ salesman / customer 角色的菜单从「仅活动浏览页」      │
│        追加为「活动浏览页 + 排班/收入/打卡（salesman）      │
│                  + 预约/我的预约（customer）」             │
│  → 前端刷新菜单，即时可见预约/结算/报表等入口              │
│  → lite 期间推广数据、活动浏览数据全部保留                 │
└─────────────────────────────────────────────────────────┘

降级（到期未续费）：
┌─────────────────────────────────────────────────────────┐
│  version_type: micro_pro → micro_lite                    │
│  → 菜单收回（预约/结算/报表不可见）                       │
│  → 数据保留（订单/结算单/流水不删，续费即恢复可见）         │
│  → salesman / customer 角色菜单收回至「仅活动浏览页」       │
│    （角色本身不断、用户绑定不断，只缩窄菜单范围）           │
└─────────────────────────────────────────────────────────┘
```

> **为什么能零迁移**：预约、结算、收支、报表等**数据库表和后端接口始终完整部署**，lite 档只是通过 `role_template` 把这些菜单从角色上"摘掉"。
> 升级 = 把菜单"装回来"，**没有 DDL、没有数据搬迁、没有业务中断**。
> **salesman / customer 的"活动浏览页"贯穿 lite 与 pro 两档**：升级只是"加菜单"，角色和页面壳不变，体验连贯。

### 18.5 与现有 `version_type` 机制的关系

```
tenant_type = micro 时：  version_type ∈ { micro_lite, micro_pro }
tenant_type = enterprise 时：version_type ∈ { basic, advanced, pro }

两条线完全对称：
  小微线  micro_lite ──→ micro_pro      （免费 ──→ 收费，菜单扩围）
  企业线  basic ──→ advanced ──→ pro    （解锁功能，菜单扩围）

实现方式完全一致：同一套标准角色 + 同一张 role_template 表
                   + 按 version_type 绑定不同菜单范围。
```

> **新增一档 = 在 `role_template` 加几行配置，不加角色 code、不改框架。**（沿用第二十四、二十五条自检原则）

## 一句话总结

> **全平台一个微信小程序，所有角色（老板/业务员/顾客/项目经理/报销人员/财务）都在里面，靠 `租户号 + 角色` 路由到不同视图；appid 只验身份不辨业务。PC 后台 = 老板 + 平台管理员的重管理阵地，菜单靠 `sys_menu.client_type` 与小程序自动裁剪，权限仍由若依原生 RBAC 统一管控。**
>
> **v9.0 角色核心：系统管理员定义「一套标准角色集」，各版本（小微版 / 企业版基础/高级/专业）的平台管理员通过「角色映射」挑选 + 改名 + 启用停用 + 分配用户；企业版高级版的项目经理/报销人员/财务与小微版的助教/配送员地位完全平等，共用同一套机制，权限永远由 admin 在角色模板里预置——平台管理员碰不到菜单。**
>
> **小程序页面采用"单一页面壳 + 区块组件库 + 后台配置"的模块化架构——所有角色共用同一套页面，谁看到什么、按什么顺序，全由 `page_block_config`（按 module_type 区分小微/企业区块）决定，老板可自行装修，加角色/加行业/加版本都不改页面代码。**
>
> **v10.0 定时任务核心：调度器统一采用 XXL-JOB，原生无租户概念，通过 `@TenantJob` 注解 + `TenantJobAspect` 切面实现租户化——租户级任务遍历活跃租户、逐个 `setTenantId → proceed → clear`，单租户异常隔离；平台级任务清上下文；一个 Handler 覆盖全量租户，版本过滤靠 `versions`，异步线程显式传上下文，Cron/报警统一在 XXL-ADMIN 管理。**
>
> **v10.1 小微版分档核心：小微版拆为 `micro_lite`（轻量版·免费，仅推广：发海报/活动预告/公众号通知）与 `micro_pro`（经营版·收费，放开预约/打卡/结算/报表/定价全部经营功能）；两档共用同一套标准角色集与同一张 `role_template` 表，仅靠 `version_type` 绑定不同菜单范围——升级 = `UPDATE tenant.version_type` + 菜单刷新，角色 code / 用户 / 业务数据零迁移；lite 期间推广数据在升级后完整保留。计费对齐 499 元/月标准（首月 299、包年 4790），到期未续则降级为 lite（菜单收回、数据保留）。**
>
> **v10.5 防爽约核心：仅 `micro_pro`（有预约功能）生效——顾客预约过期未到店且未主动取消 → 订单标记 `no_show`，累计次数 +1，满 3 次自动置 `is_blacklisted=1`；黑名单顾客「禁止新预约 + 活动推送默认过滤」双重限制，**唯一解除出口是老板在「顾客管理」手动移出**；爽约明细落 `no_show_record` 可追溯，跨租户按 `tenant_id` 隔离、移出不清零（保留信誉历史）。判定由第十五章 `@TenantJob` 定时任务逐租户扫描，版本过滤 `micro_pro`，单租户异常隔离。**

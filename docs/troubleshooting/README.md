# 技术组件排障手册

> 对应开发规范"四、技术组件排障手册" + "五、修复决策与发布判定"。
>
> **查阅方式**：日志中 `component = "xxx"` → 翻到对应组件章节 → 找到 `reason` 匹配项 → 查看"发布判定"与"修复方向"。

---

## 修复决策表

一句话：**异常的根因在"数据 / 配置 / 基础设施"→ 不发布；根因在"代码逻辑"→ 必须发布。**

| 根因位置 | 发布判定 | 典型场景 |
|---------|---------|---------|
| 数据（脏数据/缺失数据） | **不发布** | 修数据、补数据、清理重复记录 |
| 配置（参数错误/未配置） | **不发布** | 改配置项、补配置、调整开关 |
| 基础设施（宕机/网络） | **不发布** | 重启服务、切备用、恢复网络 |
| 代码逻辑 | **必须发布** | 补判空、修逻辑、加异常处理 |

---

## 4.1 Redis

### reason 匹配项

| reason 描述 | 发布判定 | 修复方向 | 备注 |
|------------|---------|---------|------|
| redis 连接池耗尽 | 不发布 | 检查连接池配置，排查连接泄漏 | 可能需要调整 maxTotal / maxIdle |
| redis key 过期导致缓存未命中 | 不发布 | 确认业务逻辑是否兜底查 DB | 如果代码未兜底则需发布 |
| redis 序列化/反序列化失败 | 需要发布 | 检查对象结构变更是否兼容旧缓存 | 可能需要清理缓存 |
| redis 集群节点不可用 | 不发布 | 检查集群状态，切换可用节点 | 基础设施问题 |

---

## 4.2 MySQL

### reason 匹配项

| reason 描述 | 发布判定 | 修复方向 | 备注 |
|------------|---------|---------|------|
| mysql 表不存在 | 不发布 | 执行建表 SQL | 检查 SQL 脚本是否已执行 |
| mysql 列不存在 | 不发布 | 执行补列 SQL | 检查版本升级脚本 |
| mysql 连接超时 | 不发布 | 检查网络、连接池、DB 负载 | 基础设施问题 |
| mysql 死锁 | 需要发布 | 优化事务范围和锁顺序 | 如果频繁出现需代码优化 |
| mysql 唯一约束冲突 | 不发布 | 检查数据是否重复 | 如果代码未做前置校验则需发布 |
| mysql 数据源未找到 | 不发布 | 检查数据源配置 | CannotFindDataSourceException |

## 4.3 HTTP 下游服务

### reason 匹配项

| reason 描述 | 发布判定 | 修复方向 | 备注 |
|------------|---------|---------|------|
| http-client 连接超时 | 不发布 | 检查下游服务状态 | 基础设施问题 |
| http-client 响应超时 | 不发布 | 检查下游服务性能，调整超时配置 | 可能需要增加超时时间 |
| http-client 返回非 200 | 不发布 | 联系下游排查 | 如果代码未处理异常状态码则需发布 |
| http-client 返回 null | 需要发布 | 补充判空逻辑 | 代码缺陷 |
| http-client 响应格式异常 | 需要发布 | 补充响应解析的容错处理 | 代码缺陷 |

## 4.4 消息队列（MQ）

### reason 匹配项

| reason 描述 | 发布判定 | 修复方向 | 备注 |
|------------|---------|---------|------|
| mq 连接断开 | 不发布 | 检查 MQ 服务状态 | 基础设施问题 |
| mq 消息发送失败 | 不发布 | 检查 MQ 服务，重试发送 | retryable=true 时可自动重试 |
| mq 消息消费异常 | 需要发布 | 检查消费逻辑，修复后重新消费 | 代码缺陷 |
| mq 消息格式不兼容 | 需要发布 | 补充消息解析的容错处理 | 代码缺陷 |

|------------|---------|---------|------|
| oss 上传超时 | 不发布 | 检查 OSS 服务状态和网络 | 基础设施问题 |

## 4.6 配置中心

### reason 匹配项

| reason 描述 | 发布判定 | 修复方向 | 备注 |
|------------|---------|---------|------|
| config 配置项缺失 | 不发布 | 补充配置项 | 数据/配置问题 |
| config 配置格式错误 | 不发布 | 修正配置格式 | 配置问题 |
| config 配置加载失败 | 不发布 | 检查配置中心连接 | 基础设施问题 |

---

## 4.7 扩展规则

- 新增组件时，按上述格式补充章节。
- 每种 reason 的描述必须遵循 **"组件 + 具体对象 + 状态/问题"** 的句式。
- 修复方向只描述"做什么"，不描述"怎么做"（不写命令/代码）。
- 如果某个 reason 的修复方向可能涉及发布，在备注中说明条件。

## 附录：AI 辅助修复模板

### 输入模板

```
## 上下文
系统：{系统名称}
环境：{环境，如生产/预发}
时间：{报错时间}

## 日志内容
{日志 JSON，脱敏后}

## 已知信息
- 异常类型：{exceptionType}
- 组件：{component，如有}
- 错误码：{errorCode，如有}
- 原因描述：{reason}

## 要求
1. 判定异常分类（业务/技术/代码bug）
2. 给出根因分析
3. 给出修复方向（区分是否需要发布）
4. 如果需要发布：指出涉及的逻辑范围
5. 如果不需要发布：指出具体操作对象
6. 给出验证方式
7. 给出预防建议
```

### 输出模板

```
## 异常分类
{类型} — {一句话说明}

## 根因分析
{基于日志字段的推理}

## 修复方向
### 发布判定：{需要 / 不需要}
### 具体操作
- {操作1}
- {操作2}

## 验证方式
{怎么确认问题已修复}

## 预防建议
- {建议1}
- {建议2}
```

### 约束

- AI 输出中的修复方案，最终由人确认后执行。
- AI 不执行任何变更操作，只输出方案。
- 涉及数据变更的，AI 只说明"改什么对象"，不生成具体 SQL（防误执行）。
- 涉及发布的，AI 只说明"改什么逻辑"，不生成完整代码。

## 开发自审清单

每人提交代码前逐条核对：

- [ ] 我的方法入口有没有判空关键参数？
- [ ] 我查 DB 返回的对象有没有判空？
- [ ] 我调外部接口返回有没有判空？
- [ ] 前端这个字段能不能用下拉框？
- [ ] 文本框长度有没有与 DB 字段对齐？
- [ ] 这张新表的 ID 是自增长的吗？
- [ ] 非空字段建表时标了 NOT NULL 吗？
- [ ] 如果出问题，日志里能看出是哪种异常吗？

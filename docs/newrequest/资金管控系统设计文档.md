## 一、总体设计

### 1.1 产品定位

系统定位为**资金管控平台**（ADR-019）：不是替代金蝶/用友记账，而是"管住下个月别花超 + 看清每个项目赚没赚"。覆盖完整资金流：

> **v1.3 定位修正（依据《多业态SaaS平台需求规格说明书》）**：资金管控不再是独立产品，而是多业态 SaaS 平台的**一个业态包（`biz_bundle.biz_code = fund_control`）**，与 `boardgame`（桌游店）、`fresh_food`（社区买菜）等业态包共用同一套公共底座（多租户隔离、收支三表、审批引擎、Schema 页面引擎、组队/组团引擎、微信/企微双通道登录、图片处理管线）。
>
> **能力版本边界同步修正**：需求规格说明书 4.1 版本矩阵与 5.4 明确——基础版资金管控为「轻量记账」，**完整预算科目、报销管控、烂账标记、发票验真、凭证（金蝶）导出、条件审批流自高级版起提供**，专业版增加多账套。因此本文档 1.4/1.5/1.6/1.7 全部按此重排，原 v1.2「预算编制→管控→凭证导出基础版完整提供」的边界作废。

```
支出类（报销单/付款单） + 收入类（收款单/收入确认） + 项目维度（资金汇聚容器）
→ 核算汇总（预算执行 / 项目利润 / 烂账预警）
```

### 1.2 全局多租户设计（硬约束）

系统全局采用 **SaaS 多租户模式**，租户隔离为所有模块的设计前提：

| 约束 | 说明 |
|------|------|
| **所有表必须带 `tenant_id`** | 全部业务表（含既有表与本文档新增的**每一张**表）必须包含 `tenant_id` 字段并建立租户索引，无一例外；建表评审时逐表检查 |
| 隔离方式 | 共享表 + `tenant_id` 行级隔离（ADR-007），由 MyBatis-Plus `TenantLineInnerInterceptor` 统一自动拼接租户条件，防漏过滤 = 防越权 |
| 租户识别 | `tenant_id` 置于 JWT payload（M-2），后端过滤器解析 → TenantContext（ThreadLocal）→ 拦截器拼 SQL；**绝不**从 URL/参数/前端传入 |
| 自动填充 | 新增/更新数据由 MetaObjectHandler 自动填充 `tenant_id`，业务代码零感知 |
| 部署形态 | 单域名 + 单实例逻辑隔离（M-3）；新租户开通 = 建租户记录 + 复制模板 + 分配版本；大客户物理隔离为专业版预留（FEAT_ISOLATED_SCHEMA） |
| 版本分配 | 版本（BASIC/ADVANCED/PROFESSIONAL）挂在**租户**维度，同一套系统按租户差异化解锁功能开关 |

### 1.3 核心业务主线（全版本一致）

**主干流程：老板定大类预算 → 系统按比例拆到预算科目 → 财务微调 → 定编制版本 → 费用管控，规则引擎全程穿插。**

```
① 老板设定费用大类（约6个）并制定各大类预算额度（只管粗粒度）
② 系统按历史实际支出结构比例，将大类额度自动分配到预算科目，生成编制初稿（无历史数据时按财务设置的默认拆分比例）
③ 财务人员在预算科目层微调（明细之和 = 大类限额，不得突破）
④ 老板确认 → 定预算编制版本 → 锁定并生成版本快照（不可变，调整走新版本）
⑤ 月中费用管控：报销提交瞬间大类硬拦截 + 科目软提示 + 项目双扣（规则引擎校验）
⑥ 报销单据经规则引擎自动匹配财务科目 → 财务兜底确认 → 计入实际 → 月末按模板导出凭证
```

**科目链路（大类 - 预算编制 - 财务科目）**：

```
费用大类（老板视角，约6个）
  ↑ 映射B（系统内置，固定）
预算科目（编制/管控中间层，预算编制的落点）
  ↑ 映射A（租户级，关键字+财务确认）
费用科目（财务科目，由客户提供）
```

- **财务科目由客户提供**：客户从自家财务软件（金蝶/用友等）导出科目表 → 导入本系统 → 关键字自动匹配 + 人工补完，建立映射A；
- **系统已准备 7 套模板**（通用/金蝶/用友/畅捷通/速达/管家婆/柠檬云）：既用于识别各主流财务软件的科目导入格式，也用于月末凭证导出，客户按自家软件选模板即可，零配置接入；
- **报销人不接触财务科目**（ADR-004）：只选大类，科目匹配是系统 + 财务的工作。

**规则引擎穿插点**：

| 阶段 | 规则引擎职责 |
|------|-------------|
| 编制阶段 | 按历史实际支出结构比例将大类额度拆分到预算科目（初稿自动生成；无历史数据时按财务设置的默认拆分比例） |
| 提交阶段 | 报销单据自动匹配财务科目：发票号精确 → 关键字精确 → 模糊 → 金额区间 → 人工兜底；同步执行大类额度校验 |
| 审核阶段 | 财务确认/纠偏科目，确认结果反哺规则库（越用越准） |
| 导出阶段 | 按所选模板取财务科目编码与借贷方向，生成凭证行 |

### 1.4 版本分级策略

采用**一套代码底座 + 三维组合**策略（需求规格说明书 2.1/2.3），不拆分多套产品：

| 维度 | 载体 | 说明 |
|------|------|------|
| **业态包** | `sys_tenant.biz_code` → `biz_bundle` | 决定菜单声明、文案映射、Schema 区块排列、引擎策略；新增行业仅需新增业态包 + 文案映射，**不动核心表结构** |
| **版本开关** | `sys_tenant.edition` → `feature_flag` | 决定功能可见性；基础版 = 轻量记账 + 活动/组团业态能力，高级版起解锁完整资金管控，专业版解锁多组织/多账套 |
| **访问通道** | `sys_tenant.access_channel` | `wechat`（公众号 + 小程序）/ `wecom`（企业微信自建应用）；决定入口形态与消息通道 |

| 原则 | 说明 |
|------|------|
| 底座标配 | 多租户隔离、收支三表、项目容器、审批引擎、通知体系、小程序壳为**全版本标配**，不接受业务定制 |
| 轻量记账标配 | 基础版提供收支三表（收款/付款/费用）轻量记账 + 项目资金流 + 极简确认审批，**不含**预算编制/科目三层/发票验真/凭证导出 |
| 资金管控高级版起 | 预算编制闭环、科目三层、报销管控与预警、规则引擎、发票验真、烂账、隐形成本、老板看板、凭证导出统一由高级版开关解锁 |
| 增量按版解锁 | 风控增强（打卡/信用/人脸）、组织扩展（部门/多组织/多账套）、报表增强按版本解锁 |
| 功能开关控制 | 所有版本差异通过功能开关（第五章 + `feature_flag` 表）控制，代码零分支 |
| 引擎靠策略 | 组队引擎、审批引擎通过策略模式分发，新业态新增子类，引擎源码零改动 |
| 文案靠映射 | 前端硬编码中文全部改为 `t('key')`，同一套代码按业态输出不同文案 |
| 单店靠覆盖 | 租户级 `tenant_biz_config.module_overrides` 微调，**不 fork 业态包** |
| 升级零迁移 | 基础版→高级版→专业版仅需解锁开关 + 执行增量脚本 + 分配菜单，数据全保留无需迁移 |

### 1.6 角色体系（按版本分层，v1.3 修正）

> 原 v1.2「三版本一致四角色」作废。需求规格说明书 4.1 明确角色数：基础版 2 个 / 高级版 4-6 个 / 专业版不限。

| 角色 | 标识 | 职责 | 主用端 | 基础版 | 高级版 | 专业版 |
|------|------|------|--------|:------:|:------:|:------:|
| 老板 | `boss` | 建项目/发活动、审批、看板、定总额 | 小程序为主 | ● | ● | ● |
| 店员/参与人 | `employee` | 报名/填报销单、选项目、补票 | 小程序 | ● | ● | ● |
| 财务 | `finance` | 编制微调、审核报销、核验收入、导出凭证、隐形成本配置 | PC 为主 | — | ● | ● |
| 项目经理 | `manager` | 确认收入（三态）、盯利润、发起合同变更 | 小程序为主 | — | ● | ● |
| 平台管理员 | `platform_admin` | 租户组织管理（用户/部门；高级版起 + 角色管理）、业态包启用、License 导入 | PC | ● | ● | ● |
| 租户自建角色 | 自定义 | 专业版 `platform_admin` 可自建/编辑/删除，数量不限 | PC | — | — | ● |

**角色数口径说明**：需求文档「2 / 4-6 / 不限」按**业务角色**计数（不含平台级 `platform_admin`）：

- 基础版 = `boss` + `employee`（2 个），对应个体小老板「老板 + 店员」；
- 高级版 = `boss` + `finance` + `manager` + `employee`（4 个），可按业态包扩展至 6 个（如新增 `store_manager` 店长 / `cashier` 出纳）；
- 专业版 = 不限，`platform_admin` 开放角色管理（菜单 101）自建租户级角色。

> 角色菜单分配详见《各角色菜单权限文档》；后端以 `@RequireRole` 方法级拦截 + 数据范围过滤双重防护（M-6、ADR-021）。`project_member.role` 统一为 `owner / manager / member / participant / signup`（需求文档 6），与系统角色解耦。

#### 1.8.4 双阶段租户识别（ADR 级决策，化解与 1.2 硬约束的冲突）

**冲突**：需求规格说明书 7.2 要求「URL 参数 `?tenant=xxx`、公众号 AppID 反查」识别租户；本文档 1.2 硬约束「`tenant_id` **绝不**从 URL/参数/前端传入」。

**决策：两者不矛盾，按阶段拆分。**

| 阶段 | 场景 | 识别方式 | 用途 | 权限含义 |
|------|------|---------|------|---------|
| **引导态**（登录前） | 公众号菜单点入、扫码进入、共用小程序首屏 | URL `?tenant=xxx` / 公众号 AppID 反查 / 首页门店选择 | 决定加载**哪个门店的公开展示数据**（店名、Logo、海报、活动列表、直播公告）与首页渲染 | **零数据权限**，只读公开态字段，接口白名单 + 限流 |
| **鉴权态**（登录后） | 一切业务读写 | JWT payload `tenant_id` → TenantContext → 拦截器拼 SQL | 决定业务数据的租户隔离 | **唯一权限来源，1.2 硬约束不变** |

**关键约束**：

1. 引导态接口走**独立白名单 Controller**（建议 `/portal/**`，免鉴权），**不得**复用业务接口；返回值只含公开展示字段；
2. 引导态解析出的 `tenant` 只能写入**前端展示上下文**，**绝不**写入后端 `TenantContext`；
3. 用户可能归属多个租户（`user_tenant_bind`，openid 跳租户），登录时必须**显式选定**当前 tenant 再签发 JWT，**禁止按 openid 自动猜测**；
4. 引导态 URL 参数被篡改时，最坏结果仅为「看到别家门店的公开首页」，登录后仍只能操作自己租户数据 → **不构成越权**；
5. 共用小程序首页**不可空白**（微信审核硬要求），必须提供门店选择/搜索入口（需求文档 7.3）。

#### 1.8.5 四大设计原则落地（需求规格说明书 2.3）

| 原则 | 落地手段 | 反例（禁止） |
|------|---------|------------|
| **项目即容器** | 所有业态业务实体 FK → `project`，差异字段进 `extra_config` JSON（`project_task` / `project_signup` 分表） | 为每个业态建独立主表 |
| **引擎靠策略** | 组队/组团/审批引擎按 `biz_bundle.engine_strategy` 分发到策略实现类（`FullHouseStrategy` / `GroupBuyStrategy`） | 在引擎源码里写 `if (bizCode == "boardgame")` |
| **文案靠映射** | 前端全部 `t('key')`，文案表按 `biz_code` 取值，缺失回落默认包 | 前端硬编码「项目」「报销」「活动」 |
| **单店靠覆盖** | `tenant_biz_config.module_overrides` JSON 覆盖模块开关/文案/字段可见性 | fork 一份业态包给单店改 |

## 二、基础版（BASIC）详细设计

### 2.1 版本定位（v1.3 修正）

面向**个体小老板 / 约 50 人小公司**，提供**轻量记账 + 项目资金流闭环**：收支三表录入（收款/付款/报销）→ 项目立项与项目预算 → 收入确认三态 → 合同变更 → 三层通知 + 极简确认审批。同时具备**完整业态能力**（活动管理、海报主题、直播公告、组队组团）。

> **v1.3 边界修正**：原「基础版 = 完整资金管控闭环（预算编制→月中管控→看板→凭证导出）」定位**作废**。依据需求规格说明书 4.1「基础版资金管控 = 轻量记账」与 5.4「资金管控为高级版核心能力」，预算编制/科目三层/报销管控/规则引擎/发票验真/后补通道/烂账/关联规则/隐形成本/老板看板/凭证导出**统一下移到高级版**（开关见 5.1 组 A）。本章 2.2~2.7 的设计细节**保留不删**，作为下移后能力的实现基线，仅版本归属按 2.2 开头的划分表重定。

**设计约束**：
- 基础版仅**项目级自定义科目**（`fee_project_subject`），不引入系统级费用大类主数据与公司级预算（ADR-009 预留 `department_id` 字段，不启用）
- **极简确认审批**：单级老板一人批（立项/付款/变更/收入核验），不引入多级条件流转（`FEAT_FLOW_MULTI_LEVEL` 高级版起）
- **角色数 = 2 个**（`boss` + `employee`，需求规格说明书 4.1）；`finance` / `manager` 自高级版起开放
- 基础版**不提供**发票验真与后补通道，报销单仅录入金额/事由/附件，不做科目匹配与额度拦截
- 共用小程序形态：平台 AppID，公众号菜单带 `?tenant=xxx`（引导态识别，见 1.8.4）

### 2.3 核心流程设计

**① 月初编制闭环**

```
老板设定大类及大类预算（约6个大类额度）
→ 系统按历史实际支出结构比例，将大类额度自动分配到预算科目（生成初稿；无历史数据时按财务设置的默认拆分比例）
→ 财务在大类限额内微调预算科目（明细之和 = 大类限额）
→ 老板确认/打回 → 定预算编制版本 → 锁定生成版本快照 → 管控生效（规则引擎全程穿插）
```

**② 报销管控流程**

```
报销人：选大类 → 填金额描述 → 选项目(按角色规则) → 传发票/勾选后补 → 提交
提交瞬间：大类额度校验(硬拦截) + 项目预算双扣(关联项目时) + 科目自动匹配
→ 财务审核(确认/纠偏科目，后补单必填理由) → 老板审批 → 通过后计入实际
```

**③ 收入确认三态**

```
项目经理创建(附依据) → 🟡待核验（不计利润）
财务核验通过 → ✅已核验（计入利润）｜核验驳回 → ❌已驳回（补据重提）
收款单审核通过 → 联动生成已核验记录（财务即核验人）
```

**④ 合同变更分步生效**

```
发起变更单 → 老板审批 → 通过：合同额/预算+=delta（仅未来，基线保留）
→ 状态=待收款确认🟡 → 财务确认到账 → 闭环
→ 超期：30天🟡收款逾期 → 60天🟠长期未到 → 90天🔴疑似烂账
```

**⑤ 后补通道（基础版规则）**

| 环节 | 规则 |
|------|------|
| 提交 | 勾选"发票后补"+预计补票日期（默认7天，不可按信用延长） |
| 审批 | 财务审核必须填理由；一律老板审批（不管金额） |
| 额度 | 审批通过→大类额度预占（已承诺未核销）；补票完成→转实扣；超时→释放+标记异常 |
| 看板 | 大类卡片区分"实扣/预占/剩余" |

| 角色 | 可用功能 | 关键限制 |

| 环节 | 机制 | 说明 |
|------|------|------|

## 三、高级版（ADVANCED）详细设计

### 3.1 版本定位

在基础版全部能力之上，面向中型企业补齐**风控增强**（打卡/信用/证据链）、**组织细化**（部门级预算）与**经营分析**（项目利润报表、规则自定义）。核心升级话术："基础版管住钱，高级版看穿钱 + 防住假"。

> **v1.3 重大扩展**：高级版同时**承接从基础版下移的全部资金管控重能力**（见 1.7 矩阵与 5.1 组 A 共 11 项开关）：预算编制与调整、科目三层、报销管控与预警、规则引擎、发票验真、后补通道、烂账标记、项目关联规则、隐形成本、老板看板、凭证导出；另增完整多级审批流、独立小程序、企业微信通道（5.1 组 C）。升级话术修订为：**"基础版记好账，高级版管住钱 + 看穿钱 + 防住假"**。
>
> **实现影响**：下移能力的接口必须补 `@RequireFeature`（开关编码见 5.1 组 A），菜单按 T2.2 高级版模板分配，定时任务执行前校验开关（T4.4）；已有数据与表结构**全部保留**，基础版仅关闭入口（降级保护，开发任务文档 0.2）。本章 3.2 原有六项增量设计不变，与下移能力**叠加**生效。

### 3.2 增量功能设计

#### 3.2.1 打卡定位（防假账辅助，ADR-014 定位：威慑非定罪）

**触发规则（可配置）**：

| 条件 | 触发动作 |
|------|---------|
| 大类=差旅/招待 | 报销提交时要求定位+拍照 |
| 单笔金额 ≥ 500 | 同上 |
| 该员工历史异常 ≥ 2 次 | 同上 |

**处理逻辑**：定位精度 > 50 米 → 标记"定位存疑"（不拦截）；小额单据自动跳过打卡减少待办。打卡记录与证据等级（medium）写入报销追溯时间线。

#### 3.2.2 信用体系（后补通道差异化）

**信用分规则**：按时补票 +2；逾期 -5；连续 3 次按时 +10 奖励。

**信用等级 → 权限**：

| 等级 | 条件 | 无发票报销权限 |
|------|------|---------------|
| 🟢 优秀 | ≥80 分 | 免老板审批（仅财务审），补票期限延长至 14 天 |
| 🟡 正常 | 50-79 分 | 标准流程（老板审批，7 天期限） |
| 🔴 受限 | <50 分 | 禁止无发票报销，必须上传发票 |

**实现要点**：新增 `fee_employee_credit`（信用分/等级/按时次数/连续次数）与 `fee_credit_rule`（加减分规则配置，财务可维护）；`creditScoreCalcJob`（每周一 02:00）重算等级；小程序"我的"页展示本人信用分。

#### 3.2.3 部门级预算与弹性额度

- 大类额度支持**公司级/部门级双粒度**（启用预留的 `department_id`）
- 编制闭环扩展到部门：部门预算汇总 → 财务平衡 → 老板确认锁定
- 弹性额度：部门大类超支但在弹性阈值内（如 +10%）→ 自动标记预警放行，超出才拦截
- 报销按提交人部门扣对应部门额度；未归类（公司级）不扣部门

#### 3.2.4 规则引擎租户级自定义

- 财务可在 PC 端维护**本租户**关键字匹配规则（大类+关键字+金额区间）
- 映射走**草稿→发布**流程（ADR-008），发布前做影响分析（影响多少预算/报销）
- 每条报销保留匹配链路（匹配方式/关键词/是否人工修改），支持追溯反查

#### 3.2.5 项目利润报表（高级版核心卖点）

| 能力 | 说明 |
|------|------|
| 纸面利润 vs 实际利润 | 纸面=合同额-(已核验+待核验)-支出；实际=已核验收入-支出，分开显示 |
| 利润拆解 | 已核验收入 - 报销/付款 - 折旧分摊 - 项目分成 = 项目利润；公司毛利 = 总收入-(项目支出+固定成本) |
| 收支时间线 | 合同→首付→进度款→验收→付款→收款全链路追溯 |
| 收入确认进度 | 已核验/合同额进度条 |
| 导出 | 项目利润报表按项目/按月导出 |

#### 3.2.6 其他增量

- **自定义凭证模板**：在内置 7 套基础上新增/修改模板（列头定义/分隔符/借贷方向）
- **证据链分级**：每条报销单存 `evidence_level`（strong/medium/weak），看板异常筛选支持多维标记
- **项目关联规则自定义**：可开启"某大类所有角色强制关联"/"某项目严格模式"
- **批量操作**：财务报销审核批量通过/打回

## 四、专业版（PROFESSIONAL）详细设计

### 4.1 版本定位

面向集团/多组织客户，在高级版之上提供**多组织预算体系**、**生物识别防作弊**、**完整规则引擎与版本快照**、**二维核算导出**。核心升级话术："集团多公司独立预算，一张表看清项目×科目"。

### 4.2 增量功能设计

#### 4.2.1 多组织体系

```
集团总部（租户）
 ├── 子公司A（独立预算体系、独立科目树覆盖、独立锁定快照）
 ├── 子公司B
 └── 合并视角（集团看板：各子公司汇总 + 抵销项标记）
```

- 组织树：`fee_org`（tenant_id + parent_id），用户挂组织
- 预算编制按组织分别走闭环，各自生成**组织版本快照**（组织合并/拆分时新旧版本隔离）
- 额度粒度：公司级/部门级/组织级三层
- 数据范围：用户可见范围 = 本组织 + 下级组织（管理员全量）
- 同租户多组织复用单域名 + tenant_id 隔离（M-3），组织为租户内二级维度

#### 4.2.2 人脸比对防作弊

- 大额报销（阈值可配，默认 ≥2000）/ 敏感大类提交时触发人脸核身
- 小程序端调起人脸采集 → 与入职底照比对 → 不一致标记"人脸存疑"进异常池
- 与打卡、发票验真组成三级证据（人脸为 strong 级）

#### 4.2.3 项目-科目二维导出

在凭证导出基础上新增第二张 Sheet：

```
        差旅招待 | 住宿费 | 材料费 | 合计
客户A    3000    2000    10000   15000
工程B     --      --     25000   25000
合计     3000    2000    35000   40000
```

财务直接用于金蝶项目辅助核算明细贴账，省去手动汇总。

#### 4.2.4 完整规则引擎与版本快照

- 规则发布**灰度**：新规则先对 10% 单据生效，比对命中率后再全量
- 规则版本快照：已锁定预算永远使用当时的规则快照，规则迭代不腐蚀历史（ADR-008 延伸）
- AI 语义匹配（可选开启）：未命中关键字的单据由语义模型推荐科目，财务一键确认

#### 4.2.5 成员跨项目负载预警

- 拉人进项目时显示"已在哪些项目"，允许跨项目不拦截
- 投入比例（手动维护）合计 >100% 时提示负载超限
- 老板看板新增"团队人力分布"卡片

#### 4.2.6 大客户物理隔离（预留，M-5）

- VIP 租户可切换独立 schema（动态数据源），业务代码因 TenantContext 透传无需改动
- 交付形态：租户配置项 `isolation_mode=SHARED/DEDICATED`

### 4.3 专业版增量页面

**PC 新增**：组织管理（组织树/用户归属）、组织预算编制与快照管理、人脸核身配置、二维导出入口（导出页附加选项）、规则灰度发布管理、团队人力分布看板
**小程序增量**：登录后"选择组织"（多组织用户）、大额报销人脸核身流程

### 4.4 专业版增量数据模型

> 全部增量表均带 `tenant_id`（全局多租户硬约束，见 1.2）；多组织为租户内二级维度，组织相关表同时带 `tenant_id + org_id`。


| 表 | 说明 |
|----|------|
| fee_org | 组织树（租户内） |
| fee_org_budget_version | 组织级预算版本快照 |
| fee_face_verify_record | 人脸核身记录（比对结果/存疑标记） |
| fee_rule_version | 规则引擎版本快照（灰度状态） |
| 成员表扩展 | 投入比例字段（负载计算） |

### 5.2 控制机制

| 层 | 机制 | 说明 |

| API 层 | 功能开关拦截（注解式，如 `@RequireFeature("FEAT_CREDIT_SCORE")`） | 版本不足直接拒绝，防绕过 |
| 前端 | 版本能力配置下发（`/system/edition/features`）→ 动态渲染 | 未解锁功能入口不显示 |
| 定时任务 | 任务执行前校验租户开关 | 如基础版租户跳过信用分重算 |
| 菜单 | 菜单可见性由角色控制，**与版本解耦** | 升级解锁后需为角色分配新增菜单（见第六章） |

## 六、版本升级路径

### 6.1 升级流程（零迁移）

```
① License/租户表更新 edition 值（BASIC → ADVANCED → PROFESSIONAL）
② 执行该版本增量脚本（新增表/字段，均为增量，不改存量数据）
③ 为对应角色分配新增菜单（菜单与版本解耦，须手动授权）
④ 重启服务 → 功能开关生效，前端入口自动出现
```

### 6.2 各级新增能力速览（v1.3 重排）

| 升级路径 | 新增能力 | 开关数 |
|---------|---------|:------:|
| 基础版 → 高级版 | **【v1.3 下移承接】**预算编制与调整、科目三层（大类主数据/映射A/映射B/财务科目导入）、报销管控与三级预警、规则引擎（内置关键字）、发票 OCR+验真+金额比对、无发票后补通道、烂账标记+坏账计提、项目关联规则（内置三层）、隐形成本四项、老板看板、凭证导出（内置 7 套模板）<br>**【原有增量】**打卡定位、信用体系（后补差异化审批）、部门级预算、弹性额度、规则自定义+影响分析、项目利润报表、自定义模板、证据链分级<br>**【底座新增】**完整多级审批流、独立小程序（客户 AppID）、企业微信自建应用、`finance`/`manager` 角色 | 23 项 |
| 高级版 → 专业版 | 多组织+组织快照、**多账套**、人脸比对、二维导出、规则灰度+AI语义、成员负载预警、物理隔离预留、**自定义流程设计器**、**开放平台 API**、**不限角色数（可自建）** | +10 项 |

> **升级不迁移**：基础版已录入的收支三表/项目数据在升级后全部保留并自动纳入预算执行与看板统计；降级时已产生的预算/报销/凭证数据**保留不删除**，仅关闭增量入口（开发任务文档 0.2 降级保护）。

### 6.3 升级兼容性约束

- 部门级预算启用后，历史公司级预算继续有效，新月度按部门编制（不回溯）
- 多组织启用后，存量数据默认挂"总部"组织，不影响既有流程
- 信用分自启用日起累计，不回溯历史补票行为
